12. Developing Secure Applications on AWS

1. Introduction

O foco da arquitetura de aplicações na nuvem agora muda da escalabilidade e performance para o pilar mais crítico do AWS Well-Architected Framework: a Segurança. Este módulo aborda a proteção de ponta a ponta da aplicação, lidando com tráfego público na internet, criptografia e a autenticação/autorização de usuários reais.

Objetivos de Aprendizado

Ao final deste módulo, você aprenderá a proteger sua aplicação em duas frentes principais:

  • Proteger as conexões de rede entre os clientes (navegadores/apps móveis) e os servidores através da internet pública utilizando criptografia SSL/TLS e gerenciamento automatizado de certificados.
  • Controlar o acesso de usuários aos recursos da AWS utilizando o AWS STS (Security Token Service) e o Amazon Cognito para federação de identidades seguras e temporárias.

O Caso da Cafeteria (O Portal do Funcionário)

Até este momento, o site da cafeteria era 100% público: qualquer cliente podia navegar pelo cardápio e fazer pedidos. No entanto, com a automação de relatórios gerenciais e acompanhamento de estoque implementada no Módulo 11 (Step Functions), Sofía e Frank precisam criar uma área restrita e autenticada (portal de login) dedicada exclusivamente aos funcionários.

Construir do zero sistemas completos de autenticação, armazenamento seguro de senhas com hash e salt, fluxo de recuperação e emissão de tokens de autorização é um processo complexo, caro e suscetível a brechas críticas de segurança. Para solucionar isso de forma profissional, a equipe integrará o Amazon Cognito:

  • Um serviço totalmente gerenciado pela AWS que disponibiliza telas de login responsivas, suporte a autenticação multifator (MFA) e diretórios de usuários (User Pools).
  • Fornece tokens temporários de segurança integrados ao Amazon API Gateway e ao AWS STS, garantindo que apenas funcionários autenticados consigam disparar o fluxo de relatórios no Step Functions e acessar relatórios protegidos no S3.
Amazon Cognito na arquitetura da cafeteria: autenticando funcionários, fornecendo tokens de autorização para o API Gateway e protegendo a orquestração do Step Functions

A Regra de Ouro da AWS: Modelo de Responsabilidade Compartilhada

A segurança na nuvem obedece estritamente ao AWS Shared Responsibility Model:

  • A AWS garante a Segurança DA Nuvem (Security OF the Cloud): Proteção física das instalações e data centers, hardware dos servidores, refrigeração, rede física global e os hypervisors de virtualização.
  • Você garante a Segurança NA Nuvem (Security IN the Cloud): Criptografia de dados (em repouso e em trânsito), gestão segura de credenciais e senhas, configuração de firewalls (Security Groups/NACLs/WAF) e permissões de acesso da própria aplicação.

Enquanto nos módulos anteriores a segurança foi abordada em nível de infraestrutura com o Amazon VPC (isolamento de sub-redes públicas e privadas) e o AWS IAM (permissões de execução entre serviços da AWS), agora o foco será a camada de aplicação: proteger dados em trânsito contra espionagem e autenticar com precisão as identidades dos usuários finais.

2. Securing network connections

Para proteger dados confidenciais enquanto eles trafegam pela internet pública entre navegadores, smartphones e os servidores de backend (criptografia em trânsito), a AWS foca na padronização, automação e eliminação de falhas humanas na gestão de certificados de segurança.

Na internet aberta, criptografar os pacotes de dados não é suficiente: o cliente precisa ter a certeza absoluta e inequívoca de que o servidor com quem ele está conversando é genuinamente quem afirma ser (Autenticidade e Identidade do Servidor).

Como Funciona a Criptografia SSL/TLS?

O protocolo TLS (Transport Layer Security) e seu antecessor histórico SSL (Secure Sockets Layer) formam os alicerces fundamentais do HTTPS:

  • Para estabelecer uma conexão segura e confiável, o servidor Web apresenta ao cliente um Certificado Digital Público assinado por uma CA (Certificate Authority - Autoridade Certificadora) de renome mundial.
  • A CA funciona como um "cartório digital" da internet: como o sistema operacional ou navegador do usuário já traz pré-instaladas as chaves das CAs confiáveis, ele valida a assinatura criptográfica do certificado do servidor.
  • Uma vez confirmada a identidade do servidor, cliente e servidor realizam o aperto de mãos (TLS Handshake), combinam uma chave de sessão simétrica efêmera e passam a trafegar dados com criptografia de ponta a ponta sem risco de interceptação (ataques Man-in-the-Middle).

O Problema: Gestão Manual de Certificados

Gerenciar certificados SSL/TLS manualmente em ambientes corporativos modernos é um verdadeiro pesadelo operacional sujeito a erros graves:

  • Renovações Esquecidas: Certificados possuem prazo de validade estrito (geralmente 1 ano ou até 90 dias). Deixar um certificado expirar derruba imediatamente o acesso dos clientes, exibindo telas vermelhas de alerta no navegador — uma das falhas humanas mais frequentes e danosas na indústria de TI.
  • Custo e Complexidade Elevados: Adquirir certificados comerciais, gerar CSRs (Certificate Signing Requests), aprovar domínios manualmente e distribuir chaves privadas em dezenas ou centenas de servidores requer orçamento dedicado e consome tempo excessivo de equipes de DevOps.

A Solução AWS: AWS Certificate Manager (ACM)

O AWS Certificate Manager (ACM) é o serviço gerenciado da AWS que simplifica e automatiza completamente todo o ciclo de vida de certificados SSL/TLS públicos e privados. É um tema cobrado intensamente nos exames de desenvolvedor e arquiteto:

  • Automação Total: O ACM provisiona, valida (via registros DNS Route 53 ou e-mail), implementa e renova automaticamente os certificados SSL/TLS antes que eles expirem, sem necessidade de intervenção humana.
  • Custo Zero para Uso na AWS: Os certificados públicos gerados e gerenciados pelo ACM para uso nos serviços da AWS são 100% gratuitos.
  • Integração Nativa e Protegida: O ACM não instala chaves privadas diretamente no sistema operacional de instâncias EC2 comuns. Em vez disso, ele se acopla diretamente aos pontos de terminação gerenciados da AWS:
    • Elastic Load Balancing (ALB e NLB)
    • Amazon CloudFront (CDN global)
    • Amazon API Gateway (APIs REST, HTTP e WebSocket com domínios customizados)

Arquiteturas Comuns de Segurança de Rede

A integração do ACM permite adotar padrões arquiteturais consolidados para segurança perimetral:

1. Terminação TLS no Load Balancer (TLS Termination):

Em vez de fazer cada instância EC2 ou contêiner gastar capacidade preciosa de processamento (CPU) criptografando e descriptografando fluxos HTTPS, você atrela o certificado do ACM diretamente ao Load Balancer (ALB).

  • O ALB recebe o tráfego HTTPS criptografado vindo da internet pública na porta 443.
  • O balanceador descriptografa os pacotes (terminação TLS) e encaminha as requisições HTTP internas de forma rápida e leve para as instâncias EC2 localizadas na sub-rede privada da VPC.
  • Desonera os servidores de aplicação e centraliza a renovação de chaves em um único ponto arquitetural.

2. CloudFront + Origin Access Identity (OAI / OAC):

Quando você distribui uma aplicação web estática ou arquivos confidenciais armazenados no Amazon S3 através da rede de borda do CloudFront, surge um risco: usuários poderiam tentar acessar o bucket S3 diretamente via URL do bucket, contornando o HTTPS forçado e os mecanismos de segurança do CloudFront.

  • Para fechar essa brecha, configura-se uma Origin Access Identity (OAI) ou o recurso moderno Origin Access Control (OAC) no CloudFront.
  • A política do bucket S3 (Bucket Policy) é configurada para bloquear qualquer acesso público direto e autorizar estritamente a identidade de acesso do CloudFront.
  • Dessa forma, todo e qualquer tráfego é forçado a trafegar pelo CloudFront com HTTPS criptografado de alta velocidade.

3. Authenticating with AWS STS

Entramos em um dos conceitos fundamentais da segurança na nuvem: a concessão de privilégios e permissões sem a criação de usuários fixos ou credenciais permanentes, utilizando o AWS STS (Security Token Service).

O AWS STS é o serviço global da AWS especializado em emitir e gerenciar credenciais de segurança temporárias com tempo de expiração programado (de minutos a poucas horas).

A Regra de Ouro da Segurança na AWS: Nunca incorpore, grave ou embuta chaves de acesso estáticas e permanentes (AWS_ACCESS_KEY_ID e AWS_SECRET_ACCESS_KEY) dentro do código-fonte, repositórios de controle de versão (Git) ou imagens de contêiner. Utilize sempre credenciais temporárias fornecidas dinamicamente pelo AWS STS.

Quem Precisa de Credenciais Temporárias? (Entidades Confiáveis)

O AWS STS pode conceder tokens de acesso temporários para três grandes grupos de consumidores:

  1. Usuários IAM Existentes (Acesso Cross-Account): Permite que desenvolvedores ou operadores com identidade IAM em uma conta AWS assumam papéis (Roles) em outra conta AWS (como alternar temporariamente da conta de desenvolvimento para a de homologação ou produção) sem precisar de múltiplos logins.
  2. Serviços da AWS (EC2, Lambda, ECS): Em vez de armazenar credenciais dentro de servidores virtuais ou contêineres, as instâncias assumem IAM Roles (Funções de Execução). O STS injeta periodicamente credenciais temporárias atualizadas via serviço de metadados da instância (IMDS).
  3. Identidades Federadas (O Grande Foco de Aplicações): Usuários que não possuem e não devem possuir conta na AWS nem usuário no IAM, mas que realizam login na sua aplicação através de um provedor de identidade externo. O STS atende a federação em duas grandes categorias:
    • Enterprise SSO (SAML 2.0 / Active Directory): Para colaboradores internos da empresa autenticando via diretórios corporativos corporativos (como Microsoft Active Directory, Okta ou PingFederate).
    • Web Identity (Social Sign-in via OIDC): Para clientes e consumidores finais que utilizam provedores de grande escala, como Google, Facebook, Apple ou Login with Amazon.

Como Funciona o Fluxo de Federação? (O Papel do Identity Broker)

Quando um usuário externo faz login em um aplicativo web ou móvel, a aplicação utiliza um Identity Broker (como o Amazon Cognito Identity Pools) para orquestrar duas etapas distintas:

Etapa 1: Autenticação Externa (Quem é você?)

  • O usuário insere seu login e senha diretamente no provedor confiável (ex: tela de login do Google ou Facebook).
  • A aplicação da cafeteria nunca enxerga ou manipula a senha do usuário.
  • O provedor externo confirma a identidade do usuário e devolve para a aplicação um Token de Identidade criptograficamente assinado (JWT).

Etapa 2: Autorização na AWS (O que você tem permissão de fazer?)

  • O Identity Broker repassa o token validado para o AWS STS.
  • O AWS STS valida a autenticidade do token com o provedor externo, avalia as políticas da IAM Role associada àquele perfil e gera um conjunto de credenciais temporárias da AWS contendo 4 valores:
    1. AccessKeyId: Identificador da chave temporária (iniciado normalmente com o prefixo ASIA...).
    2. SecretAccessKey: Chave de acesso secreta temporária.
    3. SessionToken: Token de sessão de segurança obrigatório que acompanha cada requisição assinada (SigV4).
    4. Expiration: Timestamp exato informando a data/hora em que as credenciais deixarão de funcionar.

Poder Prático para o Desenvolvedor: Com essas chaves temporárias em mãos no smartphone do usuário, o aplicativo móvel pode realizar ações diretamente na AWS — como fazer upload de fotos diretamente para o Amazon S3 ou ler itens autorizados no Amazon DynamoDB — sem precisar sobrecarregar os servidores da aplicação para intermediar o tráfego de arquivos grandes!

Rastreabilidade e Auditoria com o AWS CloudTrail

Uma dúvida frequente de governança e segurança: Se um usuário externo realizou login social via Google, obteve credenciais temporárias do STS e deletou um arquivo vital do S3 ou alterou um pedido no DynamoDB, como a equipe forense descobre a identidade exata de quem cometeu a ação?

A Resposta é o AWS CloudTrail:

  • O CloudTrail registra integralmente todas as ações executadas no ambiente AWS, mesmo quando efetuadas através de credenciais temporárias.
  • Ao investigar o evento destrutivo no log (por exemplo, uma chamada DeleteObject no S3), você identifica o campo arn da role assumida temporariamente.
  • O CloudTrail registra a correlação exata com o evento de federação do STS, permitindo inspecionar o e-mail ou identificador único do usuário externo (por exemplo, b@example.com).
  • Isso assegura total não-repúdio, rastreabilidade forense e conformidade regulatória sem necessidade de cadastrar previamente cada pessoa como usuário individual no AWS IAM.

4. Authenticating with Amazon Cognito

O Amazon Cognito resolve completamente a dor de cabeça e os riscos de criar sistemas próprios de login, cadastro, redefinição de senhas, validação de e-mails/SMS e armazenamento seguro de dados confidenciais dos usuários. Ele é dividido em dois componentes principais (e os exames da AWS exigem que você domine exatamente a distinção entre eles):

  1. User Pools (Diretórios de Usuários): Focado na Autenticação ("Quem é o usuário?").
  2. Identity Pools (Identidades Federadas): Focado na Autorização ("O que o usuário pode acessar na AWS?").

1. User Pools (Diretórios de Usuários)

O foco central do Cognito User Pool (CUP) é a Autenticação:

  • O que é: É o seu banco de dados de usuários totalmente gerenciado na nuvem. Ele fornece os serviços completos de Cadastro (Sign-up), Login (Sign-in), redefinição de senha self-service e encerramento de sessão.
  • Recursos Prontos para Uso: Oferece uma interface web de login responsiva e customizável (Hosted UI) com o logotipo e identidade visual da sua empresa, verificação automática de contas por e-mail ou SMS (códigos de 6 dígitos), bloqueio preditivo de credenciais comprometidas e suporte a MFA (Multi-Factor Authentication) via SMS ou aplicativos autenticadores baseados em tempo (TOTP, como Google Authenticator).
  • Integração Social e Corporativa: Permite que os usuários se cadastrem ou façam login utilizando contas do Google, Apple, Facebook ou Amazon, além de provedores corporativos SAML 2.0 e OIDC. O Cognito extrai os dados desses provedores e unifica todos eles dentro do seu diretório padrão de usuários.

A Moeda de Troca: Os 3 Tokens JWT (JSON Web Tokens)

Após o usuário concluir a autenticação com sucesso, o Cognito User Pool devolve para a aplicação cliente um conjunto com três tokens JWT essenciais:

Decisivo para Certificações: Conheça a função exata de cada um dos três tokens emitidos pelo Cognito User Pool:

  • 1. ID Token: Contém as afirmações (claims) sobre a identidade real do usuário (nome, endereço de e-mail, telefone, atributos customizados como custom:cargo e timestamp de autenticação). Utilizado pela aplicação frontend para renderizar o perfil do usuário logado.
  • 2. Access Token: Contém as informações de autorização e escopos de acesso (scopes e grupos de usuários do Cognito, como cognito:groups: ["Admins", "Gerentes"]). É o token enviado nos cabeçalhos HTTP para autorizar requisições contra as suas próprias APIs no Amazon API Gateway.
  • 3. Refresh Token: Token de segurança de longa duração (permanece protegido e criptografado no dispositivo do usuário). É utilizado pelo SDK do Cognito para renovar silenciosamente o ID Token e o Access Token expirados sem forçar o usuário a digitar suas credenciais novamente.

2. Identity Pools (Identidades Federadas)

O foco central do Cognito Identity Pool é a Autorização de Serviços da AWS ("O que esse usuário pode acessar dentro da infraestrutura da AWS?"):

  • O que é: É a máquina orquestradora (o Identity Broker) que recebe provas de identidade validadas de provedores externos e as troca por Credenciais Temporárias da AWS (emitidas via AWS STS).
  • Como Funciona o Fluxo:
    1. O usuário faz login no aplicativo através de um provedor de identidade (Google, Apple, Facebook, SAML corporativo ou o próprio Cognito User Pool).
    2. O aplicativo cliente recebe o token de comprovação e o envia para o Amazon Cognito Identity Pool.
    3. O Identity Pool valida o token, faz uma chamada de bastidores para o AWS STS e solicita: "Assuma a IAM Role configurada e conceda a este usuário permissões temporárias para acessar a pasta dele no bucket S3".
    4. O STS devolve as chaves temporárias (AccessKeyId, SecretAccessKey e SessionToken).
  • Suporte a Usuários Convidados (Unauthenticated/Guest Access): O Identity Pool permite atribuir uma IAM Role restrita para usuários anônimos que ainda não se cadastraram ou não fizeram login, viabilizando recursos como navegação em catálogo público ou upload de formulários de contato antes do cadastro.
Visão Geral dos Identity Pools: federando credenciais de provedores sociais, corporativos e do próprio User Pool para obter permissões temporárias via AWS STS Role

O Grande Benefício Arquitetural: Com o Identity Pool, o seu aplicativo móvel ou web no dispositivo do cliente pode acessar o Amazon S3, o Amazon DynamoDB ou invocar funções AWS Lambda de forma direta e extremamente segura, sem necessidade de servidores intermediários para repassar tráfego e sem chaves fixas embutidas!

Os Padrões Clássicos de Arquitetura com Amazon Cognito

Dominar a aplicação prática desses dois componentes resolve a grande maioria das decisões de arquitetura e questões de prova:

Fluxo 1: Protegendo sua Própria API (Cognito User Pool + API Gateway)

Cenário: Você possui uma API REST no API Gateway e precisa garantir que apenas funcionários autenticados da cafeteria possam requisitá-la.

  1. O funcionário faz login através do Cognito User Pool (tela de login da cafeteria) informando usuário e senha (ou via Google).
  2. O User Pool valida as credenciais e devolve os tokens JWT (ID Token e Access Token) para o aplicativo.
  3. O aplicativo envia uma requisição HTTP para o Amazon API Gateway anexando o token no cabeçalho: Authorization: Bearer <Token>.
  4. O API Gateway utiliza um Cognito Authorizer integrado para validar a assinatura criptográfica e a expiração do token na borda.
  5. Se o token for válido e não expirado, a requisição é liberada para a função Lambda ou backend; caso contrário, a requisição é barrada imediatamente com erro 401 Unauthorized sem consumir nenhum processamento do seu backend.

Fluxo 2: Dando Acesso Direto aos Recursos da AWS (Cognito + Identity Pool)

Cenário: Você precisa que o aplicativo móvel dos funcionários faça upload direto de comprovantes fiscais ou fotos para um bucket do Amazon S3, sem trafegar gigabytes de dados através dos seus servidores de backend.

  1. O funcionário faz login no User Pool (ou Google/Facebook) e recebe o ID Token.
  2. O aplicativo envia esse ID Token para o Cognito Identity Pool.
  3. O Identity Pool troca o token por Credenciais Temporárias da AWS junto ao AWS STS (baseadas na IAM Role configurada).
  4. O aplicativo cliente, utilizando o AWS SDK com essas credenciais temporárias, assina digitalmente a requisição (SigV4) e envia o arquivo diretamente para o bucket do Amazon S3.

Dica de Segurança para Armazenamento Multi-inquilino (S3): Para garantir que o Funcionário A não consiga ler ou apagar os arquivos do Funcionário B no S3, a política da IAM Role utiliza a variável de substituição de política ${cognito-identity.amazonaws.com:sub} no ARN do S3: arn:aws:s3:::bucket-cafeteria/funcionarios/${cognito-identity.amazonaws.com:sub}/*. Dessa forma, cada usuário só consegue manipular estritamente os arquivos da sua própria pasta individual!

Lab 12.1: Implementing Application Authentication Using Amazon Cognito

Visão Geral e Objetivos do Laboratório

Neste laboratório prático, você trabalhará como Sofía para integrar o Amazon Cognito ao site da cafeteria. Frank quer fazer login e solicitar um relatório de estoque de grãos de café diretamente do site da cafeteria. O Amazon Cognito fornece um serviço de autenticação completo que Sofía utilizará para aprimorar o site, aproveitando a máquina de estados criada no laboratório anterior usando o AWS Step Functions.

Depois de concluir este laboratório, você será capaz de:

  • Criar um Grupo de Usuários (User Pool) do Amazon Cognito.
  • Criar e gerenciar um usuário dentro do grupo de usuários do Amazon Cognito.
  • Configurar um Cliente de Aplicativo (App Client) para usar o Amazon Cognito como serviço de autenticação e emitir tokens JWT.
  • Integrar o cliente de aplicativo do Amazon Cognito em uma aplicação web hospedada no Amazon S3 e distribuída pelo Amazon CloudFront.
  • Atualizar os endpoints da API REST criados no Amazon API Gateway para exigir autenticação via Amazon Cognito.
  • Configurar e testar um Autorizador do API Gateway (Cognito Authorizer) para validar tokens na borda antes de invocar o backend.

Duração e Restrições de Serviço AWS

  • Duração estimada: Aproximadamente 90 minutos para ser concluído.
  • Restrições de serviço: Neste ambiente de laboratório, o acesso aos serviços da AWS é limitado estritamente ao necessário para concluir as instruções (Amazon Cognito, API Gateway, CloudFront, S3, Step Functions, Lambda, SNS e AWS WAF).

Cenário da Cafeteria

Frank deseja fazer login no site da cafeteria e solicitar que um relatório de estoque atualizado seja enviado para o seu endereço de e-mail (para visualização no smartphone). Ele quer consultar rapidamente os dados mais recentes do estoque de grãos de café. Neste laboratório, você desempenhará o papel de Sofía para implementar essa solicitação técnica com segurança de ponta a ponta.

No laboratório anterior (Lab 11.1), Sofía criou uma máquina de estados do Step Functions que, uma vez invocada, gera o relatório consolidado. No entanto, atualmente, a máquina de estados só pode ser invocada através do recurso de teste no console do Step Functions ou executando um comando curl manual contra o endpoint REST create_report.

Neste laboratório, Sofía integrará o Amazon Cognito ao site:

  1. Frank fará login no site para confirmar sua identidade antes de solicitar um relatório.
  2. O site conectará o endpoint da API REST ao portal da cafeteria, permitindo que Frank solicite o relatório diretamente pela interface gráfica.
  3. A solicitação da API incluirá o Token de ID/Access recuperado como parte da autenticação no Cognito.
  4. O Amazon API Gateway validará o token através de um autorizador dedicado.
  5. Uma vez autorizada, a máquina de estados do Step Functions será acionada, coordenando as funções Lambda para gerar o relatório no Aurora Serverless e enviar o link por e-mail via Amazon SNS.
Arquitetura Inicial: O site da cafeteria acessado via CloudFront possui o botão LOGIN desabilitado ("No API to call") e o endpoint do API Gateway não possui autenticação vinculada ao site
Arquitetura Final: Frank faz login no site via CloudFront usando o Amazon Cognito, obtém o token de autenticação, dispara a solicitação para o endpoint do API Gateway (protegido por autorizador do Cognito) e recebe o relatório orquestrado pelo Step Functions via SNS/S3

Tarefa 2: Configuração de um Grupo de Usuários e um Cliente de Aplicativo do Amazon Cognito

Nesta tarefa, você configurará o diretório de usuários da cafeteria no Amazon Cognito e criará um cliente de aplicação para interagir com a web.

1. Criação do User Pool:

  • No console do Amazon Cognito, clique em Criar grupo de usuários (Create user pool).
  • Em Tipo de aplicação, verifique se está selecionado Traditional web application.
  • Em Name your application (Nomeie a aplicação), digite: the_cafe_app_client.
  • Em Configure options (Configurar opções), selecione Nome de usuário.
  • Em Atributos obrigatórios para a inscrição, selecione E-mail.
  • Em Adicionar URL de retorno – opcional (Callback URL), informe:
    https://<cloudfront-domain>/callback.html
    (Substitua <cloudfront-domain> pelo domínio real da sua distribuição do CloudFront).
  • Clique no botão Criar diretório de usuário.
  • Na tela seguinte, clique em Visualizar página de login para inspecionar a interface pré-gerada e feche a aba.

2. Renomeação do Grupo e Cópia do ID:

  • Na lista de grupos de usuários, abra o pool recém-criado.
  • Clique em Renomear, altere o nome do pool para the_cafe e salve as alterações.
  • Copie e salve o ID do grupo de usuários (ex: us-east-1_xxxxxxxxx) para consultas posteriores.

3. Configuração da Página de Login e OAuth 2.0 no Cliente:

  • No painel inferior Recomendações, clique no cliente the_cafe_app_client.
  • Acesse a aba Páginas de login e, em Configuração gerenciada de páginas de login, clique em Editar.
  • Em URLs de saída permitidos – opcional (Sign-out URL), adicione:
    https://<cloudfront-domain>/sign_out.html
  • Em Tipos de concessão do OAuth 2.0:
    • Desmarque a opção Concessão de código de autorização (Authorization code grant).
    • Selecione a opção Concessão implícita (Implicit grant).
  • Em Escopos de conexão do OpenID:
    • Marque E-mail e OpenID.
    • Desmarque Telefone.
  • Clique em Salvar alterações.

4. Ajuste dos Fluxos de Autenticação do App Client:

  • Na página do cliente the_cafe_app_client, clique em Editar.
  • Em Fluxos de autenticação:
    • Selecione ALLOW_USER_PASSWORD_AUTH.
    • Desmarque ALLOW_USER_SRP_AUTH.
  • Clique em Salvar alterações.

Tarefa 3: Configuração do Cliente do Aplicativo (Servidor de Recursos)

Nesta etapa, você criará um Servidor de Recursos (Resource Server) no Cognito associado ao endpoint da API REST, permitindo autorizar escopos OAuth 2.0 contra o API Gateway.

1. Criação do Servidor de Recursos:

  • No grupo de usuários the_cafe, navegue até a seção Domínio no menu lateral esquerdo.
  • Na área Servidores de recursos, clique em Criar servidor de recursos e preencha:
    • Nome do servidor de recursos: cafe_resource_server.
    • Identificador do servidor de recursos: Cole o URL de invocação do método POST do endpoint /create_report da API.

Como Obter o URL de Invocação do API Gateway:

  1. No console do API Gateway, abra a API ProductsApi.
  2. No menu lateral, selecione Estágios (Stages) e expanda a árvore do estágio prod.
  3. Selecione o método POST em /create_report.
  4. Copie o URL de invocação exibido (ex: https://<api-id>.execute-api.us-east-1.amazonaws.com/prod/create_report).
  5. Volte ao Cognito e cole essa URL exatamente no campo Identificador.
  6. Clique em Criar servidor de recursos.
Configuração do Servidor de Recursos no Amazon Cognito: nome cafe_resource_server e identificador atrelado à URL do endpoint /create_report

2. Captura da URL da Interface de Usuário Hospedada (Hosted UI):

  • Volte à visão geral do grupo de usuários e abra o cliente the_cafe_app_client.
  • Clique em Visualizar página de login. Uma nova aba abrirá com a tela de login gerenciada pela AWS.
  • Copie a URL completa da barra de endereços do navegador e guarde-a no bloco de notas. A URL possui formato semelhante a:

Tarefa 4: Integração da Interface de Usuário Hospedada ao Site

Agora você integrará a URL da Hosted UI do Cognito no arquivo de configuração do site estático da cafeteria e enviará a versão atualizada para o Amazon S3.

1. Edição do Arquivo config.js no VS Code IDE:

Tarefa 5: Observação e Teste do Endpoint da API REST

Nesta etapa, você entenderá como o site manipula os tokens e testará o envio de relatórios antes de ativar a autorização estrita.

Mecânica do Frontend com Tokens JWT: Quando o usuário realiza o login na tela do Cognito, ele é redirecionado para a página /callback.html do site. O código JavaScript dessa página captura o token contido no fragmento de URL, armazena-o na sessão do navegador (SessionStorage) e o utiliza em requisições AJAX subsequentes anexado ao cabeçalho HTTP Authorization.

1. Verificação do CORS no API Gateway:

  • No console do API Gateway, em ProductsApi > Recursos > /create_report, selecione o método OPTIONS.
  • Abra Resposta de integração (Integration Response) e expanda a resposta com código 200.
  • Em Mapeamentos de cabeçalho, note que Access-Control-Allow-Origin já aponta para a sua distribuição do CloudFront ('https://<cloudfront-domain>'), permitindo chamadas do frontend sem bloqueios de origem cruzada.

2. Teste Direto pelo Console do API Gateway:

  • Na árvore de recursos, selecione POST em /create_report.
  • No painel inferior, clique na aba TESTE e, em seguida, clique no botão Teste.
  • Verifique que o corpo da resposta exibe o JSON com executionArn e os logs terminam com Method completed with status: 200.
  • Abra sua caixa de e-mail: em cerca de 1 a 2 minutos você receberá o e-mail do Amazon SNS contendo a URL pré-assinada do relatório gerado pelo Step Functions e Lambda.

Dica de Troubleshooting (Caso não receba o e-mail ou o link expire):

  • Se não receber o e-mail: No console do AWS WAF & Shield, em IP sets, abra office_regional e certifique-se de que o seu IPv4 público está listado com máscara /32.
  • Se o link do relatório der erro de expiração: No console do Lambda, edite o código da função GeneratePresignedURL, aumente o valor de expires_in_seconds_int de 60 para 240 e clique em Deploy.

A Brecha de Segurança Identificada por Sofía: O endpoint da API atualmente aceita chamadas de qualquer máquina com o IP do escritório da cafeteria. Isso significa que qualquer visitante conectado ao Wi-Fi da loja conseguiria disparar comandos curl e gerar relatórios sem qualquer login. Sofía corrigirá isso configurando a verificação de identidade obrigatória no API Gateway com o Amazon Cognito!

3. Tentativa de Bypass da API via cURL:

Execute o comando curl a partir de dois ambientes distintos para avaliar o comportamento de segurança:

Resposta esperada:

Por que falhou? Porque o VS Code IDE roda em uma instância EC2 cujo IP externo não faz parte do IP set autorizado no AWS WAF.

Resposta obtida:

Alerta de Segurança Crítico: A chamada funcionou e gerou um relatório por e-mail sem exigir nenhuma senha ou token, apenas porque o computador local compartilha o IP permitido no WAF! Para blindar o endpoint, Sofía implementará a autorização do Cognito diretamente no API Gateway.

Tarefa 7: Configuração de um Autorizador do API Gateway (Cognito Authorizer)

Nesta tarefa crucial, você configurará o API Gateway para validar o token JWT emitido pelo Cognito antes de permitir qualquer invocação ao endpoint create_report.

1. Criação do Autorizador na ProductsApi:

  • No console do API Gateway, selecione a API ProductsApi.
  • No menu de navegação à esquerda, clique em Autorizadores (Authorizers).
  • Clique em Criar autorizador e preencha:
    • Nome: cafe_lockdown.
    • Tipo: Cognito.
    • Grupo de usuários do Cognito: Selecione a região us-east-1 e escolha the_cafe.
    • Origem do token (Token Source): Digite Authorization.
    • Validação do token: Deixe em branco (o Cognito cuidará da verificação criptográfica da assinatura do JWT).
  • Clique em Criar autorizador.

2. Vinculação do Autorizador ao Método POST /create_report:

  • No menu lateral, selecione Recursos e clique no método POST em /create_report.
  • Clique em Solicitação de método (Method Request).
  • Em Configurações, localize o campo Autorização (que atualmente exibe NENHUM).
  • Clique no ícone de lápis para editar, selecione o autorizador cafe_lockdown no menu suspenso e clique no ícone de marca de seleção (check) para salvar.
  • Expanda a seção Cabeçalhos de solicitação HTTP, clique em Adicionar cabeçalho, digite Authorization, salve e marque a caixa Obrigatório (Required).

3. Reimplantação da API REST:

  • Na árvore de Recursos, selecione a raiz / da API.
  • No menu suspenso Ações, clique em Implantar API (Deploy API).
  • Selecione o estágio de implantação: prod e clique em Implantar.

4. Teste de Bloqueio sem Token via cURL:

Retorne ao terminal da sua máquina local e reexecute o comando curl anterior:

curl -X POST https://<api-id>.execute-api.us-east-1.amazonaws.com/prod/create_report

Resposta obtida imediatamente:

{"message": "Unauthorized"}

Sucesso Absoluto: O API Gateway agora rejeita requisições não autenticadas na borda com erro 401 Unauthorized, garantindo que usuários na mesma rede física não consigam disparar relatórios sem um token JWT válido!

5. Análise do Código Frontend (main.js):

No VS Code IDE, ao abrir resources/website/scripts/main.js na função attemptCreateReport (linha 71), é possível verificar como o código injeta o cabeçalho Authorization com o token recuperado do Cognito antes de realizar o disparo da requisição AJAX para o API Gateway:

function attemptCreateReport() {
    let authHeader = sessionStorage.getItem("id_token");
    if (!authHeader) {
        showError("Por favor, faça login antes de gerar o relatório.");
        return;
    }
    
    fetch(window.COFFEE_CONFIG.API_GW_BASE_URL_STR + "/create_report", {
        method: "POST",
        headers: {
            "Content-Type": "application/json",
            "Authorization": "Bearer " + authHeader
        }
    })
    .then(response => response.json())
    .then(data => showSuccess("O relatório está sendo gerado, verifique seu e-mail!"))
    .catch(error => showError("Erro ao solicitar relatório."));
}
