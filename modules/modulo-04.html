4. Securing Access to Cloud Resources

1. Introduction

Este módulo é totalmente focado em como gerenciar quem pode entrar na sua conta AWS e o que essas pessoas ou sistemas podem fazer lá dentro, utilizando o serviço IAM (AWS Identity and Access Management).

Objetivos de Aprendizado:

  • Compreender o Modelo de Responsabilidade Compartilhada (divisão de tarefas de segurança entre você e a AWS).
  • Entender como o IAM ajuda a criar uma barreira de proteção para os seus recursos.
  • Diferenciar os métodos de autenticação de usuários.
  • Aprender a organizar e autorizar acessos usando os três pilares do IAM: Usuários (Users), Grupos (Groups) e Funções/Papéis (Roles).

O Caso da Cafeteria (Cenário Prático):

  • Os donos da cafeteria (Frank e Martha) adoraram o site de prova de conceito! Com o sucesso, o projeto vai crescer e novos membros da equipe vão entrar para ajudar a Sofía a desenvolver a aplicação web completa.
  • O grande requisito de negócio agora é a governança: antes de continuar escrevendo código, Sofía precisa definir regras rígidas de segurança. Ela vai usar o IAM para criar perfis específicos (por exemplo, um perfil com acesso de "desenvolvedor" e outro de "administrador de banco de dados"), garantindo que cada pessoa ou sistema tenha acesso única e exclusivamente aos recursos que precisa para trabalhar, sem risco de apagarem algo importante por acidente.

2. Shared responsibility model

A segurança e a conformidade na AWS funcionam como uma parceria. A regra de ouro que você precisa tatuar na mente para a prova é:

  • A AWS é responsável pela segurança DA nuvem (Security OF the cloud).
  • O Cliente (Você) é responsável pela segurança NA nuvem (Security IN the cloud).

Isso foi desenhado para tirar o peso das suas costas de ter que gerenciar infraestrutura física, mas ainda te dar flexibilidade total sobre como construir seus sistemas.

Responsabilidades da AWS (Segurança DA Nuvem)

A Amazon cuida de tudo o que você não consegue tocar ou configurar diretamente. Isso inclui:

  • Infraestrutura Global: A segurança física dos datacenters, Regiões, Zonas de Disponibilidade e Edge Locations.
  • Fundação de Hardware e Software: Servidores físicos, armazenamento físico, rede física e o software base (como o Hypervisor, que é a camada que virtualiza as máquinas).

Responsabilidades do Cliente (Segurança NA Nuvem)

Você assume a responsabilidade por tudo o que coloca dentro da AWS ou configura nos serviços. Isso inclui:

  • Seus Dados: Você é sempre responsável por proteger e criptografar os dados dos seus clientes (seja em trânsito ou em repouso).
  • Gerenciamento de Acesso (IAM): Controlar quem tem permissão para acessar o quê.
  • Sistema Operacional (Guest OS): Se você sobe uma máquina virtual (Amazon EC2), as atualizações, patches de segurança e configurações do Windows ou Linux são problema seu. A AWS não entra no seu sistema operacional.
  • Rede e Firewall: Configurar corretamente os Security Groups (firewalls virtuais) para liberar apenas as portas necessárias.
  • Aplicações: A segurança do código que você desenvolve e dos softwares de terceiros que você instala.

3. Introducing AWS Identity and Access Management (IAM)

Antes de criar qualquer acesso, você precisa entender a diferença entre dois conceitos que o IAM gerencia muito bem:

  • Autenticação (Authentication): "Quem é você?" É a verificação da identidade de quem está tentando acessar a AWS (chamado de Principal). Isso é provado usando usuário e senha, chaves de acesso ou, para maior segurança, o MFA (Multi-Factor Authentication / Autenticação de Múltiplos Fatores), como um código no Google Authenticator.
  • Autorização (Authorization): "O que você pode fazer?" Depois de provar quem você é, o IAM verifica as regras para saber se você tem permissão para realizar aquela ação (ex: você pode ver os arquivos, mas não pode deletá-los).

Os 4 Pilares do IAM

Para controlar esses acessos, o IAM utiliza quatro componentes principais. Isso é figurinha carimbada em qualquer prova da AWS:

  • Usuário IAM (IAM User): Representa uma pessoa ou uma aplicação (sistema). Possui credenciais permanentes (de longo prazo), como uma senha para o console ou chaves de acesso para rodar códigos.
  • Grupo IAM (IAM Group): É uma coleção de usuários. Serve para facilitar a sua vida: em vez de dar permissão um por um, você dá permissão ao grupo (ex: "Desenvolvedores") e coloca os usuários lá dentro.
  • Função IAM (IAM Role): É parecido com o usuário, mas com uma diferença crucial: não possui credenciais permanentes. Em vez disso, fornece credenciais de segurança temporárias. Pessoas ou serviços (como uma máquina EC2 precisando acessar o S3) podem "assumir" essa função por um tempo limitado.
  • Política IAM (IAM Policy): É o documento (escrito em JSON) que define as permissões exatas (o que é permitido ou negado). Você anexa essas políticas aos Usuários, Grupos ou Funções.

4. Authenticating with IAM

A forma como você se autentica muda dependendo de onde você está acessando a AWS:

  • Console da AWS (Navegador): Você faz login utilizando um Usuário e Senha.
  • Acesso Programático (CLI, SDKs e APIs): Sistemas e códigos não preenchem telas de login. Para eles, você gera um par de chaves composto pelo Access Key ID (pense nele como um nome de usuário) e pela Secret Access Key (pense nela como uma senha super complexa).
Atenção (MFA): Para acessos humanos no Console, é uma forte recomendação de segurança sempre ativar o MFA (Multi-Factor Authentication). Ele exige algo que você sabe (a senha) e algo que você tem (um código no celular ou token físico).

O Poder das Funções IAM (IAM Roles)

As Roles são as grandes estrelas da segurança para aplicações na nuvem. Em vez de gerar senhas fixas que podem vazar, as Roles fornecem credenciais de segurança temporárias. Quando um usuário ou sistema assume uma Role, ele recebe permissões com prazo de validade.

Casos de uso clássicos para provas e dia a dia:

  • Aplicações no EC2: O seu servidor EC2 assume a Role para poder gravar arquivos no S3, sem que você precise salvar senhas dentro do servidor.
  • Acesso entre contas (Cross-account access): Permitir que um desenvolvedor de uma conta AWS parceira acesse a sua conta, sem precisar criar um novo usuário para ele.
  • Aplicativos Mobile/Federação: O usuário faz login no celular (ex: via Google ou Facebook), a AWS valida isso externamente (Identity Federation) e entrega uma Role temporária para o app acessar os dados.

Gerenciamento de Credenciais (O Arquivo .aws/credentials)

Regra de ouro absoluta para desenvolvedores: NUNCA escreva suas chaves de acesso diretamente (hardcoded) no seu código-fonte. Se você enviar isso para um repositório como o GitHub, hackers podem roubar sua conta em minutos.

A maneira correta de trabalhar localmente é utilizando o arquivo de credenciais.

  • Onde fica? Fica salvo no seu próprio computador (~/.aws/credentials no Linux/Mac ou C:\Users\SEU-USUARIO\.aws\credentials no Windows).
  • Perfis (Profiles): Dentro desse arquivo, você pode configurar vários perfis diferentes (ex: [default] para a conta de testes e [prod] para a conta de produção). No seu código, você apenas diz para o SDK usar o profile_name='prod', e ele puxa as chaves de forma segura, sem expô-las no código.

5. Authorizing with IAM

Toda a lógica de autorização da AWS é baseada em um conceito fundamental de segurança da informação:

O Princípio do Menor Privilégio (Principle of least privilege)

Nunca dê acesso total para depois tentar restringir. A regra é começar com zero permissões e conceder única e exclusivamente o acesso estritamente necessário para que o usuário ou sistema execute sua função.

O Cenário Prático da Cafeteria (Como o IAM funciona na vida real)

O material ilustra a aplicação dessas regras através das ações da Sofía. Aqui estão as lições arquiteturais tiradas desse cenário:

  • O Usuário Raiz (Root User): É o dono da conta (o e-mail usado no cadastro). Ele tem poder absoluto e irrestrito. Melhor prática: A primeira coisa que Sofía fez foi criar um usuário IAM administrador para ela mesma, logar com ele e trancar as credenciais do usuário Root. O Root não deve ser usado no dia a dia.
  • Herança de Grupos: Sofía criou grupos (Admins, DBAdmins, Developers) e colocou as permissões lá. Quando novos funcionários (como os desenvolvedores ou administradores de banco) entram na empresa, basta adicioná-los aos respectivos grupos e eles herdam todas as políticas automaticamente.
  • A Regra de Ouro do IAM (Deny vs. Allow): Sofía colocou o consultor Mateo no grupo Admins (que tem permissão para tudo), mas anexou uma política diretamente ao usuário dele dizendo "Não pode gerenciar grupos do IAM" (Explicit Deny).
Dica de Prova: Na AWS, uma negação explícita (Explicit Deny) SEMPRE anula uma permissão (Allow). Mesmo que o grupo permita, se o usuário tiver um Deny, ele será bloqueado.
  • Uso Estratégico de Roles (Funções): Dois membros do banco de dados precisavam acessar um serviço diferente (Amazon RDS) apenas por um tempo, para um projeto específico. Em vez de dar essa permissão para o grupo DBAdmins inteiro (o que violaria o menor privilégio), Sofía criou uma Role temporária com acesso ao RDS. Os dois usuários "assumiram" essa Role, fizeram o trabalho e depois a Role foi removida. O mesmo foi feito para um desenvolvedor terceirizado temporário, evitando misturá-lo com o grupo fixo da empresa.
