1. Introduction

Enquanto no módulo anterior exploramos como o AWS Lambda abstrai integralmente a infraestrutura para executar funções rápidas sob demanda (Serverless FaaS), neste módulo veremos como os Contêineres resolvem um desafio corporativo crucial: empacotar uma aplicação completa junto com todas as suas bibliotecas, configurações, binários e runtimes, garantindo que ela execute de forma idêntica e sem atritos em qualquer ambiente computacional.

  • Orquestração de Contêineres na AWS: Reconhecer os desafios de gerenciar centenas de contêineres em produção e mapear as soluções nativas da AWS: Amazon Elastic Container Service (Amazon ECS), Amazon Elastic Kubernetes Service (Amazon EKS), a computação serverless do AWS Fargate e o registro privado Amazon Elastic Container Registry (Amazon ECR).
  • AWS Elastic Beanstalk: Compreender como utilizar essa plataforma como serviço (PaaS) totalmente gerenciada para simplificar a implantação, balanceamento de carga e escalabilidade automática de aplicações web conteinerizadas.

2. Introducing containers

Para compreender o conceito de contêineres na computação moderna, a AWS utiliza a célebre analogia histórica dos contêineres de transporte marítimo. Essa revolução logística transformou o comércio global no século XX exatamente da mesma forma como os contêineres de software transformaram a indústria de tecnologia da informação.

A Analogia Definitiva: O Navio de Carga e o Contêiner Intermodal

Antes da década de 1950, o transporte de mercadorias entre continentes era um processo caótico, lento e ineficiente. A carga consistia em uma mistura heterogênea de caixas de madeira, sacas de grãos, engradados de vidro e barris de ferro de todos os formatos e tamanhos imagináveis. Cada navio exigia estivadores especializados para carregar e arrumar manualmente os itens nos porões como se fosse um quebra-cabeça tridimensional. O carregamento demorava dias ou semanas, mercadorias eram roubadas ou quebravam, e transferir a carga do navio para trens ou caminhões exigia desempacotar e recarregar tudo do zero.

Tudo mudou quando foi inventado o contêiner de aço padronizado (Intermodal Container). Uma caixa metálica retangular simples com dimensões universais (20 ou 40 pés) e travas padronizadas em todos os cantos. De repente, o navio, o guindaste portuário, o vagão de trem e a carroceria do caminhão não precisavam mais saber o que havia dentro da caixa. Pouco importava se o contêiner carregava sacas de café, televisores, roupas ou peças mecânicas pesadas; bastava acoplar o guindaste nas travas universais e movimentar o contêiner de aço.

O Paralelo na Computação: Durante décadas, implantar software foi igualmente caótico. Desenvolvedores entregavam código que dependia de versões específicas de compiladores, variáveis de ambiente, bibliotecas do sistema e patches do sistema operacional. O que rodava no laptop do desenvolvedor quebrava no servidor de testes e falhava catastroficamente em produção. O contêiner de software é a caixa de aço padronizada da computação: você coloca seu código e todas as suas dependências lá dentro, e os servidores na nuvem apenas transportam e executam a caixa sem se preocupar com os detalhes internos!

O que é um Contêiner de Software?

  • A "Caixa" Padronizada: Uma unidade padrão de software que empacota o código-fonte da aplicação junto com seu runtime (ex: Node.js, Python, Java), todas as dependências externas, bibliotecas binárias compartilhadas e arquivos de configuração essenciais.
  • Portabilidade Extrema: Uma vez construído, o contêiner garante comportamento 100% reproduzível e idêntico em qualquer ambiente: seja no laptop de desenvolvimento (macOS ou Windows), em servidores de homologação ou em clusters de instâncias EC2 na nuvem da AWS. O clássico dilema "Na minha máquina funciona, por que não funciona em produção?" deixa de existir.
  • Virtualização a Nível de Sistema Operacional: Diferente da virtualização tradicional de hardware (baseada em hypervisors), múltiplos contêineres em execução operam de forma isolada entre si, mas compartilham o mesmo núcleo (Kernel) do Sistema Operacional da máquina hospedeira.

A Evolução da Infraestrutura: Por que os Contêineres Venceram?

A história da computação corporativa evoluiu através de três grandes paradigmas de infraestrutura:

Característica 1. Servidores Físicos (Bare-metal) 2. Máquinas Virtuais (VMs) 3. Contêineres (A Solução Moderna)
Nível de Virtualização Nenhuma virtualização. SO instalado diretamente no hardware físico. Virtualização de Hardware via Hypervisor (Type 1 ou Type 2). Virtualização de Sistema Operacional no espaço de usuário (User Space).
Isolamento Nulo entre aplicações no mesmo servidor. Forte isolamento em nível de hardware virtualizado. Isolamento lógico robusto via Linux Namespaces e cgroups.
Tamanho do Artefato Código + SO instalado no disco inteiro (dezenas de GBs). Imagens pesadas de SO completo (geralmente de 2 GB a 20 GB). Imagens compactas e enxutas (dezenas a poucas centenas de MB).
Tempo de Inicialização Minutos (boot físico de BIOS, POST e SO). Minutos (boot completo do sistema operacional convidado). Frações de segundo (milissegundos; apenas um processo no kernel).
Eficiência de Recursos Baixa (recursos ociosos dedicados a uma única máquina). Média (overhead de memória e CPU para rodar múltiplos kernels). Altíssima densidade (centenas de contêineres sobre um único kernel).
  1. Servidores Físicos (Bare-Metal):

    No início, o sistema operacional era instalado diretamente na placa-mãe de servidores dedicados. Várias aplicações eram instaladas lado a lado. Isso gerava o famoso "Inferno de Dependências" (Dependency Hell): se a Aplicação A exigia a versão 1.0 de uma biblioteca e a Aplicação B exigia a versão 2.0 da mesma biblioteca, ocorria um conflito insolúvel. Além disso, os servidores precisavam ser superdimensionados para picos de tráfego, resultando em gigantesco desperdício de energia e capacidade durante períodos ociosos.

  2. Máquinas Virtuais (VMs - Era da Virtualização de Hardware):

    Para resolver o conflito de dependências, surgiu a tecnologia de Máquinas Virtuais (gerenciadas por um Hypervisor, como o KVM utilizado pelas instâncias Amazon EC2). Cada aplicação passou a rodar em seu próprio "servidor virtual" independente com seu próprio hardware emulado. Porém, as VMs são computacionalmente pesadas: cada VM obriga a instalação de um Sistema Operacional completo (Windows ou Linux), consumindo gigabytes de memória RAM e disco rígido apenas para manter o kernel e os daemons do SO rodando. Adicionalmente, aplicar patches de segurança e atualizar SOs convidados em dezenas de VMs multiplica o trabalho operacional.

  3. Contêineres (A Era Moderna de Virtualização de SO):

    Em vez de emular hardware e instalar dezenas de SOs convidados, os contêineres compartilham o mesmo kernel do SO hospedeiro. Cada contêiner recebe apenas seus binários e bibliotecas de aplicação empacotados. Graças ao compartilhamento do kernel, um contêiner inicializa quase instantaneamente (iniciando apenas o processo da aplicação, sem passar por rotinas de boot do SO) e consome apenas a memória estritamente necessária para rodar o código de negócio, permitindo densidade e escalabilidade incomparáveis!

3. Introducing Docker containers

Embora as tecnologias de isolamento do Linux (como chroot, cgroups e namespaces) já existissem há anos, os contêineres só se tornaram o padrão absoluto da indústria de tecnologia a partir de 2013, graças ao surgimento do Docker. O Docker criou uma plataforma simples, intuitiva e padronizada que transformou a criação, empacotamento, distribuição e execução de contêineres em uma experiência acessível a qualquer desenvolvedor.

Por que o Docker se Tornou o Padrão da Indústria?

  • A "Caixa" Totalmente Imutável: A aplicação, suas dependências, o runtime e os arquivos de configuração são compilados em um único artefato binário imutável chamado Imagem (Container Image).
  • Portabilidade Universal: Uma vez construída a imagem Docker, ela pode ser executada sem qualquer modificação em desktops de desenvolvimento, instâncias Amazon EC2, clusters do Amazon ECS/EKS ou qualquer provedor de computação que suporte o padrão OCI (Open Container Initiative).
  • Isolamento Versátil e Convivência Pacífica: É perfeitamente viável executar simultaneamente no mesmo servidor uma aplicação legada rodando Python 2.7 e uma nova aplicação rodando Python 3.12, cada uma em seu próprio contêiner isolado, sem qualquer interferência de dependências de sistema ou conflitos de portas.

O Dicionário Essencial do Docker: Os 4 Pilares Centrais

Para operar com contêineres com confiança em ambientes de produção e exames da AWS, você precisa dominar com precisão os quatro conceitos basilares:

  1. Dockerfile (A "Receita de Bolo"):

    É um arquivo de texto simples (obrigatoriamente nomeado como Dockerfile, sem qualquer extensão de arquivo) contendo a sequência exata de instruções declarativas para construir a imagem do seu aplicativo. Cada comando no Dockerfile define uma ação (baixar uma imagem base, instalar pacotes, expor portas de rede, copiar arquivos e definir comandos de inicialização).

  2. Container Image (A Imagem - O "Molde" Imutável):

    É o resultado compilado da execução do Dockerfile (através do comando docker build). Uma imagem Docker é um modelo estritamente somente-leitura (read-only) e imutável. Uma vez gerada a imagem, seu conteúdo jamais é alterado; se você modificar uma única linha de código, uma nova imagem com uma nova tag ou hash é gerada.

  3. Container Registry (O "Repositório / GitHub" das Imagens):

    É o serviço de catálogo e armazenamento onde as imagens Docker são publicadas para distribuição e versionamento. Permite baixar imagens públicas oficiais da comunidade (como imagens de Linux Alpine, Nginx, Python ou MySQL disponíveis no Docker Hub) ou armazenar imagens corporativas proprietárias em repositórios privados altamente seguros, como o Amazon Elastic Container Registry (Amazon ECR).

  4. Container (A Instância Viva em Execução):

    É a imagem "ganhando vida". Quando você executa o comando docker run, o Docker Engine instancia o molde somente-leitura da imagem e adiciona uma fina camada de leitura e escrita (Read/Write Layer) no topo da pilha. A aplicação executa seus processos e grava dados temporários nessa camada superior.

    Regra de Ouro Arquitetural para Contêineres:
    A camada de leitura/escrita do contêiner é completamente efêmera! Se o contêiner falhar, travar ou for encerrado pelo orquestrador, todos os dados gravados nessa camada de escrita são permanentemente apagados. Por essa razão, contêineres nunca devem armazenar dados persistentes localmente: utilize bancos de dados gerenciados (Amazon DynamoDB, Amazon Aurora / RDS) ou monte sistemas de arquivos compartilhados duráveis (como volumes do Amazon EFS ou Amazon EBS).

A Magia das Camadas (Layers) no Dockerfile

O segredo arquitetural que torna as imagens Docker tão leves, rápidas para compilar e eficientes para baixar pela rede está no modelo de camadas sobrepostas (Layered Union Filesystem). Cada instrução declarada no Dockerfile cria uma camada somente-leitura independente sobreposta à anterior.

Estrutura oficial de camadas de uma imagem Docker: cada linha do Dockerfile cria uma camada somente-leitura empilhada sequencialmente a partir da imagem base.

Analisando detalhadamente o exemplo do slide oficial exibido acima:

  • FROM centos:7 → Camada 1 (Base Layer): Define a imagem base do sistema operacional (CentOS 7). Todas as demais instruções serão executadas sobre essa base.
  • RUN yum -y update && yum -y install httpd → Camada 2: Executa a atualização de pacotes e instala o servidor web Apache HTTPD, gravando os binários instalados como uma nova camada intermediária.
  • EXPOSE Port 80 → Camada 3: Adiciona metadados à imagem informando que o container escuta requisições na porta TCP 80.
  • ADD run-httpd.sh /run-httpd.sh & RUN chmod -v +x /run-httpd.sh → Camada 4: Copia o script de inicialização do Apache para dentro da imagem e atribui permissões de execução.
  • CMD ["/run-httpd.sh"] → Comando de Inicialização: Define o executável padrão que entrará em execução no momento em que o contêiner for instanciado.

A Grande Vantagem Operacional: O Cache de Camadas (Build Cache)

Como cada uma das camadas é imutável e identificada por um hash criptográfico exclusivo, o Docker implementa um poderoso sistema de cache inteligente de compilação:

  • Se um desenvolvedor alterar apenas o conteúdo do script run-httpd.sh (a Camada 4) e executar docker build novamente, o Docker não reexecutará os comandos de download do CentOS nem reinstalará o Apache via yum!
  • Ele detecta que as camadas 1, 2 e 3 permanecem idênticas, recupera essas camadas instantaneamente a partir do cache local e recompila exclusivamente a Camada 4 modificada.
  • Impacto na Prática: Processos de compilação em esteiras de integração contínua (CI/CD) que levariam 10 a 15 minutos em máquinas virtuais tradicionais são concluídos em poucos segundos no Docker. Além disso, no momento de fazer o upload para o Amazon ECR ou download em instâncias EC2, apenas as camadas alteradas são transmitidas pela rede!

1. O Ciclo de Criação: Do Código-Fonte à Imagem

  • docker build (O Cozinheiro que "Assa o Bolo"):

    É o comando responsável por interpretar o arquivo Dockerfile e executar cada uma de suas instruções sequencialmente para produzir a imagem imutável final.

    docker build --tag node_app .
    • O ponto final (.): Define o Build Context (o contexto de compilação). Ele indica ao Docker daemon que todos os arquivos do diretório atual devem ser disponibilizados para comandos como COPY e ADD.
    • A flag --tag (ou -t): Atribui um nome amigável e opcionalmente uma versão à imagem criada (no exemplo: node_app, assumindo automaticamente a tag padrão :latest).
Exemplo oficial de compilação com docker build: envio do contexto de build (9.007 MB), download da imagem base node:11-alpine e atribuição da tag node_app:latest.
  • docker images: Exibe a tabela de imagens locais armazenadas no computador ou instância EC2 hospedeira, indicando o repositório, a tag, o Image ID exclusivo de 64 bits (exibido em forma truncada de 12 caracteres hexadecimais), a data de criação e o tamanho total em disco.
  • docker tag: Permite renomear ou marcar uma imagem existente com uma nova tag. Em fluxos de trabalho com a AWS, esse comando é fundamental para associar a imagem local ao endereço do repositório no Amazon ECR antes de realizar o push: 
    # Marcando a imagem local para o repositório privado no Amazon ECR:
docker tag node_app:latest 123456789012.dkr.ecr.us-east-1.amazonaws.com/cafe-supplier:v1

2. O Ciclo de Execução: Da Imagem Estática ao Contêiner Vivo

  • docker run (Dando Vida ao Molde):

    Pega a imagem estática somente-leitura, cria uma instância isolada com sua camada de escrita no topo e inicializa o processo principal configurado no CMD ou ENTRYPOINT.

    docker run -d --name node_app_1 -p 8000:80 node_app
    • -d (Modo *Detached* / Segundo Plano): Executa o contêiner em background, liberando o terminal imediatamente para que o usuário possa continuar trabalhando. Sem a flag -d, o terminal fica preso aos logs de execução do contêiner.
    • --name node_app_1: Atribui um nome customizado e legível ao contêiner. Se essa opção for omitida, o Docker gerará automaticamente um nome aleatório combinando um adjetivo e o nome de um cientista famoso (ex: nervous_einstein).
    • -p 8000:80 (Mapeamento de Portas / *Port Forwarding*): Conceito vital para exames AWS e redes! O formato é estritamente -p <porta-do-host>:<porta-do-container>. Isso significa que qualquer requisição que chegar na porta 8000 da máquina física (ou instância EC2) será encaminhada pelo daemon do Docker diretamente para a porta 80 dentro do contêiner isolado.
  • docker ps: Lista os contêineres atualmente ativos, mostrando o Container ID, a imagem base, o comando de inicialização, o tempo de execução (*uptime*), os mapeamentos de porta e o nome atribuído. Para visualizar também os contêineres que já foram encerrados ou falharam, utiliza-se a flag docker ps -a.

3. Interação, Diagnóstico e Depuração

  • docker exec (Entrando no Contêiner):

    Permite executar novos comandos dentro de um contêiner que já está rodando. O caso de uso mais importante para desenvolvedores é abrir uma sessão de terminal interativa dentro do ambiente do contêiner para explorar arquivos, testar conexões de rede ou depurar variáveis:

    docker exec -it node_app_1 sh

    A combinação das flags -i (interativo, mantém o STDIN aberto) e -t (aloca um pseudo-TTY) permite navegar diretamente pelo sistema de arquivos Linux interno do contêiner como se você tivesse feito login via SSH!

  • docker logs:

    Exibe todo o histórico de logs emitido pelo contêiner (saídas de console.log(), print() ou logs de erro do servidor web). Utilize a flag -f (follow) para acompanhar o fluxo de logs em tempo real na tela.

    docker logs -f node_app_1
  • docker port: Exibe rapidamente os mapeamentos de rede ativos para um contêiner específico (ex: docker port node_app_1 revelará 80/tcp -> 0.0.0.0:8000).
  • docker inspect: Gera um "raio-X" estruturado em formato JSON detalhando todas as configurações internas de baixo nível do contêiner: endereço IP atribuído na rede bridge virtual, variáveis de ambiente injetadas, volumes e binds montados, políticas de reinicialização e status de saúde do processo.

4. O Ciclo de Encerramento e Limpeza

  • docker stop <container>: Interrompe a execução do contêiner enviando primeiramente o sinal SIGTERM (dando à aplicação um período de tolerância de até 10 segundos para encerrar conexões de banco de dados e salvar arquivos com segurança antes de forçar o encerramento com SIGKILL).
  • docker start <container>: Reinicia um contêiner que estava parado preservando seu estado anterior na camada de escrita efêmera.
  • docker rm <container>: Remove o contêiner finalizado do sistema. Lembre-se: o contêiner precisa estar parado antes de poder ser removido (ou deve-se utilizar a flag forçada -f).
  • docker rmi <image>: Remove a imagem do host local para liberar espaço em disco, desde que nenhum contêiner (mesmo parado) dependa mais dela.

5. Compartilhamento: O Pipeline para a Nuvem

  • docker push: Faz o upload da imagem local compilada para um repositório remoto (Container Registry). Em esteiras corporativas da AWS, após efetuar login via aws ecr get-login-password e taguear a imagem com docker tag, você executa o docker push para disponibilizar a imagem no Amazon ECR. A partir desse momento, serviços de orquestração como AWS Elastic Beanstalk, Amazon ECS ou Amazon EKS conseguem baixar e instanciar contêineres automaticamente na nuvem!

Para o sistema de rastreamento de grãos de café adquirido por Frank e Martha, Sofía utilizará docker build -t cafe-supplier . para gerar a imagem imutável da aplicação web, testará localmente com docker run -p 8080:80, enviará para o Amazon ECR com docker push e utilizará o AWS Elastic Beanstalk para orquestrar o deploy elástico em produção!

Lab 8.1: Migrating a Web Application to Docker Containers

Visão geral e objetivos do laboratório

Neste laboratório prático, você realizará a migração completa de uma aplicação web legada de monitoramento de fornecedores e estoque — instalada diretamente nos sistemas operacionais convidados (Ubuntu Linux) de duas instâncias do Amazon Elastic Compute Cloud (Amazon EC2) — para contêineres padronizados e portáteis do Docker.

Você empacotará tanto a aplicação web desenvolvida em Node.js (Express) quanto o banco de dados relacional MySQL em contêineres autônomos, configurará a comunicação de rede bridge interna entre eles via variáveis de ambiente e, por fim, autenticará o Docker e publicará a imagem corporativa no registro gerenciado Amazon Elastic Container Registry (Amazon ECR).

Depois de concluir este laboratório, você será capaz de:

  • Escrever e estruturar um arquivo Dockerfile otimizado utilizando imagens base enxutas (Alpine Linux).
  • Compilar imagens Docker com o comando docker build atribuindo tags semânticas.
  • Executar e gerenciar contêineres em segundo plano (detached mode) com docker run, configurando mapeamento de portas de rede (-p).
  • Depurar e inspecionar variáveis de ambiente e configurações internas de contêineres com docker exec, docker logs e docker inspect.
  • Criar e exportar dumps lógicos de bancos de dados relacionais com mysqldump e inicializar contêineres MySQL com dados pré-carregados.
  • Configurar a comunicação de rede entre múltiplos contêineres Docker usando IPs virtuais da rede bridge e variáveis de ambiente dinâmicas (APP_DB_HOST).
  • Criar repositórios privados no Amazon Elastic Container Registry (Amazon ECR).

6. Using containers for microservices

A grande força motriz que impulsionou a adoção explosiva de contêineres na nuvem corporativa foi a consolidação da Arquitetura de Microsserviços. Embora seja tecnicamente possível empacotar uma aplicação monolítica gigantesca em um único contêiner ("Fat Container"), essa abordagem neutraliza quase todos os benefícios de agilidade, escalabilidade granular e velocidade de inicialização que a tecnologia de contêineres oferece.

A Batalha Arquitetural: Monólito vs. Microsserviços

Compreender o contraste estrutural e operacional entre monólitos e microsserviços é um dos tópicos mais recorrentes em avaliações e exames de arquitetura da AWS:

Comparação arquitetural oficial: Sistema Monolítico fortemente acoplado com banco centralizado versus Arquitetura de Microsserviços desacoplada e poliglota com bancos de dados isolados.

1. A Arquitetura Monolítica (O "Bloco Único")

  • Como Funciona: Todas as funcionalidades da aplicação de e-commerce (interface web da vitrine, autenticação de contas de clientes, gestão de carrinho de compras, cálculo de frete, gateway de pagamentos e relatórios de vendas) são compiladas, empacotadas e executadas como um único processo gigante, compartilhando o mesmo esquema de banco de dados relacional.
  • O Problema da Escalabilidade Excessiva: Se uma campanha promocional (como a Black Friday) gerar uma sobrecarga súbita de acessos ao serviço de "Carrinho de Compras", a equipe de infraestrutura é obrigada a escalar o monólito inteiro! Você precisa provisionar instâncias de servidores gigantescas e replicar todo o catálogo, o módulo de frete e os relatórios (desperdiçando memória RAM, CPU e orçamento da AWS).
  • O Risco do Ponto Único de Falha (Single Point of Failure): Como todos os módulos rodam no mesmo processo em memória, se o desenvolvedor cometer um erro de ponteiro nulo ou vazamento de memória no módulo secundário de cálculo de frete, o processo do servidor sofre um encerramento forçado (*crash*) e a loja inteira sai do ar para todos os clientes do mundo!
  • Acoplamento Tecnológico Estrito: Toda a organização fica refém de uma única linguagem de programação e de uma versão fixa de biblioteca, dificultando inovações pontuais.

2. A Arquitetura de Microsserviços (Desacoplamento e Autonomia)

  • Como Funciona: O sistema é decomposto em múltiplos componentes pequenos, modulares e independentes, com responsabilidade única e contexto bem delimitado (*Bounded Context*).
    • O Storefront UI é um serviço independente em Node.js.
    • O Account service é um serviço autônomo.
    • O Cart service roda em Python com seu próprio banco otimizado em memória (Amazon ElastiCache).
    • O Shipping service roda em Java com seu próprio banco de dados relacional.
  • Comunicação Leve por APIs: Os serviços comunicam-se exclusivamente através de contratos de interface bem definidos, utilizando chamadas REST/HTTP, gRPC ou filas de mensageria assíncrona (Amazon SQS, SNS e EventBridge).
  • A Vantagem da Escalabilidade Cirúrgica: Se o Carrinho de Compras receber 100.000 requisições simultâneas, você escala apenas o contêiner do Carrinho, mantendo os demais serviços dimensionados de forma econômica.
  • Isolamento Total de Falhas: Se o serviço de frete falhar temporariamente, os clientes continuam navegando na vitrine, adicionando produtos ao carrinho e fechando pedidos (com frete calculado posteriormente por fila assíncrona).

Por que os Contêineres são o "Par Perfeito" para Microsserviços?

A filosofia de microsserviços encontra no Docker o veículo de transporte ideal por quatro razões técnicas fundamentais:

  1. Liberdade e Descentralização Tecnológica (Arquitetura Poliglota):

    Como cada microsserviço reside em seu próprio contêiner isolado, cada equipe de engenharia tem autonomia total para escolher a pilha tecnológica mais adequada para o seu domínio (ex: Node.js para I/O intensivo no front-end, Python para cálculos e IA no carrinho, Java ou Rust para alta performance financeira). Diferentes versões de bibliotecas coexistem no mesmo cluster sem qualquer conflito.

  2. Produtos Independentes e Ciclos de Deploy Desacoplados:

    O contêiner empacota o código e todas as suas dependências em um artefato imutável. Isso permite que a equipe de frete faça deploys de novas versões 10 vezes ao dia em produção sem exigir coordenação com as equipes de catálogo ou pagamentos, e sem nunca pausar o sistema.

  3. Projetados para Falhar (Descartabilidade: *Start Fast, Fail Fast*):

    Contêineres inicializam e encerram em frações de segundo. Se uma instância apresentar lentidão ou comportamento anômalo, o orquestrador simplesmente a destrói de forma graciosa e instancia um novo contêiner saudável em milissegundos. Isso viabiliza padrões arquiteturais de alta resiliência, como Circuit Breakers e auto-recuperação (*Self-Healing*).

  4. Paridade Rigorosa entre Dev e Prod:

    O contêiner assegura que o ambiente de desenvolvimento local, a esteira de testes automatizados e o cluster de produção na AWS compartilhem exatamente os mesmos binários, variáveis e configurações, fortalecendo a cultura DevOps e garantindo previsibilidade absoluta.

7. Introducing AWS container services

Executar e gerenciar um ou dois contêineres na máquina local através do terminal é simples e direto. O verdadeiro desafio surge no mundo corporativo real: como manter em produção um ecossistema com dezenas de instâncias de servidores e centenas de contêineres distribuídos? Como agendar contêineres nos hosts com memória e CPU disponíveis? Como balancear o tráfego de rede e o que acontece quando um servidor físico falha?

Para solucionar essa complexidade operacional em larga escala, a AWS oferece um conjunto robusto de serviços gerenciados de registro, orquestração e computação elástica.

1. Amazon ECR (Elastic Container Registry): O Cofre das Imagens

Antes de executar contêineres em produção na nuvem, você precisa de um local seguro, confiável e altamente disponível para armazenar seus artefatos compilados. O Amazon ECR é o "Docker Hub corporativo e privado" da AWS.

  • Totalmente Gerenciado e de Alta Disponibilidade: As imagens Docker são armazenadas com redundância de dados respaldada pela arquitetura do Amazon S3, garantindo durabilidade de 99,999999999% (11 noves).
  • Segurança Integrada em Primeiro Lugar: Diferente de repositórios públicos, no Amazon ECR todas as comunicações são criptografadas em trânsito via HTTPS/TLS, as imagens são criptografadas em repouso por padrão (com AWS KMS) e o controle de acesso é estritamente regulado pelas políticas e perfis do AWS IAM.
  • Escaneamento Automatizado de Vulnerabilidades: O ECR realiza verificações de segurança nas imagens (Image Scanning) identificando vulnerabilidades e exposições comuns (CVEs) em pacotes de sistema operacional.
  • Desempenho Otimizado: O tráfego de rede entre o Amazon ECR e outros serviços AWS na mesma região (como ECS, EKS ou EC2) é roteado pela infraestrutura interna de alta velocidade da AWS, sem custos adicionais de transferência de dados (*Data Transfer*).

2. Amazon ECS (Elastic Container Service): O Maestro da Orquestração Nativa

O Amazon ECS é o orquestrador nativo da AWS projetado para automatizar a implantação, o agendamento (*scheduling*), a escalabilidade e o gerenciamento contínuo de contêineres Docker em larga escala.

  • Como Funciona: O ECS recupera a imagem armazenada no Amazon ECR, interpreta a Definição de Tarefa (Task Definition) — que define memória, CPU, portas de rede e variáveis de ambiente — e distribui os contêineres de forma otimizada pelas Zonas de Disponibilidade (Multi-AZ), garantindo resiliência e auto-recuperação contínua.
  • Integração Nativa Profunda com o Ecossistema AWS:
    • Application Load Balancer (ALB): Suporte a Dynamic Port Mapping, permitindo rodar múltiplos contêineres da mesma aplicação no mesmo host sem conflito de portas TCP.
    • AWS IAM: Concessão de permissões granulares por contêiner através de IAM Roles for Tasks (cada contêiner acessa apenas os recursos que precisa).
    • Amazon CloudWatch: Roteamento nativo de logs de contêiner via driver awslogs e métricas em tempo real de consumo de CPU/Memória.
    • AWS Secrets Manager e SSM Parameter Store: Injeção segura de senhas e credenciais diretamente no ambiente do contêiner.

3. O Grande Dilema de Arquitetura: Fargate vs. EC2 (Atenção para Provas!)

Ao solicitar que o Amazon ECS execute seus contêineres, você deve definir o Launch Type (modelo de infraestrutura computacional onde os contêineres serão hospedados):

Critério de Comparação Modelo Amazon EC2 (Launch Type EC2) Modelo AWS Fargate (Launch Type Serverless)
Gerenciamento de Servidores Você gerencia e mantém o cluster de instâncias EC2 (SO, patches, atualizações do Docker daemon). Totalmente Serverless. Você não gerencia nenhuma máquina virtual ou cluster.
Nível de Controle Controle total sobre o SO hospedeiro, acesso root via SSH e escolha detalhada de hardware/AMIs. Nenhum acesso ao SO subjacente. Foco estritamente na configuração da aplicação.
Modelo de Cobrança Você paga pelas instâncias EC2 ativas, estejam os contêineres consumindo recursos ou ociosos. Você paga por segundo estritamente pela vCPU e memória RAM alocadas para as tarefas em execução.
Elasticidade e Picos Escala em dois níveis: precisa adicionar mais instâncias EC2 antes de poder subir novos contêineres. Instantânea. O Fargate aloca capacidade computacional sob demanda para cada contêiner em segundos.
Melhores Casos de Uso Workloads previsíveis e estáveis com Instâncias Reservadas / Savings Plans, GPUs customizadas ou requisitos regulatórios de SO. Microsserviços modernos, times enxutos (foco total em código), workloads com picos imprevisíveis e jobs em lote (batch).

Compreendidos os conceitos de orquestração e modelos de lançamento, aprofundamos agora o fluxo operacional completo de publicação de imagens no Amazon ECR e exploramos a solução gerenciada de Kubernetes da AWS: o Amazon EKS.

O Fluxo Prático do Amazon ECR (Do Terminal para a Nuvem)

A publicação de uma aplicação conteinerizada no Amazon ECR envolve uma esteira de 4 etapas essenciais executadas pela combinação da AWS CLI com a Docker CLI:

  1. Criar o Repositório no ECR:

    Primeiro, você provisiona o "cofre" que armazenará as versões da sua imagem na nuvem:

    aws ecr create-repository --repository-name cafe-supplier --region us-east-1
  2. Compilar e Taguear a Imagem Localmente:

    No seu ambiente de desenvolvimento, você compila a imagem via docker build e, em seguida, utiliza o docker tag para associar a imagem local ao endereço completo do repositório remoto (incluindo o ID da sua conta AWS de 12 dígitos e a região):

    docker build -t cafe-supplier .
docker tag cafe-supplier:latest 123456789012.dkr.ecr.us-east-1.amazonaws.com/cafe-supplier:latest
  3. Autenticação Segura (O "Login" no ECR):

    O cliente Docker nativo não compreende credenciais do IAM. O comando aws ecr get-login-password gera um token de autenticação temporário de 12 horas que é repassado via pipe diretamente para o comando docker login:

    aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
  4. O Envio (Push) das Camadas para a Nuvem:

    Com o cliente autenticado, você envia as camadas da imagem para o repositório seguro da AWS:

    docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/cafe-supplier:latest

Amazon EKS (Elastic Kubernetes Service): O Padrão Aberto na Nuvem

Se o Amazon ECS é a solução nativa, simples e opinativa da AWS, o Amazon EKS é a resposta líder de mercado para empresas que adotaram a plataforma open-source de orquestração Kubernetes.

  • O que é o Kubernetes: É o sistema open-source de orquestração de contêineres mais popular e utilizado globalmente, mantido pela Cloud Native Computing Foundation (CNCF), permitindo automação de deploy, escalonamento e gerenciamento de aplicações em contêineres agrupados em Pods.
  • A Complexidade Resolvida pelo EKS: Instalar, configurar e manter o plano de controle (Control Plane) do Kubernetes por conta própria é uma tarefa extremamente árdua, arriscada e propensa a falhas operacionais (exige gerenciar o banco de dados distribuído etcd, múltiplos servidores de API kube-apiserver, controladores e agendadores com alta disponibilidade). O Amazon EKS automatiza integralmente essa camada:
    • A AWS provisiona e gerencia o Control Plane com alta disponibilidade garantida em múltiplas Zonas de Disponibilidade (Multi-AZ) com SLA de 99,95%.
    • A AWS gerencia upgrades de versão do Kubernetes, backups do etcd e substituição automática de instâncias defeituosas do control plane de forma invisível.
  • Conformidade Oficial Estrita (Certified Kubernetes Conformant): O EKS roda a versão oficial upstream do Kubernetes puro. Isso garante portabilidade total: qualquer manifesto YAML, chart do Helm, operador ou ferramenta do ecossistema CNCF (Istio, Prometheus, Fluentd, ArgoCD) funciona no EKS sem nenhuma alteração no código.
  • Os Nós Operários (Worker Nodes no EKS): Assim como no ECS, no EKS você pode escolher como executar os Pods reais da sua aplicação:
    • Amazon EC2: Nós de trabalho em instâncias EC2 gerenciadas por Managed Node Groups (a AWS automatiza o provisionamento e atualizações de nós) ou nós autogerenciados.
    • AWS Fargate (Serverless no Kubernetes): Através de Fargate Profiles, o EKS executa cada Pod individual em seu próprio ambiente de execução de microVM totalmente isolado, sem necessidade de gerenciar nós EC2 ou planejar capacidade de cluster!
Resumo de Decisão Arquitetural: ECS vs. EKS vs. Elastic Beanstalk:
• AWS Elastic Beanstalk: A forma mais simples de subir aplicações web em contêineres na nuvem sem precisar aprender a fundo sobre orquestradores (PaaS gerenciado).
• Amazon ECS: Escolha recomendada para quem deseja uma orquestração poderosa, leve e nativa da AWS com curva de aprendizado suave e integração perfeita com IAM/ALB.
• Amazon EKS: Escolha estratégica para empresas que já utilizam Kubernetes on-premises, necessitam de portabilidade multi-cloud ou possuem ecossistemas avançados baseados em ferramentas da CNCF.

9. Deploying applications with AWS Elastic Beanstalk - part 1

O AWS Elastic Beanstalk é um serviço gerenciado do tipo Platform-as-a-Service (PaaS) projetado para que equipes de desenvolvimento consigam implantar, monitorar e escalar aplicações e microsserviços web rapidamente na nuvem. Ele automatiza integralmente os detalhes mais complexos de infraestrutura — como provisionamento de servidores, balanceamento de carga, auto-scaling e health checks contínuos —, permitindo que você gerencie todos os recursos subjacentes centralizados em um único ambiente unificado.

Componentes Principais do Elastic Beanstalk

Para operar com o Elastic Beanstalk, é essencial dominar a hierarquia e o vocabulário de seus blocos fundamentais:

  • Application (Aplicação):

    Uma coleção lógica de componentes do Elastic Beanstalk que funciona conceitualmente como uma pasta de projeto. Ela agrupa versões de código-fonte, ambientes provisionados e configurações salvas.

  • Application Version (Versão da Aplicação):

    Uma iteração específica, rotulada e imutável do código-fonte ou contêiner que será implantado. Normalmente aponta para um pacote compactado (arquivo .zip ou .war) armazenado no Amazon S3 ou para uma imagem Docker hospedada no Amazon ECR.

  • Environment (Ambiente):

    O conjunto real de recursos computacionais da AWS provisionados e configurados para executar uma versão específica da aplicação. Uma única aplicação pode abrigar múltiplos ambientes independentes, como Development, Staging e Production.

  • Environment Tier (Camada do Ambiente):

    Define a arquitetura e a finalidade operacional da aplicação, determinando quais recursos o Beanstalk provisionará:

    • Web Server Tier: Projetado para atender requisições HTTP/HTTPS diretamente de usuários na internet. Inclui um Application Load Balancer (ALB) que distribui o tráfego de entrada para instâncias EC2 em um Auto Scaling Group.
    • Worker Tier: Projetado para tarefas de processamento em segundo plano (*background processing*) e filas de longa duração. Não possui load balancer voltado à internet; em vez disso, utiliza um daemon especializado (SQSD) que lê mensagens de uma fila do Amazon SQS e as encaminha via HTTP local para a aplicação processar.
  • Environment Configuration & Saved Configuration:

    Coleção de parâmetros e ajustes que controlam o comportamento do ambiente (tipo e família das instâncias EC2, portas de rede, variáveis de ambiente, gatilhos de escalabilidade). As configurações podem ser exportadas como Saved Configurations para servirem de modelos reutilizáveis (*templates*) em novos ambientes.

  • Platform (Plataforma):

    A combinação pré-configurada de sistema operacional (Amazon Linux 2 / Amazon Linux 2023), runtime de linguagem (Node.js, Python, Java, PHP, .NET, Go, Ruby), servidor web reverso (Nginx ou Apache HTTPD) e motor de contêineres Docker.

  • Elastic Beanstalk CLI (eb):

    Interface de linha de comando interativa e altamente produtiva desenvolvida em Python que permite inicializar projetos (eb init), provisionar ambientes (eb create), implantar código (eb deploy), acompanhar logs (eb logs) e abrir a aplicação no navegador (eb open) diretamente pelo terminal.

Modelo de Permissões do IAM no Elastic Beanstalk

O Elastic Beanstalk opera através de uma divisão clara de responsabilidades de segurança no AWS Identity and Access Management (IAM):

Papel / Política IAM Quando é Atribuída Finalidade Operacional e Permissões Perfil Padrão Gerenciado
Service Role (Função de Serviço) Durante a criação inicial do ambiente. Permite que o serviço Elastic Beanstalk invoque APIs da AWS em seu nome para provisionar e gerenciar recursos (EC2, ELB, Auto Scaling, CloudWatch). aws-elasticbeanstalk-service-role
Instance Profile (Perfil de Instância) Durante a criação do ambiente; anexado diretamente às instâncias EC2. Concede permissões para as instâncias EC2 baixarem o pacote de código do S3, gravarem logs no CloudWatch, enviarem métricas de saúde e baixarem imagens do ECR. aws-elasticbeanstalk-ec2-role (inclui as políticas WebTier, WorkerTier e MulticontainerDocker).
User Policies (Políticas de Usuário) Atribuída a desenvolvedores ou grupos no IAM. Determina as permissões que usuários humanos ou esteiras de CI/CD possuem para criar, modificar, configurar ou visualizar ambientes do Beanstalk. AdministratorAccess ou AWSElasticBeanstalkReadOnly

Implantação de Contêineres: Amazon ECS vs. Elastic Beanstalk

O Elastic Beanstalk utiliza o AWS CloudFormation nos bastidores para automatizar todo o trabalho pesado de infraestrutura:

  • O processo no Amazon ECS puro: Exige que o engenheiro crie e gerencie manualmente as VPCs, sub-redes, Security Groups, cluster de servidores, perfis do IAM, Task Definitions com JSONs complexos e crie um Service para manter as tarefas rodando.
  • O processo no Elastic Beanstalk: Exige apenas escrever um arquivo de manifesto simples chamado Dockerrun.aws.json (ou fornecer um Dockerfile), selecionar a plataforma Docker no console ou CLI e clicar em iniciar. Toda a orquestração do ECS e da rede é abstraída e gerenciada de forma transparente.

A Plataforma Docker Multicontêiner

A plataforma multicontêiner do Elastic Beanstalk permite executar múltiplos contêineres Docker simultaneamente dentro da mesma instância EC2, aproveitando ao máximo a capacidade de CPU e memória em um grupo de Auto Scaling. Para isso, as imagens dos contêineres devem estar previamente publicadas em um registro (como o Amazon ECR ou Docker Hub público).

Ao iniciar um ambiente Docker Multicontêiner, o Elastic Beanstalk provisiona automaticamente os seguintes recursos do Amazon ECS para você:

  1. Amazon ECS Cluster: Um cluster ECS dedicado é criado automaticamente nos bastidores para abrigar as instâncias EC2 do ambiente.
  2. Amazon ECS Task Definition: A definição de tarefas do ECS é gerada automaticamente pelo Beanstalk a partir da leitura do seu arquivo Dockerrun.aws.json.
  3. Amazon ECS Task: O Beanstalk inicia e gerencia as tarefas ECS em cada instância EC2, escalando-as dinamicamente conforme a demanda de acessos varia.
  4. Amazon ECS Container Agent: Um daemon que executa em contêiner em cada instância EC2, comunicando-se com o serviço ECS para coordenar e reportar o status de execução de cada contêiner.

Configuração de Contêineres: O Arquivo Dockerrun.aws.json

Para executar aplicações Docker multicontêiner no Elastic Beanstalk, as instâncias EC2 exigem um arquivo de configuração declarativo denominado Dockerrun.aws.json. Esse arquivo pode ser enviado sozinho diretamente no deploy ou empacotado dentro de um arquivo .zip junto com o código-fonte.

O arquivo possui três seções estruturais indispensáveis:

{
  "AWSEBDockerrunVersion": 2,
  "volumes": [
    {
      "name": "app-storage",
      "host": {
        "sourcePath": "/var/app/storage"
      }
    }
  ],
  "containerDefinitions": [
    {
      "name": "web-app",
      "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/cafe-supplier:latest",
      "essential": true,
      "memory": 512,
      "portMappings": [
        {
          "hostPort": 80,
          "containerPort": 3000
        }
      ],
      "mountPoints": [
        {
          "sourceVolume": "app-storage",
          "containerPath": "/usr/src/app/storage"
        }
      ]
    }
  ]
}
  • AWSEBDockerrunVersion: Define a versão da especificação. Para ambientes multicontêiner no Elastic Beanstalk, o valor deve ser obrigatoriamente 2 (o valor 1 é exclusivo para implantações de contêiner único).
  • volumes: Declara os volumes de armazenamento mapeados a partir de diretórios do host EC2 ou do pacote de código. Esses volumes são montados nos contêineres para persistência ou compartilhamento de arquivos entre múltiplos contêineres.
  • containerDefinitions: Uma lista (array) contendo a definição detalhada de cada contêiner (imagem no ECR, memória alocada em MB, portas mapeadas, variáveis de ambiente e volumes). O formato é rigorosamente compatível com as Task Definitions do Amazon ECS.

Políticas de Implantação (Deployment Policies): Velocidade vs. Segurança

Ao atualizar a versão de uma aplicação em produção, o Elastic Beanstalk permite escolher entre diferentes políticas de deploy para equilibrar tempo de implantação, custo de recursos e tolerância a indisponibilidade (*downtime*):

Política de Deploy Mecânica de Funcionamento Impacto na Capacidade e Disponibilidade Recomendação de Uso
All at once (Tudo de uma vez) Implanta a nova versão em todas as instâncias EC2 simultaneamente. Causa Downtime. Todas as instâncias ficam indisponíveis enquanto o serviço reinicia. Ambientes de desenvolvimento e testes rápidos, onde o downtime é aceitável. Método mais rápido.
Rolling (Contínua em Lotes) Atualiza as instâncias em lotes sequenciais (ex: 2 instâncias por vez). Sem downtime, porém reduz a capacidade total do cluster durante o processo. Produção com tráfego moderado e capacidade ociosa suficiente para suportar a perda temporária de um lote.
Rolling with additional batch (Com Lote Adicional) Lança previamente um lote extra de novas instâncias antes de começar a atualizar os lotes existentes. Sem downtime e SEM redução de capacidade (mantém 100% da capacidade ativa em todo o deploy). Produção crítica que opera perto do limite de carga e não tolera nenhuma degradação de desempenho.
Immutable (Imutável) Lança um grupo de Auto Scaling temporário paralelo com instâncias totalmente limpas e novas. Serve tráfego para ambas até validar os health checks. Sem downtime e com segurança máxima. Rollback quase instantâneo destruindo o novo grupo caso haja falha. Implantações de missão crítica onde a integridade é prioritária e não se deseja herdar configurações residuais antigas.
Traffic Splitting (Divisão de Tráfego / Canary) Lança instâncias novas paralelas (como na Imutável), mas direciona apenas uma pequena fração do tráfego (ex: 10%) para a nova versão. Sem downtime e risco mínimo. Permite testar a versão em produção real com usuários reais (*Canary Testing*). Lançamento gradual de versões com validação comportamental antes da virada completa de 100% do tráfego.

Namespaces e Automação de Configuração com .ebextensions

Todas as opções de implantação e parâmetros de ambiente podem ser versionados como código (IaC) adicionando arquivos de configuração com extensão .config dentro da pasta oculta .ebextensions/ na raiz do projeto:

  • aws:elasticbeanstalk:command: Utilizado para configurar a estratégia de implantação, o tempo limite (*timeout*), o tamanho percentual ou numérico dos lotes e se o deploy deve ser cancelado automaticamente caso os testes de saúde falhem: 
    option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: RollingWithAdditionalBatch
    BatchSizeType: Percentage
    BatchSize: 50
    Timeout: 600
  • aws:elasticbeanstalk:trafficsplitting: Utilizado para parametrizar a política de Divisão de Tráfego (Canary Testing): 
    option_settings:
  aws:elasticbeanstalk:trafficsplitting:
    NewVersionPercent: 10
    EvaluationTime: 15

    No exemplo acima, exatamente 10% do tráfego é direcionado para a nova versão durante uma janela de avaliação de 15 minutos. Se os alarmes do CloudWatch permanecerem saudáveis, os 90% restantes são migrados automaticamente!

Implantações Blue/Green (Azul/Verde) com Troca de CNAME (Swap CNAMEs)

Enquanto as políticas anteriores atualizam instâncias dentro do mesmo ambiente, a abordagem Blue/Green consiste em manter dois ambientes do Elastic Beanstalk totalmente independentes e paralelos:

  1. O ambiente atual de produção (Blue) atende 100% dos usuários no URL público (ex: cafe-api.elasticbeanstalk.com).
  2. Você clona o ambiente ou cria um novo ambiente idêntico (Green) e implanta a nova versão nele, testando e homologando as alterações em isolamento total.
  3. A Virada de Chave (Swap Environment CNAMEs): No console ou CLI (eb swap), você executa a troca de CNAMEs. O Elastic Beanstalk altera o mapeamento de DNS nos bastidores, redirecionando instantaneamente todo o tráfego de produção para o ambiente Green sem nenhuma perda de conexão!
  4. Uso Obrigatório: Esse método é estritamente obrigatório quando você precisa atualizar seu ambiente para uma versão de plataforma do Beanstalk incompatível com a atual (por exemplo, migrando de uma AMI legada do Amazon Linux 2 para o Amazon Linux 2023, ou trocando o tipo de Load Balancer de Classic para Application Load Balancer).
Síntese para o Arquiteto de Nuvem:
• O Elastic Beanstalk centraliza todo o ciclo de vida da aplicação em um único painel com automação de infraestrutura via CloudFormation.
• O arquivo Dockerrun.aws.json (versão 2) possibilita rodar contêineres Docker multicontêiner sem a sobrecarga de gerenciar clusters ECS manualmente.
• Para máxima segurança e zero downtime, utilize as políticas Rolling with additional batch, Immutable ou estratégias Blue/Green com Swap CNAMEs!

Tarefa 2: Configuração das Sub-redes para Amazon RDS e AWS Elastic Beanstalk

Tanto o Amazon RDS / Aurora (via DB Subnet Groups) quanto o AWS Elastic Beanstalk com balanceamento de carga exigem a presença de pelo menos duas sub-redes em Zonas de Disponibilidade (AZs) distintas na mesma VPC. Isso garante resiliência contra falhas em um datacenter físico.

Tarefa 9: Criar a Aplicação e o Ambiente no AWS Elastic Beanstalk

Nesta etapa, você criará a aplicação e o ambiente Elastic Beanstalk via AWS CLI e implantará a aplicação de fornecedores em contêiner Docker usando um arquivo de manifesto Dockerrun.aws.json.

  1. No terminal do VS Code, prepare o diretório da aplicação e crie a aplicação Beanstalk: 
    cd ~/environment
mkdir bean && cd bean
aws elasticbeanstalk create-application --application-name MyNodeApp
  2. Crie o arquivo de configurações do ambiente options.txt dentro de ~/environment/bean: 
    [
  {
    "Namespace": "aws:autoscaling:launchconfiguration",
    "OptionName": "IamInstanceProfile",
    "Value": "aws-elasticbeanstalk-ec2-role"
  },
  {
    "Namespace": "aws:autoscaling:launchconfiguration",
    "OptionName": "SecurityGroups",
    "Value": "<FMI_1>"
  },
  {
    "Namespace": "aws:ec2:vpc",
    "OptionName": "VPCId",
    "Value": "<FMI_2>"
  },
  {
    "Namespace": "aws:ec2:vpc",
    "OptionName": "Subnets",
    "Value": "<FMI_3>,<FMI_4>"
  },
  {
    "Namespace": "aws:elasticbeanstalk:application:environment",
    "OptionName": "APP_DB_HOST",
    "Value": "<FMI_5>"
  }
]

    Substitua os placeholders pelos valores coletados:

    • <FMI_1>: IDE security group ID
    • <FMI_2>: IDE VPC ID
    • <FMI_3>,<FMI_4>: IDE subnet ID,extraSubnetForRds subnet ID (separados por vírgula sem espaços)
    • <FMI_5>: Database endpoint
  3. Identifique a Solution Stack mais recente do Docker no Amazon Linux 2: 
    aws elasticbeanstalk list-available-solution-stacks | grep 'running Docker'

    Exemplo de pilha retornada: 64bit Amazon Linux 2 v4.0.5 running Docker

  4. Inicie o ambiente Elastic Beanstalk executando: 
    aws elasticbeanstalk create-environment   --application-name MyNodeApp   --environment-name MyEnv   --solution-stack-name "64bit Amazon Linux 2 v4.0.5 running Docker"   --region us-east-1   --option-settings file://options.txt
  5. Acompanhe a criação do ambiente no console do AWS Elastic Beanstalk. Aguarde até que o status de saúde passe de Pendente/Cinza para Ok (Verde).
  6. Abra a URL do domínio gerado (MyEnv.eba-xxxxxxx.us-east-1.elasticbeanstalk.com) para visualizar a aplicação de exemplo padrão do Elastic Beanstalk em execução.
  7. Agora, atualize o ambiente com o código do aplicativo de fornecedores criando o manifesto Dockerrun.aws.json (versão 1 para contêiner único): 
    {
  "AWSEBDockerrunVersion": "1",
  "Image": {
    "Name": "<Repository-URI>",
    "Update": "true"
  },
  "Ports": [
    {
      "ContainerPort": 3000
    }
  ]
}

    Nota Arquitetural: O Elastic Beanstalk recebe tráfego na porta padrão 80 (via proxy Nginx ou Load Balancer) e faz proxy reverso automaticamente para a porta declarada em ContainerPort (porta 3000 da aplicação Node.js).

  8. No console do Elastic Beanstalk, no ambiente MyEnv:
    • Clique no botão Fazer upload e implantar (Upload and deploy).
    • Selecione o arquivo Dockerrun.aws.json.
    • Em Rótulo de versão (Version label), insira MyNodeApp-version-1a.
    • Clique em Implantar.
  9. Após a conclusão da implantação, teste os seguintes endpoints no navegador:
    • http://<elastic-beanstalk-url>/suppliers → Lista HTML dos fornecedores.
    • http://<elastic-beanstalk-url>/beans → Lista HTML do inventário de grãos.
    • http://<elastic-beanstalk-url>/beans.json → Objeto JSON estruturado contendo todas as 14 variedades de café. Guarde esta URL!
