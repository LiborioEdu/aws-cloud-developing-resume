13. Automating Deployment Using CI/CD Pipelines

1. Introduction

Depois de aprender a arquitetar bancos de dados relacionais e NoSQL, desacoplar sistemas com mensageria (SNS/SQS), orquestrar fluxos complexos com Step Functions e proteger aplicações com AWS STS e Amazon Cognito, chegou a hora de aprender a entregar tudo isso em produção. O foco central deste módulo final é como sair definitivamente do infame "funciona na minha máquina" para o "rodando em produção" de forma 100% automatizada, previsível e segura.

Objetivos de Aprendizado

Neste módulo, você entrará no universo da automação de infraestrutura e entrega de software. Ao final, você será capaz de:

  • Compreender a cultura, as práticas técnicas e as ferramentas que compõem o DevOps.
  • Reconhecer a suíte de serviços de desenvolvimento da AWS (AWS Code Services) focada em Integração Contínua e Entrega Contínua (CI/CD).
  • Descrever como o AWS CloudFormation é usado para provisionar, gerenciar e versionar infraestrutura como código (Infrastructure as Code - IaC).
  • Descrever como o AWS SAM (Serverless Application Model) é usado para implantar arquiteturas sem servidor de forma simplificada e declarativa.

O Caso da Cafeteria (O Fim do Trabalho Manual)

A Sofía percebeu um problema clássico de desenvolvimento: fazer o deploy (implantação) das novas versões do site e das APIs manualmente é um processo lento, estressante e altamente propenso a falhas humanas (alguém sempre esquece de copiar um arquivo atualizado, aplicar uma política de IAM ou configurar uma variável de ambiente).

Conversando com o engenheiro Mateo, ela decide adotar a filosofia DevOps. O objetivo agora é construir um Pipeline Automatizado: assim que os desenvolvedores terminarem de escrever o código e enviarem para o repositório, a própria nuvem da AWS vai testar, empacotar e lançar a atualização no ar, de ponta a ponta, sem intervenção humana.

2. Introducing DevOps

O DevOps não é um cargo ou uma ferramenta única: é uma Filosofia Cultural combinada com Práticas Técnicas que unem o time de Desenvolvimento (Dev) ao time de Operações/Infraestrutura (Ops).

A Grande Mudança de Paradigma na Nuvem

Antes da nuvem, o desenvolvedor escrevia o código no seu computador e "jogava o pacote por cima do muro" para a equipe de infraestrutura se virar para hospedar e configurar nos servidores (gerando o clássico conflito: "na minha máquina funciona, o problema deve ser no servidor de vocês").

A Nova Regra de Ouro na Nuvem: "A sua aplicação não é apenas o seu código-fonte. A sua aplicação é o código-fonte + toda a infraestrutura associada a ele."

Como na nuvem tudo é virtualizado e 100% programável através de APIs, os próprios desenvolvedores conseguem e devem provisionar seus bancos de dados DynamoDB, instâncias EC2, tópicos SNS, buckets S3 e redes VPC diretamente como parte do ciclo de desenvolvimento.

As 4 Práticas Técnicas do DevOps

Para que a união entre Dev e Ops funcione com velocidade e estabilidade, o mercado adotou 4 práticas fundamentais:

  1. Arquitetura de Microsserviços: Abandonar sistemas monolíticos gigantescos e adotar serviços menores, independentes e desacoplados (utilizando contêineres Docker e funções AWS Lambda). Se uma parte do sistema falhar ou precisar de atualização, o restante da aplicação continua operando normalmente, permitindo deploys frequentes e seguros.
  2. Infraestrutura como Código (Infrastructure as Code - IaC): Parar de clicar em botões no console da AWS para criar servidores manualmente. Você escreve um arquivo de texto declarativo (código em YAML ou JSON) especificando todos os recursos que precisa, e a AWS cria, atualiza e audita tudo automaticamente utilizando o AWS CloudFormation.
  3. Monitoramento e Telemetria Contínua: Utilizar métricas, logs centralizados e rastreamento distribuído (como Amazon CloudWatch e AWS X-Ray) para descobrir gargalos e falhas operacionais antes mesmo que os clientes percebam ou abram chamados de suporte.
  4. Integração Contínua e Entrega Contínua (CI/CD):
    • CI (Continuous Integration - Integração Contínua): Desenvolvedores fundem (merge) seus códigos frequentemente (várias vezes ao dia) em um repositório central compartilhado. O sistema automaticamente compila o código e roda testes automatizados de unidade a cada alteração para garantir que ninguém quebrou a base de código.
    • CD (Continuous Delivery / Deployment - Entrega/Implantação Contínua): Se o código passar com sucesso em todos os testes, o sistema o empacota e o lança nos servidores de produção automaticamente, completando a automação de ponta a ponta sem atritos operacionais.

O Objetivo Final do DevOps: Garantir entregas de software rápidas, frequentes, escaláveis e com alto nível de segurança, eliminando totalmente a dependência de processos manuais lentos, burocráticos e sujeitos a falhas humanas.

3. Using AWS code services for CI/CD

A sigla CI/CD é o coração técnico e o motor operacional da cultura DevOps. Nesta seção, a AWS define as fronteiras exatas de cada fase do ciclo de entrega de software e apresenta a sua suíte de ferramentas gerenciadas e serverless para executar essa automação.

Fases da esteira de software (Code, Build, Test, Deploy) e a extensão de cada estágio: Continuous Integration, Continuous Delivery (com intervenção manual) e Continuous Deployment (100% automatizado)

A Diferença Exata entre CI, Continuous Delivery e Continuous Deployment

Embora sejam frequentemente citados juntos como "CI/CD", esses termos representam níveis progressivos de maturidade na automação do pipeline de software:

  1. Integração Contínua (CI - Continuous Integration):
    • O que é: Os desenvolvedores enviam (commit e push) pequenas alterações de código para um repositório central compartilhado (como GitHub ou AWS CodeCommit) várias vezes ao dia.
    • O que a automação faz: Assim que o código chega, o sistema compila o código-fonte, instala dependências e executa testes automatizados de unidade (unit tests) para garantir que a nova alteração não quebrou nenhuma funcionalidade pré-existente.
    • Onde termina: O ciclo de CI termina na fase de Build / Teste Inicial gerando um pacote ou artefato compilado pronto e validado.
  2. Entrega Contínua (CD - Continuous Delivery):
    • O que é: Estende o CI para além da compilação. O artefato aprovado nos testes é implantado automaticamente em ambientes de teste, homologação (staging) ou pré-produção para testes de integração, carga e segurança.
    • A Característica Fundamental: Existe um Portão de Intervenção Manual (Manual Intervention / Approval Gate). O código está pronto e tecnicamente validado para ir para produção a qualquer momento, mas a liberação final para os clientes reais depende de um clique humano de aprovação de um líder técnico, product owner ou operador de operações.
  3. Implantação Contínua (CD - Continuous Deployment):
    • O que é: É o nível máximo de maturidade e automação de uma esteira DevOps.
    • Sem Qualquer Intervenção Humana: Do instante em que o desenvolvedor faz o git push no repositório até o código estar rodando nos servidores de produção atendendo clientes reais, não há aprovações manuais nem cliques intermediários.
    • Se o código passar em todas as etapas sucessivas de compilação, testes de unidade, testes de regressão e verificações de segurança, ele é lançado diretamente em produção de forma 100% autônoma.

Pegadinha Clássica de Certificação: A diferença exata entre Continuous Delivery e Continuous Deployment é exclusivamente a presença da aprovação manual para entrar em produção. No Delivery, a implantação em produção é acionada manualmente após testes; no Deployment, a implantação em produção é totalmente automática.

A Suíte de Serviços CI/CD da AWS (AWS Code Services)

Em vez de montar e manter servidores dedicados complexos (como clusters autogerenciados de Jenkins que precisam de patches, upgrades e gerenciamento de capacidade), a AWS disponibiliza uma suíte de serviços nativos totalmente gerenciados e serverless especializados em cada elo da esteira:

A suíte de serviços de código da AWS: CodeBuild para compilar e testar, ferramentas de teste integradas, intervenção manual opcional, CodeDeploy para instalar e CodePipeline orquestrando o fluxo

1. AWS CodeBuild (O Compilador e Executor de Testes):

  • Totalmente Serverless: Você não provisiona nem gerencia servidores ou agentes de build. O CodeBuild sobe contêineres sob demanda, executa os comandos e os destrói logo após a conclusão.
  • Escalabilidade Elástica e Paralelismo: Ele escala dinamicamente com o volume de requisições, permitindo que dezenas de builds e baterias de testes rodem simultaneamente em paralelo sem criar filas de espera.
  • Cobrança por Minuto de Computação: Paga-se estritamente pelos minutos exatos em que a compilação ficou executando.
  • O Arquivo buildspec.yml: O comportamento do CodeBuild é configurado declarativamente por meio de um arquivo YAML na raiz do projeto dividido em 4 fases sequenciais:
version: 0.2

phases:
  install:
    runtime-versions:
      python: 3.11
    commands:
      - echo "Instalando dependencias da aplicacao..."
      - pip install -r requirements.txt
  pre_build:
    commands:
      - echo "Executando analise estatica e testes unitarios..."
      - pytest tests/
  build:
    commands:
      - echo "Compilando e empacotando a aplicacao..."
      - python setup.py build
  post_build:
    commands:
      - echo "Build concluido com sucesso em $(date)"

artifacts:
  files:
    - '**/*'
  base-directory: 'dist'

2. AWS CodeDeploy (O Implantador Automatizado):

  • Destinos Suportados: Automatiza a implantação de código e contêineres em uma ampla variedade de plataformas computacionais: instâncias Amazon EC2, contêineres Amazon ECS / AWS Fargate, funções AWS Lambda e até servidores físicos locais (on-premises).
  • Implantação sem Indisponibilidade (Zero Downtime): Suporta estratégias sofisticadas de substituição de software:
    • In-place Deployment: Atualiza as instâncias existentes em lotes progressivos (ex: One-at-a-time, Half-at-a-time), garantindo que parte do parque de servidores continue atendendo clientes enquanto a outra é atualizada.
    • Blue/Green Deployment: Cria um novo ambiente espelho (Green) com a versão nova, roda testes de integridade e, em seguida, redireciona o tráfego do Elastic Load Balancer (ELB) do ambiente antigo (Blue) para o novo sem interrupção. Em caso de falha, o rollback é instantâneo redirecionando o balanceador de volta para o ambiente Blue.
  • O Arquivo appspec.yml: Define o passo a passo da instalação e os ganchos de ciclo de vida (Lifecycle Event Hooks) que executam scripts antes e depois da implantação (ex: BeforeInstall, AfterInstall, ApplicationStart, ValidateService).

3. AWS CodePipeline (O Orquestrador da Esteira):

  • A "Esteira de Montagem" de Produção: O CodePipeline é o serviço visual que conecta todos os pontos da entrega de software, criando o fluxo automatizado de ponta a ponta.
  • Gatilhos Rápidos de Evento: Monitora repositórios (GitHub, AWS CodeCommit, Bitbucket, Amazon S3 ou Amazon ECR) através de eventos do Amazon EventBridge. No instante em que um novo commit é enviado, o CodePipeline detecta a mudança e inicia a execução da esteira.
  • Passagem de Artefatos: Cada etapa gera artefatos de saída (Output Artifacts compactados em .zip salvos em um bucket seguro do S3) que são repassados como artefatos de entrada (Input Artifacts) para a etapa seguinte.
  • Suporte a Aprovação Manual: Permite inserir etapas de Manual Approval com notificações via Amazon SNS (disparando e-mail para os líderes da equipe com botão de aprovação ou rejeição antes de promover para produção).

Resumo Visual da Integração: O CodePipeline atua como o maestro da orquestra: ele puxa o código novo do GitHub/CodeCommit, aciona o CodeBuild para compilar e testar, pausa para aprovação manual se configurado, e aciona o CodeDeploy para lançar a versão final nos servidores e contêineres!

4. Deploying applications with CloudFormation

O AWS CloudFormation é o motor central que transforma o conceito de Infraestrutura como Código (Infrastructure as Code - IaC) em realidade prática na AWS. Ele permite construir, atualizar, versionar e deletar conjuntos inteiros de recursos da nuvem utilizando apenas arquivos de texto declarativos, garantindo que os ambientes de Teste, Homologação e Produção sejam clones idênticos e 100% reproduzíveis.

O Fluxo Básico do CloudFormation: Template → Engine → Stack

O funcionamento do CloudFormation é sustentado por dois conceitos primários inseparáveis: o Template (Gabarito) e a Stack (Pilha de Recursos):

  1. O Desenvolvedor escreve um Template: Um arquivo de texto estruturado (em YAML ou JSON) que descreve o estado desejado da infraestrutura (quais servidores, bancos de dados, redes e permissões devem existir).
  2. O CloudFormation interpreta o Template: O mecanismo da AWS analisa a sintaxe, mapeia as dependências entre recursos e planeja a ordem exata de criação ou atualização.
  3. O CloudFormation provisiona a Stack: O serviço entra em ação e executa todas as chamadas de API da AWS para criar a infraestrutura. O conjunto de recursos criados e gerenciados juntos a partir daquele template é chamado de Stack.

A Regra de Ouro do CloudFormation: A Stack é uma unidade de ciclo de vida indivisível. Se você deletar a Stack, o CloudFormation deletará automaticamente todos os recursos criados dentro dela de forma coordenada e limpa. Isso elimina para sempre recursos "órfãos" que continuariam gerando custos esquecidos na conta da AWS!

Anatomia de um Template do CloudFormation

Os templates são arquivos de texto estruturados em JSON ou YAML. A AWS aceita ambos os formatos com paridade total de recursos, porém o YAML é o padrão mais adotado pela comunidade por ser muito mais conciso, limpo e suportar comentários explicativos (#).

Um template pode conter diversas seções, mas apenas uma seção é estritamente obrigatória. Conheça as três seções mais importantes cobradas nos exames de desenvolvedor e arquiteto:

1. Parameters (Parâmetros - Seção Opcional):

Permite que a sua infraestrutura receba variáveis externas e customizadas no momento exato em que a Stack for criada ou atualizada (em tempo de execução).

  • Evita hardcoding de valores fixos no template, permitindo reaproveitar o mesmo arquivo para múltiplos ambientes.
  • Exemplo: Perguntar qual o tipo de instância EC2 utilizar (t3.micro em dev vs. m5.large em prod) ou solicitar o nome de usuário do banco.
  • Segurança com NoEcho: Ao definir "NoEcho": "true" para senhas e credenciais, o CloudFormation mascara o valor digitado com asteriscos no console, CLI e eventos de log para que ninguém consiga ler o dado sensível.
"Parameters": { 
  "DBUser": { 
    "NoEcho": "true", 
    "Type": "String", 
    "Description": "Nome da conta admin do banco de testes" 
  }
}

2. Resources (Recursos - SEÇÃO ESTRITAMENTE OBRIGATÓRIA):

É o coração palpitante do template. É aqui que você declara formalmente quais componentes da AWS você deseja criar (instâncias EC2, volumes EBS, tabelas DynamoDB, tópicos SNS, funções Lambda, buckets S3, etc.).

  • Se o template não possuir a seção Resources, ele falha imediatamente com erro de sintaxe.
  • Cada recurso possui um Tipo de Recurso padronizado com a convenção AWS::Servico::NomeDoRecurso (como AWS::EC2::Volume, AWS::S3::Bucket, AWS::Lambda::Function) acompanhado de suas propriedades de configuração (Properties).
"Resources": { 
  "Ec2Volume": { 
    "Type": "AWS::EC2::Volume", 
    "Properties": { 
      "Size": "5", 
      "AvailabilityZone": {
        "Fn::Select": [0, {"Fn::GetAZs": ""}]
      } 
    }
  }
}

3. Outputs (Saídas - Seção Opcional):

Declara os valores que o CloudFormation deve calcular e devolver para você na tela do console ou via CLI assim que terminar de provisionar a Stack.

  • Exemplo Prático: Se o template criou um banco de dados Aurora ou uma distribuição CloudFront, a seção Outputs pode exportar o endpoint DNS de conexão, o ID da VPC ou a URL pública para que sua aplicação ou outras stacks consigam se conectar automaticamente.
  • Exportação Cross-Stack: Permite que uma Stack A exporte um valor (com Export: Name: ...) e uma Stack B importe esse valor dinamicamente utilizando a função intrínseca Fn::ImportValue.
"Outputs": {
  "DatabaseEndpoint": {
    "Description": "URL de conexao do banco de dados",
    "Value": {"Fn::GetAtt": ["MyDBInstance", "Endpoint.Address"]},
    "Export": {
      "Name": "CafeDatabaseEndpoint"
    }
  }
}

Gestão de Dependências e o Atributo DependsOn

O CloudFormation é um mecanismo inteligente de ordenação topológica: ele é capaz de descobrir automaticamente as dependências entre recursos analisando o uso de referências internas (como Ref e Fn::GetAtt). Por exemplo, se uma instância EC2 faz referência ao ID de um Security Group, o CloudFormation sabe que precisa criar o Security Group antes de tentar subir a instância.

No entanto, quando você precisa forçar explicitamente uma ordem de criação específica entre recursos que não possuem referências diretas no código, utiliza-se o atributo DependsOn:

  • Exemplo Clássico: Se você deseja que um servidor Web EC2 só inicie o provisionamento depois que o banco de dados RDS estiver completamente operacional e aceitando conexões, basta adicionar DependsOn: MeuBancoRDS na declaração da máquina virtual.
  • O CloudFormation aguardará a conclusão bem-sucedida do recurso alvo antes de iniciar a criação do recurso dependente.

Recursos de Segurança e Estabilidade da Stack

Para garantir confiabilidade e proteção contra desastres em produção, o CloudFormation oferece recursos nativos indispensáveis:

  • Rollback Automático em Caso de Falha: Se qualquer recurso dentro da Stack falhar durante o provisionamento (por exemplo, estourar o limite de cota de instâncias ou um erro de configuração), o CloudFormation desfaz todas as criações anteriores automaticamente, retornando o ambiente ao último estado estável conhecido (sem deixar lixo operacional ou recursos pela metade).
  • Change Sets (Conjuntos de Alterações): Semelhante a um git diff ou dry-run, o Change Set gera uma pré-visualização detalhada de todas as alterações que a atualização do template provocará na infraestrutura (quais recursos serão adicionados, modificados ou destruídos) antes de você autorizar a execução.
  • DeletionPolicy (Proteção Contra Deleção Acidental): Por padrão, se a Stack for deletada, todos os recursos são excluídos. Porém, ao definir DeletionPolicy: Retain em bancos de dados relacionais (RDS) ou buckets S3, o CloudFormation preserva o recurso intacto mesmo após a exclusão da Stack.
  • Drift Detection (Detecção de Desvio): Permite verificar a qualquer momento se alguém realizou alterações manuais diretamente no console da AWS fora do template, identificando divergências entre o código da Stack e o estado real dos recursos.

5. Deploying applications with AWS SAM

O AWS SAM (Serverless Application Model) é um framework de código aberto projetado especificamente para facilitar a vida de quem desenvolve, testa e implanta aplicações sem servidor (Serverless) na nuvem.

Escrever a infraestrutura completa para uma função AWS Lambda integrada a um Amazon API Gateway e permissões de IAM usando AWS CloudFormation puro exige centenas de linhas de código JSON/YAML complexas e repetitivas. O SAM resolve essa fricção funcionando como uma "extensão" (ou atalho de sintaxe) do CloudFormation: você escreve poucas linhas concisas no SAM, e o motor de macros da AWS traduz isso nos bastidores para um template gigante de CloudFormation com dezenas de recursos subjacentes.

Os Dois Componentes Fundamentais do AWS SAM

O ecossistema do AWS SAM é estruturado em dois pilares essenciais:

  1. A Especificação de Template SAM: Uma sintaxe simplificada e expressiva para declarar funções Lambda, APIs REST/HTTP, permissões de segurança IAM e tabelas do Amazon DynamoDB em pouquíssimas linhas.
  2. O SAM CLI (A Ferramenta de Linha de Comando): É onde a mágica do fluxo de trabalho do desenvolvedor acontece. O CLI permite inicializar projetos, compilar dependências, rodar e depurar funções Lambda localmente no seu próprio computador (utilizando contêineres Docker que emulam o ambiente de execução real da AWS) antes de enviar qualquer linha de código para a nuvem.

Comandos Essenciais do SAM CLI:

  • sam init: Inicializa um novo projeto serverless estruturado a partir de modelos prontos na linguagem desejada (Node.js, Python, Java, Go).
  • sam build: Compila o código-fonte, empacota dependências e prepara os artefatos de build.
  • sam local invoke: Invoca uma função Lambda localmente via Docker passando um evento simulado (JSON).
  • sam local start-api: Sobe um emulador local do API Gateway na porta 3000 para testar chamadas HTTP locais.
  • sam deploy --guided: Empacota os arquivos no Amazon S3 e implanta/atualiza a Stack do CloudFormation na nuvem de forma guiada e interativa.
  • sam sync --watch: Sincroniza alterações de código diretamente com a nuvem em tempo real durante o desenvolvimento.

Anatomia de um Template SAM (Foco Crítico de Prova)

Um template SAM é baseado na estrutura do CloudFormation, mas apresenta três diferenças críticas que são intensamente cobradas em exames de certificação da AWS:

1. A Declaração Transform (Obrigatória):

  • Todo arquivo de template SAM precisa obrigatoriamente incluir a seguinte instrução no cabeçalho:
    Transform: AWS::Serverless-2016-10-31
  • É essa macro declarativa que avisa ao CloudFormation: "Atenção: este arquivo contém recursos simplificados do SAM. Traduza essas definições curtas para os recursos padrão do CloudFormation antes de criar a Stack!". Sem essa linha, o CloudFormation não reconhecerá a sintaxe do SAM e acusará erro de tipo de recurso inexistente.

2. A Seção Globals (Exclusiva do SAM):

  • Permite definir configurações padrão comuns que se aplicam automaticamente a todas as funções ou APIs declaradas no template (aplicando o princípio DRY - Don't Repeat Yourself).
  • Exemplo: Se você possui 10 funções Lambda no mesmo projeto e quer que todas usem o runtime python3.11 e timeout de 30 segundos, você declara isso uma única vez no bloco Globals em vez de repetir 10 vezes em cada função.

3. Tipos de Recursos Especiais do SAM:

O SAM introduz abstrações de alto nível que condensam múltiplos recursos complexos em um único bloco:

  • AWS::Serverless::Function: Cria a função Lambda, a Role de execução no IAM com políticas mínimas, o grupo de logs no CloudWatch e os mapeamentos de eventos.
  • AWS::Serverless::Api: Cria a API REST completa no Amazon API Gateway com recursos, métodos, integração Lambda e estágios de implantação.
  • AWS::Serverless::HttpApi: Cria uma HTTP API v2 moderna, com menor latência e custo reduzido em comparação com REST APIs.
  • AWS::Serverless::SimpleTable: Cria uma tabela no Amazon DynamoDB com chave primária e taxa de transferência configurada em poucas linhas.
  • AWS::Serverless::StateMachine: Declara e implanta fluxos orquestrados no AWS Step Functions com definição ASL integrada.

Exemplo em Código: Template AWS SAM Completo

Abaixo está a estrutura clássica de um template SAM configurando uma função Lambda, sua política de permissão de leitura no DynamoDB e o gatilho de API Gateway acionado por requisições HTTP GET:

AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Description: Exemplo de template AWS SAM para a Cafeteria

Globals:
  Function:
    Timeout: 30
    Runtime: python3.9

Resources:
  MinhaFuncaoLambda:
    Type: AWS::Serverless::Function
    Properties:
      Handler: index.handler
      CodeUri: ./meu_codigo/
      Policies: AmazonDynamoDBReadOnlyAccess
      Events:
        MeuEndpointApi:
          Type: Api
          Properties:
            Path: /dados
            Method: get

A Mágica da Abstração do SAM: No exemplo acima, com apenas 22 linhas de código YAML, o SAM instrui o CloudFormation a criar nos bastidores: a Função AWS Lambda, a IAM Execution Role com permissões seguras do CloudWatch Logs, o anexo da política gerenciada AmazonDynamoDBReadOnlyAccess, a API REST no API Gateway, o recurso /dados, o método GET, a integração Lambda Proxy e as permissões de invocação cruzada (AWS::Lambda::Permission). Fazer isso no CloudFormation puro exigiria mais de 100 linhas!

Modelos de Políticas do SAM (Policy Templates)

Outro grande facilitador do SAM são os Policy Templates. Em vez de escrever declarações JSON gigantescas de IAM com Effect, Action e Resource, o SAM disponibiliza mais de 75 modelos prontos que você declara pelo nome:

  • DynamoDBCrudPolicy: { TableName: !Ref MinhaTabela }: Concede permissões completas de Create, Read, Update e Delete na tabela especificada.
  • S3ReadPolicy: { BucketName: !Ref MeuBucket }: Concede permissão de leitura apenas nos objetos do bucket alvo.
  • SQSPollerPolicy: { QueueName: !Ref MinhaFila }: Permite que a função Lambda consuma e delete mensagens de uma fila SQS.

Tabela Comparativa: CloudFormation Puro vs. AWS SAM

Critério AWS CloudFormation Puro AWS SAM (Serverless Application Model)
Foco de Aplicação Qualquer recurso da nuvem AWS (EC2, VPC, RDS, Redshift, etc.) Especializado em arquiteturas Serverless (Lambda, API Gateway, DynamoDB)
Tamanho do Código Extenso e detalhado (100+ linhas para uma Lambda com API) Ultra conciso (20 linhas para a mesma arquitetura)
Declaração Obrigatória Apenas a seção Resources Declaração Transform: AWS::Serverless-2016-10-31 obrigatória
Ambiente Local de Testes Não possui ferramentas nativas para teste local SAM CLI completo com emulação local via Docker (sam local)
Integração com CI/CD Requer empacotar e gerenciar templates manualmente Integração nativa com CodeBuild, CodeDeploy e CodePipeline com sam deploy

Integração com Esteiras CI/CD: O AWS SAM possui integração profunda e nativa com o AWS CodeBuild, AWS CodeDeploy e AWS CodePipeline, permitindo que você construa esteiras automatizadas de CI/CD para suas aplicações Serverless com extrema facilidade utilizando o comando sam pipeline init.

Tarefa 3: Criação de um Pipeline para Automatizar as Atualizações do Site

Nesta tarefa, você configurará a esteira no CodePipeline para conectar o repositório CodeCommit ao bucket S3 que hospeda o site.

1. Análise do Arquivo de Definição do Pipeline:

No VS Code IDE, abra o arquivo resources/cafe_website_front_end_pipeline.json e examine as seções estruturais:

  • roleArn: Declara a Role do IAM que concede permissões para o CodePipeline ler do CodeCommit e escrever no S3.
  • stages[0] (Source): Conecta à branch main do repositório front_end_website no CodeCommit e emite o artefato de saída MyApp.
  • stages[1] (Deploy): Utiliza o provedor S3 para extrair os arquivos compactados ("Extract": "true") diretamente no bucket de hospedagem do site, aplicando o cabeçalho "CacheControl": "max-age=14".
  • artifactStore: Define o bucket S3 separado onde os artefatos intermediários da esteira serão guardados.
{
  "pipeline": {
    "name": "cafe_website_front_end_pipeline",
    "roleArn": "arn:aws:iam:::role/RoleForCodepipeline",
    "artifactStore": {
      "type": "S3",
      "location": "codepipeline-us-east-1--website"
    },
    "stages": [
      {
        "name": "Source",
        "actions": [
          {
            "name": "Source",
            "actionTypeId": {
              "category": "Source",
              "owner": "AWS",
              "version": "1",
              "provider": "CodeCommit"
            },
            "outputArtifacts": [{"name": "MyApp"}],
            "configuration": {
              "RepositoryName": "front_end_website",
              "BranchName": "main"
            },
            "runOrder": 1
          }
        ]
      },
      {
        "name": "Deploy",
        "actions": [
          {
            "name": "CafeWebsite",
            "actionTypeId": {
              "category": "Deploy",
              "owner": "AWS",
              "version": "1",
              "provider": "S3"
            },
            "inputArtifacts": [{"name": "MyApp"}],
            "configuration": {
              "BucketName": "",
              "Extract": "true",
              "CacheControl": "max-age=14"
            },
            "runOrder": 1
          }
        ]
      }
    ]
  }
}

2. Atualização dos Placeholders no JSON:

  • No terminal do VS Code, obtenha o ID da sua conta AWS:
    aws sts get-caller-identity --query Account --output text
    Substitua os dois espaços reservados <FMI_1> pelo ID da sua conta.
  • Obtenha o nome do bucket do site:
    aws s3 ls | grep s3bucket
    Substitua o espaço reservado <FMI_2> pelo nome exato do bucket que contém s3bucket.
  • Salve o arquivo cafe_website_front_end_pipeline.json (Ctrl + S).

3. Criação da Esteira via AWS CLI:

cd ~/environment/resources
aws codepipeline create-pipeline --cli-input-json file://cafe_website_front_end_pipeline.json

4. Acompanhamento no Console do CodePipeline:

  • No console da AWS, abra o AWS CodePipeline e selecione o pipeline cafe_website_front_end_pipeline.
  • Observe que a esteira foi acionada automaticamente: o estágio Source (CodeCommit) é concluído com sucesso e dispara em seguida o estágio Deploy (Amazon S3), finalizando com o status verde Succeeded!
Execução da esteira cafe_website_front_end_pipeline no console da AWS: estágios Source (CodeCommit) e Deploy (S3) concluídos com êxito

5. Verificação da Implantação Automatizada:

  • No terminal do VS Code, obtenha o domínio da distribuição CloudFront:
    aws cloudfront list-distributions --query DistributionList.Items[0].DomainName --output text
  • No navegador, abra a URL: https://<cloudfront_domain>/test.html.
  • A página "This is a sample HTML page." será exibida, comprovando que o pipeline já sincronizou o código do CodeCommit para o bucket S3 e o CloudFront distribuiu o arquivo com sucesso!
