Este módulo abandona os arquivos estáticos e foca no Amazon DynamoDB, o banco de dados NoSQL totalmente gerenciado da AWS. É um dos serviços mais rápidos, escaláveis e cobrados em certificações.

  • Utilizar Índices Secundários (Secondary Indexes) para fazer buscas eficientes.
  • Trabalhar com recursos avançados como Streams e Tabelas Globais (Global Tables).
  • Gerenciar o cálculo de capacidade de leitura e escrita (RCUs e WCUs - um cálculo clássico em exames da AWS).
  • Usar os AWS SDKs para interagir com as tabelas via código.

O Caso da Cafeteria (Cenário Prático):

  • Um script para buscar um único registro específico, filtrando pelo nome do produto.

2. Introducing AWS database options

Os bancos de dados são excelentes soluções de armazenamento persistente. No mundo AWS, eles são divididos em duas grandes categorias: Relacionais (SQL) e Não Relacionais (NoSQL).

Bancos de Dados Relacionais (SQL)

São as opções clássicas para quem precisa de estrutura rígida e integridade de dados rigorosa.

  • Armazenamento: Tabelas, linhas e colunas.
  • Esquema (Schema): Rígido. Você define as colunas primeiro e todos os registros precisam respeitá-las.
  • Consultas: Utilizam SQL padrão.
  • Escalabilidade: Vertical (você escala "engordando" o servidor com mais CPU e RAM).
Quando usar: Quando seus dados têm relações fortes entre si, você precisa garantir a qualidade e a estrutura dos dados, e não há exigência de performance ou capacidade extrema de leitura/escrita.

Opções AWS (Relacionais):

  • Amazon RDS: Serviço gerenciado que suporta os motores mais conhecidos do mercado (PostgreSQL, MySQL, MariaDB, Oracle e Microsoft SQL Server).
  • Amazon Aurora: O banco de dados relacional proprietário da AWS, feito para a nuvem. É compatível com MySQL (até 5x mais rápido) e PostgreSQL (até 3x mais rápido), entregando segurança e alta disponibilidade por uma fração do custo dos bancos comerciais.

Bancos de Dados Não Relacionais (NoSQL)

São as opções modernas para aplicações de escala global (escala de internet) que precisam de flexibilidade e performance insana.

  • Armazenamento: Pode ser Chave-Valor (Key-value), Documentos ou Grafos.
  • Esquema (Schema): Dinâmico/Inexistente (Schemaless). Um registro pode ter três atributos e o registro logo abaixo pode ter vinte atributos completamente diferentes.
  • Consultas: Focadas em coleções de documentos ou recuperação direta por chave.
  • Escalabilidade: Horizontal (você escala "multiplicando" o número de servidores).
Quando usar: Quando a estrutura dos seus dados varia muito (ou você nem sabe qual será), quando precisa de performance de um dígito de milissegundo e taxas massivas de leitura/escrita que um banco SQL tradicional não aguentaria (ou ficaria caro demais para aguentar).

Opções AWS (NoSQL):

  • Amazon DynamoDB: Banco de dados Chave-Valor e de documentos. É o foco deste módulo! Oferece performance em milissegundos e suporte a transações ACID, ótimo para aplicações críticas em escala web.
  • Amazon ElastiCache: Armazenamento de dados em memória (extremamente rápido), usado geralmente para cache, dados de sessão, análises em tempo real ou jogos.
  • Amazon Neptune: Banco de dados de grafos, feito para armazenar bilhões de relacionamentos. Excelente para motores de recomendação e detecção de fraudes.

3. Key Concepts for DynamoDB

O Amazon DynamoDB é um banco de dados NoSQL totalmente gerenciado que suporta modelos de dados chave-valor e documentos. Ele foi projetado para operar com latência consistente de um dígito de milissegundo em qualquer escala.

Os Componentes Básicos

  • Tables (Tabelas): O contêiner de nível mais alto onde todos os dados são armazenados. É semelhante a uma tabela de banco relacional, mas sem a necessidade de um esquema pré-definido.
  • Items (Itens): Cada registro na tabela. Um item é um agrupamento de atributos único em toda a tabela, comparável a uma linha (row) de um banco relacional. Cada tabela pode conter um número infinito de itens.
  • Attributes (Atributos): O elemento fundamental de dados, comparável a uma coluna. Ao contrário do modelo relacional, a maioria dos atributos não precisa ser declarada na criação da tabela.
  • Primary Key (Chave Primária): O único atributo obrigatório definido na criação da tabela que identifica univocamente cada item.

Tipos de Chaves Primárias

O DynamoDB suporta dois tipos distintos de chaves primárias:

  • Chave Primária Simples (Partition Key): Composta por apenas um atributo chamado Partition Key (Chave de Partição / Hash Attribute). O valor dessa chave é passado por uma função hash interna para determinar a partição física onde o item será gravado. Nenhum item pode ter a mesma Partition Key. Exemplo: SensorId.
  • Chave Primária Composta (Partition Key + Sort Key): Composta por dois atributos: a Partition Key e a Sort Key (Chave de Ordenação / Range Attribute).
Como funciona a Chave Composta: Vários itens podem ter exatamente a mesma Partition Key, contanto que possuam Sort Keys diferentes. Todos os itens com a mesma chave de partição são armazenados fisicamente juntos e ordenados pela Sort Key. Exemplo: SensorId (Partição) + Timestamp (Ordenação).

Flexibilidade e Tipos de Dados (Schemaless)

Com exceção da chave primária, o DynamoDB é livre de esquema (schemaless), permitindo que itens diferentes na mesma tabela tenham conjuntos completamente distintos de atributos. Os tipos de dados suportados são:

  • Escalares (Scalar Types): Um valor único exato. Suporta Number, String, Binary, Boolean e Null.
  • Conjuntos (Sets): Múltiplos valores escalares únicos do mesmo tipo. Suporta String Set (SS), Number Set (NS) e Binary Set (BS).
  • Documentos (Document Types): Estruturas complexas aninhadas com até 32 níveis de profundidade, utilizando List (L) (elementos ordenados) e Map (M) (pares chave-valor JSON).

4. Partitions and data

O DynamoDB não guarda todos os dados da sua tabela em um único disco rígido ou servidor. Ele divide sua tabela em pedaços menores chamados Partições (Partitions).

O que são Partições?

  • Espaço Físico Gerenciado: Uma partição é um espaço físico de armazenamento (em discos SSD super rápidos) gerenciado inteiramente pela AWS.
  • Escalabilidade Automática: Você não cria nem gerencia partições manualmente. Se sua tabela crescer demais ou precisar de mais velocidade, o DynamoDB cria novas partições e espalha os dados automaticamente por elas.

A Função de Hash e a Distribuição

O que decide para qual partição um dado vai é a sua Chave de Partição (Partition Key).

  • Cálculo do Hash: Quando você manda gravar um item novo, o DynamoDB pega o valor da chave de partição (ex: "AnimalType": "Dog") e joga em uma Função de Hash (função matemática) interna.
  • Endereçamento Exato: O resultado numérico desse cálculo indica o endereço exato de uma partição. O item é gravado lá.
Por que é tão rápido? Por conta desse cálculo direto, o DynamoDB não precisa vasculhar toda a tabela para encontrar um item; ele sabe exatamente em qual disco ele está. É por isso que uma consulta leva milissegundos, independentemente se a tabela tem 1 megabyte ou 100 terabytes de tamanho.

Como a Chave Composta Organiza os Dados

Se sua tabela usar uma Chave Primária Composta (Partition Key + Sort Key):

  • Papel da Partition Key: A Chave de Partição continua sendo responsável por escolher a partição física (o disco). Ou seja, todos os cachorros ("Dog") vão cair na mesma partição.
  • Papel da Sort Key: Dentro dessa partição específica, a Chave de Ordenação entra em ação. O DynamoDB guarda fisicamente todos os itens com a mesma chave de partição agrupados um do lado do outro, ordenados crescentemente pelo valor da Chave de Ordenação (ex: "Fido", depois "Rover", depois "Spot").
  • Buscas Otimizadas em Lote: Isso torna extremamente rápido fazer buscas em lote, como "Me traga todos os cachorros cujo nome comece com a letra R".

5. Secondary indexes

No DynamoDB, a forma mais rápida (e barata) de buscar dados é usando a Chave Primária. Mas e se você precisar pesquisar por outro atributo que não é a chave? É aí que entram os Índices Secundários (Secondary Indexes).

O que é um Índice Secundário?

Um Índice Secundário funciona como uma "cópia espelho" parcial da sua tabela, organizada com chaves diferentes para permitir buscas super-rápidas baseadas em outros atributos (ex: buscar um pedido pela Data em vez do ID_Pedido).

  • Projeção de Atributos (Projected Attributes): Quando você cria um índice, escolhe quais atributos quer copiar da tabela original para esse índice. No mínimo, as chaves primárias são projetadas automaticamente.

1. Global Secondary Index (GSI - Índice Secundário Global)

  • Como funciona: Cria uma estrutura onde a Chave de Partição E a Chave de Ordenação podem ser totalmente diferentes das chaves da tabela original.
  • Por que é Global? Porque uma consulta neste índice pode varrer dados de todas as partições originais da tabela base.
  • Limites de Tamanho: Não possui limite de tamanho.
  • Capacidade (Throughput): O GSI é totalmente independente: possui sua própria configuração dedicada de capacidade de leitura e escrita (RCUs e WCUs), separada da tabela original.
  • Criação: Pode ser criado a qualquer momento (durante ou após a criação da tabela).
Exemplo de GSI: Em uma tabela Músicas (Chave de partição: Artista), você pode criar um GSI com a chave de partição Gênero para consultar rapidamente todas as músicas de um determinado gênero (ex: "Country"), sem precisar percorrer a tabela inteira com um Scan.

2. Local Secondary Index (LSI - Índice Secundário Local)

  • Como funciona: Mantém a MESMA Chave de Partição da tabela original, mas define uma Chave de Ordenação (Sort Key) diferente.
  • Por que é Local? Porque os dados deste índice ficam confinados (locais) à mesma partição física do item na tabela original.
  • Limites de Tamanho: Como fica na mesma partição do dado original, o limite máximo de tamanho (dados da partição + índice) para uma mesma Chave de Partição é de 10 GB.
  • Capacidade (Throughput): O LSI compartilha (consome) a mesma capacidade de leitura e escrita configurada para a tabela original.
  • Criação Rígida: Só pode ser criado no exato momento da criação da tabela. Depois que a tabela já existe, não é possível adicionar um LSI.
Exemplo de LSI: Em uma tabela Músicas (Chave: Artista + Sort: NomeDaMusica), você cria um LSI (Chave: Artista + Sort: Album) para poder listar todos os álbuns de um artista ordenados alfabeticamente.

6. Read/write Throughput

O DynamoDB oferece dois modos principais de capacidade para atender diferentes perfis de tráfego, previsibilidade e custo:

1. Modo Sob Demanda (On-Demand Capacity Mode)

  • Como funciona: Modelo Pay-per-request. Você paga exatamente pela quantidade de requisições de leitura e escrita realizadas. A tabela escala de forma instantânea e automática de zero até milhares de requisições por segundo sem qualquer intervenção manual.
  • Quando usar: Ideal para cargas de trabalho novas com tráfego desconhecido, aplicações com picos imprevisíveis ou quando você prefere a simplicidade e conveniência de pagar apenas pelo que usar, sem precisar calcular limites.

2. Modo Provisionado (Provisioned Capacity Mode)

  • Como funciona: Você define previamente a capacidade máxima (um limite) que a tabela pode suportar, e paga um valor fixo por essa capacidade alocada, independentemente de usá-la totalmente ou não.
  • Unidades de Capacidade: Esse limite é medido em RCUs (Read Capacity Units) e WCUs (Write Capacity Units).

Como Calcular RCU e WCU (Importante para Provas)

Essa matemática cai muito nas provas da AWS. As regras base são:
  • 1 WCU (Escrita): Permite gravar 1 item de até 1 KB por segundo.
  • 1 RCU (Leitura Consistente): Permite ler 1 item de até 4 KB por segundo (Leitura Fortemente Consistente - Strongly Consistent).
  • Leitura Eventualmente Consistente (Eventual Consistency): Consome apenas metade de um RCU (0.5 RCU) por leitura de até 4 KB. O DynamoDB usa isso por padrão (dados podem vir ligeiramente desatualizados, mas é mais barato).

Exemplo Prático 1: Calculando RCU

Cenário: Você precisa ler 20 itens por segundo, cada um com 11 KB, usando consistência eventual. Quantos RCUs?

  1. Arredondar o tamanho para o próximo múltiplo de 4 KB: 11 KB arredonda para 12 KB.
  2. Dividir por 4 KB (tamanho de 1 RCU): 12 / 4 = 3 RCUs necessários para cada leitura.
  3. Multiplicar pela quantidade de itens por segundo: 3 RCUs × 20 leituras = 60 RCUs (se fosse fortemente consistente).
  4. Ajustar para consistência eventual (divide por 2): 60 / 2 = 30 RCUs.
Resultado Final: São necessários 30 RCUs para suportar essa carga.

Exemplo Prático 2: Calculando WCU

Cenário: Você precisa gravar 120 itens por minuto, cada um com 7 KB. Quantos WCUs?

  1. Arredondar o tamanho para o próximo múltiplo de 1 KB: 7 KB já é exato (se fosse 6.2 KB, arredondaria para 7 KB). Portanto, 7 WCUs por item.
  2. Ajustar o tempo para SEGUNDOS: 120 itens por minuto = 2 itens por segundo (120 / 60 segundos).
  3. Multiplicar: 7 WCUs × 2 itens/segundo = 14 WCUs.
Resultado Final: São necessários 14 WCUs para suportar essa carga.

7. Streams and Global Tables

DynamoDB Streams (O "Diário" de Mudanças)

O DynamoDB Streams é um recurso opcional que funciona como um observador em tempo real de todas as alterações feitas na sua tabela.

  • O que ele faz: Captura uma sequência cronológica ordenada no nível de item de cada modificação (criações, atualizações e exclusões).
  • Retenção e Estrutura: Os registros de log são organizados em contêineres chamados Shards e ficam armazenados por um período estrito de 24 horas. Após esse prazo, são excluídos automaticamente.
  • Visões do Registro (StreamViewType): Você escolhe quais informações gravar no stream: apenas chaves (KEYS_ONLY), a imagem anterior (OLD_IMAGE), a nova imagem (NEW_IMAGE) ou ambas as imagens antes e depois da alteração (NEW_AND_OLD_IMAGES).
Caso de uso clássico: Arquiteturas orientadas a eventos. Quando um usuário altera seus dados de perfil, o Stream detecta a mudança instantaneamente e aciona uma função AWS Lambda para enviar um e-mail de confirmação ou atualizar um índice de busca externo (como OpenSearch).

Tabelas Globais (Global Tables)

Se a sua aplicação possui usuários distribuídos pelo mundo (América do Norte, Europa, Ásia), centralizar o banco de dados em uma única região gera latência perceptível. As Global Tables resolvem isso oferecendo replicação multi-região e multi-ativa.

  • O que é: Uma solução totalmente gerenciada multi-ativo (leituras e escritas locais em qualquer região participante). Você define quais regiões deseja e a AWS cria e sincroniza automaticamente réplicas idênticas da tabela.
  • A Mágica da Replicação: As Tabelas Globais dependem obrigatoriamente do DynamoDB Streams para funcionar. Qualquer alteração em uma réplica local é capturada pelo Stream e propagada para as demais réplicas globais em questão de segundos.
  • Resolução de Conflitos (Concurrent Updates): Se dois usuários atualizarem simultaneamente o mesmo item em regiões diferentes, o DynamoDB adota a estratégia "Último a escrever vence" (Last Writer Wins), utilizando carimbos de data/hora nos milissegundos para sincronizar a versão definitiva em todas as réplicas.
Consistência de Leitura em Tabelas Globais (Regra para Exames): Você só obtém Leituras Fortemente Consistentes ao ler na mesma região onde a gravação foi executada. Leituras feitas em réplicas de outras regiões são sempre Eventualmente Consistentes, pois há um intervalo curto (geralmente menos de um segundo) para a propagação trans-regional dos dados.

8. Backup and Restore

O DynamoDB oferece duas estratégias complementares de proteção para garantir a integridade e retenção dos seus dados. Ambas podem ser acionadas pelo AWS Management Console, AWS CLI ou via chamadas de API (SDKs).

1. Backups Sob Demanda (On-Demand Backups)

São cópias completas (full backups) da sua tabela geradas no momento exato em que você as solicita.

  • Quando usar: Ideais para arquivamento de longo prazo, retenção periódica de dados e cumprimento estrito de normas regulatórias e de auditoria (compliance).
  • Performance Garantida (Zero Impact): Tirar um backup não degrada o desempenho nem afeta a disponibilidade ou latência da sua tabela em produção.
  • Custo de Capacidade: As operações de backup não consomem suas unidades de capacidade provisionadas (RCUs/WCUs) da tabela.
  • Sem Limite de Retenção: Não há limite para a quantidade de backups sob demanda que você pode criar e reter.

2. Recuperação em um Ponto no Tempo (Point-in-Time Recovery - PITR)

Funciona como uma "máquina do tempo" automatizada e contínua, protegendo a tabela contra desastres, exclusões e corrupções acidentais (por exemplo, quando um script defeituoso apaga registros críticos em produção).

  • Como funciona: Uma vez habilitado com um único clique, você não precisa agendar rotinas. O DynamoDB realiza backups incrementais contínuos nos bastidores.
  • Janela de Restauração de 35 Dias: Permite restaurar a tabela para qualquer segundo exato dentro da janela móvel dos últimos 35 dias (com precisão de segundos).
  • Restauração como Nova Tabela: Toda restauração (tanto sob demanda quanto PITR) cria uma nova tabela com os dados recuperados, preservando a tabela original intacta.

9. Part 1: Basic operations for DynamoDB tables

Visão Geral das Operações da API

A API do DynamoDB organiza suas ações em grupos lógicos, com foco central nas Operações de Dados (Data Operations).

Diferente de um banco de dados relacional clássico (onde se executam instruções SQL textuais como INSERT INTO, UPDATE ou DELETE), no Amazon DynamoDB as interações ocorrem exclusivamente via chamadas de métodos da API com envio de estruturas em objetos JSON / Dicionários (utilizando SDKs como o Boto3 em Python, AWS SDK for JavaScript, Java, etc.).

Ponto Importante: As 4 operações fundamentais de manipulação direta de registros em tabelas são CreateTable (plano de controle), PutItem, UpdateItem e DeleteItem (plano de dados), complementadas por Expressões Condicionais (Condition Expressions) para garantir consistência e atomicidade.

1. Criar uma Tabela (CreateTable)

Esta é uma operação do Plano de Controle (Control Plane), responsável por provisionar a infraestrutura da tabela.

  • O que faz: Cria a definição da tabela em si.
  • Comportamento Assíncrono: A chamada retorna imediatamente com a tabela no status CREATING por alguns instantes até transicionar para ACTIVE (pronta para uso).
  • Parâmetros Obrigatórios:
    • TableName: Nome exclusivo da tabela no escopo da conta/região.
    • KeySchema: Define a estrutura da Chave Primária — quem atua como Partition Key (HASH) e quem atua como Sort Key (RANGE), se for chave composta.
    • AttributeDefinitions: Especifica o tipo de dados dos atributos que compõem as chaves (ex: 'S' para String, 'N' para Number, 'B' para Binary). Atributos que não fazem parte de chaves não precisam ser declarados previamente.
    • ProvisionedThroughput: Configuração de capacidade provisionada inicial (ReadCapacityUnits e WriteCapacityUnits), necessária caso não seja selecionado o modo On-Demand (Pay-per-request).

2. Criar ou Sobrescrever um Item (PutItem)

Insere um novo item ou sobrescreve integralmente um item preexistente com a mesma chave primária.

  • O que faz: Grava um registro completo na tabela.
  • Parâmetros: Exige o parâmetro Item completo (mapa de chave-valor contendo obrigatoriamente a chave primária e, opcionalmente, qualquer quantidade de atributos adicionais).
⚠️ Detalhe Crucial para o Exame: Se você executar um PutItem passando uma Chave Primária que já existe na tabela, o DynamoDB NÃO gera erro! Ele simplesmente apaga o registro antigo por inteiro e grava o novo por cima. Para evitar essa substituição acidental de dados, deve-se utilizar uma Condition Expression (como attribute_not_exists(PK)).

3. Atualizar um Item (UpdateItem)

Modifica atributos específicos de um item existente sem a necessidade de reescrever ou reenviar todos os outros atributos.

  • Como funciona: Fornece-se a Chave Primária (Key) para localizar o item e uma expressão de atualização (UpdateExpression) descrevendo a alteração (ex: SET age = :val1), acompanhada dos valores de substituição (ExpressionAttributeValues).
⚠️ Detalhe Crucial para o Exame (Comportamento de Upsert): Se o item com a chave primária fornecida não existir, o DynamoDB cria um novo item do zero contendo a chave primária e os atributos especificados na UpdateExpression!

4. Deletar um Item (DeleteItem)

Remove permanentemente um único item da tabela com base na sua chave primária exata.

  • Como funciona: Requer apenas a especificação da Chave Primária completa (Key: Partition Key e Sort Key, se aplicável).
  • Consumo de Throughput: Deletar um item consome unidades de escrita (WCUs) proporcionais ao tamanho do item excluído.

Bônus de Segurança: Expressões Condicionais (Condition Expressions)

Mecanismo de proteção atômico para prevenir sobrescritas indevidas, exclusões acidentais ou condições de corrida (race conditions).

  • Por que usar: As operações PutItem, UpdateItem e DeleteItem podem ser destrutivas se executadas sem validação. Condition Expressions garantem que a mutação só ocorra se uma premissa de negócio for atendida.
  • Como funciona: Atrela-se uma condição à requisição. O DynamoDB avalia a condição no lado do servidor antes de efetivar a gravação. Se a condição for verdadeira, a operação executa; se for falsa, o banco recusa a operação e retorna o erro ConditionalCheckFailedException sem alterar nenhum dado.
  • Exemplo Prático: Desbloquear a conta de um usuário (SET accountLocked = 'N') através de um UpdateItem, SOMENTE SE o tempo decorrido desde o último login com falha for superior a 24 horas (currentLoginTime > lastFailedLoginTime + 24 hours).

9. Part 2: Basic operations for DynamoDB tables

Formas de Recuperação de Dados

Existem três métodos primordiais para ler dados no Amazon DynamoDB: GetItem, Query e Scan. Eles diferem profundamente em eficiência, velocidade e custo de Throughput (RCUs).

1. GetItem (O Sniper)

Busca cirúrgica de um único item específico na tabela com a máxima eficiência e menor latência possível.

  • O que faz: Busca um único registro diretamente na tabela.
  • Como funciona: É obrigatório fornecer a Chave Primária completa e exata (Partition Key e Sort Key, se a tabela tiver chave composta).
  • Eficiência e Custo: É o método mais rápido, previsível (latência consistente de 1 dígito de milissegundo) e barato de leitura, pois o DynamoDB vai direto na partição física exata do disco onde o item está gravado.
  • Otimização com ProjectionExpression: Você pode usar o parâmetro ProjectionExpression para solicitar apenas os atributos necessários de volta, evitando trafegar o item inteiro pela rede (ex: trazer apenas o first_name e account_type deste username).
⚠️ Dica de Prova sobre ProjectionExpression: O uso de ProjectionExpression economiza banda de rede e memória na sua aplicação, mas NÃO reduz o consumo de RCUs! O DynamoDB cobra RCUs com base no tamanho total do item lido no disco antes de filtrar os atributos projetados. 
# Exemplo de leitura cirúrgica com GetItem (Boto3)
response = table.get_item(
    Key={
        'username': 'janedoe',
        'last_name': 'Doe'
    }
)
item = response['Item']
print(item)
# Saída: {'username': 'janedoe', 'first_name': 'Jane', 'last_name': 'Doe', 'account_type': 'standard_user', 'age': Decimal('25')}

2. Query (A Busca Eficiente)

Pesquisa focada e altamente otimizada, retornando uma coleção ordenada de itens que compartilham a mesma Chave de Partição.

  • O que faz: Retorna uma coleção de itens (zero, um ou vários) que possuem a mesma Chave de Partição (Partition Key).
  • Como funciona: É obrigatório fornecer uma KeyConditionExpression especificando o valor exato da Partition Key (ex: Key('username').eq('johndoe')). Opcionalmente, pode-se filtrar e ordenar pela Sort Key (ex: traga todos os registros de um sensor com data maior que determinada marca temporal).
  • Eficiência: Altamente performático. O DynamoDB acessa diretamente a partição correspondente no cluster e recupera os dados já previamente ordenados pela Sort Key.
  • Filtro Adicional (FilterExpression): Depois que o DynamoDB localiza os dados pela chave primária, você pode aplicar um FilterExpression para refinar os resultados com base em atributos que não fazem parte da chave antes de enviá-los à aplicação.
⚠️ Dica de Prova sobre FilterExpression: O FilterExpression é aplicado DEPOIS que os dados são lidos do disco e NÃO reduz o consumo de RCUs. Você paga pelas RCUs de todos os itens recuperados pela KeyConditionExpression, mesmo que o filtro descarte a maioria deles antes da entrega. 
# Exemplo de consulta com Query (Boto3)
response = table.query(
    KeyConditionExpression = Key('username').eq('johndoe')
)
items = response['Items']

3. Scan (A Varredura Lenta - Cuidado!)

Operação de força bruta que examina cada item de toda a tabela ou índice, de ponta a ponta.

  • O que faz: Lê todos os itens de toda a tabela (ou índice global/local) sequencialmente.
  • Como funciona: O banco varre partição por partição, avaliando item por item. Mesmo que você aplique um FilterExpression (ex: Attr('age').lt(27)), o DynamoDB obrigatoriamente lê 100% da tabela no disco para só depois descartar o que não bate com o filtro.
  • Eficiência e Custo: É a operação mais cara, demorada e que mais consome RCUs. Em tabelas grandes, pode consumir toda a cota provisionada e gerar erros de ProvisionedThroughputExceededException (throttling) para toda a aplicação.
  • Regra de Ouro: Evite o Scan! Sempre que possível, modele seus dados e use Índices Secundários (GSIs) para resolver suas consultas com Query. Se o Scan for realmente inevitável, utilize um Scan Paralelo (Parallel Scan) dividindo a varredura em múltiplas threads concorrentes.
# Exemplo de varredura com Scan (Boto3)
response = table.scan(
    FilterExpression = Attr('age').lt(27)
)
items = response['Items']

Otimizando Consultas e Scans (Limites e Paginação)

Para evitar que uma única busca sature a rede, esgote a memória da aplicação ou cause picos descontrolados de RCUs, o DynamoDB impõe limites automáticos:

  • Paginação Automática de 1 MB: Uma única chamada de Query ou Scan nunca retorna mais do que 1 Megabyte de dados brutos. Se a busca encontrar mais dados, o banco devolve os itens processados até 1 MB acompanhados de um cursor/marcador: LastEvaluatedKey.
  • Como Buscar as Próximas Páginas: Sua aplicação deve verificar se LastEvaluatedKey está presente na resposta. Se estiver, faz uma nova chamada passando esse valor no parâmetro ExclusiveStartKey para continuar a leitura de onde parou, iterando até que a chave venha vazia.
  • Parâmetro Limit: Permite estipular um teto máximo de itens a serem avaliados antes de interromper a chamada (observação: o Limit é aplicado antes do FilterExpression).

Operações em Lote e Transações (Batch vs Transact)

Fazer chamadas individuais na API para cada item gera alta latência de rede. Para solucionar isso, o DynamoDB oferece operações agrupadas:

1. Operações em Lote (Batch operations)

  • BatchGetItem: Lê múltiplos itens de uma vez (até 100 itens ou 16 MB no total), podendo inclusive buscar em tabelas diferentes na mesma requisição.
  • BatchWriteItem: Grava (PutItem) ou deleta (DeleteItem) múltiplos itens (até 25 requisições ou 16 MB no total). Não suporta UpdateItem.
  • Característica Crucial (Processamento Independente): As operações do lote são executadas individualmente. Se você enviar 25 itens e o item 3 falhar (por exemplo, por throttling), os outros 24 serão persistidos normalmente. A API devolve os itens pendentes no campo UnprocessedItems para que sua aplicação tente gravá-los novamente.

2. Operações Transacionais (Transaction operations)

  • Utilizadas para processos críticos de negócio que exigem garantia matemática de consistência (ex: debitar o saldo da Conta A e creditar na Conta B).
  • TransactWriteItems / TransactGetItems: Realiza alterações ou leituras coordenadas em múltiplos itens (até 100 itens ou 4 MB).
  • Característica Crucial (Garantia ACID - Tudo ou Nada): É uma regra estrita de all-or-nothing. Se um único item falhar na validação ou na expressão condicional, toda a transação é cancelada e revertida, garantindo que os dados nunca fiquem corrompidos ou em estado intermediário inconsistente.
Resumo Rápido para Exame:
• Batch: Execução independente, até 25 writes ou 100 reads. Falha parcial tratada via UnprocessedItems.
• Transact: Atômica (ACID), regra de "tudo ou nada". Reverte 100% da operação se 1 item falhar.

Tarefa 7: Adição de um índice secundário global (GSI) à tabela

Para a página inicial da cafeteria, carregar todas as 26 imagens causaria lentidão desnecessária. Frank e Martha pedem para exibir apenas os produtos do cardápio especial da semana (specials) que estão disponíveis (em estoque).

Como o atributo special não faz parte da chave primária, fazer um Scan completo filtrado consumiria muitos RCUs. A solução ideal da AWS é criar um Global Secondary Index (GSI) esparso.

  1. No VS Code, abra python_3/add_gsi.py e substitua <FMI_1> pelo tipo de chave: HASH.
  2. Examine a estrutura da operação UpdateTable: 
    params = {
    'TableName': 'FoodProducts',
    'AttributeDefinitions': [
        {'AttributeName': 'special', 'AttributeType': 'N'}
    ],
    'GlobalSecondaryIndexUpdates': [
        {
'Create': {
    'IndexName': 'special_GSI',
    'KeySchema': [
        {'AttributeName': 'special', 'KeyType': 'HASH'}
    ],
    'Projection': {
        'ProjectionType': 'ALL' # Projeta todos os atributos na cópia do índice
    },
    'ProvisionedThroughput': {
        'ReadCapacityUnits': 1,
        'WriteCapacityUnits': 1
    }
}
        }
    ]
}
table = DDB.update_table(**params)
print("DONE")
    Índice Esparso (Sparse Index): Apenas os itens que possuem o atributo numérico special serão indexados no special_GSI. Itens comuns sem esse atributo são ignorados, resultando em um índice muito menor, mais rápido e econômico de ler.
  3. No terminal, execute o script para iniciar o provisionamento do GSI: 
    python3 add_gsi.py
  4. No console do DynamoDB, vá na aba Indexes (Índices) da tabela FoodProducts e aguarde o status do índice mudar de Creating (Criando) para Active (Ativo).
