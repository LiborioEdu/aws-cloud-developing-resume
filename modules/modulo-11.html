11. Defining Workflows to Orchestrate Functions

1. Introduction

O AWS Step Functions é o serviço serverless definitivo da AWS para coordenar múltiplos recursos em nuvem (como diversas funções AWS Lambda, tarefas ECS e chamadas de bancos de dados) dentro de um fluxo de trabalho estruturado, visual e lógico (um workflow).

Objetivos de Aprendizado

Neste módulo, o foco central é dominar a orquestração de microsserviços. Ao final, você será capaz de:

  • Reconhecer os desafios e as dinâmicas de coordenar tarefas em aplicações distribuídas.
  • Descrever os recursos e a utilidade do AWS Step Functions.
  • Identificar os diferentes Tipos de Estado (State types) usados para construir o fluxo (como decisões, esperas e processamento paralelo).
  • Reconhecer os casos de uso mais comuns para implementar orquestração serverless.
  • Dominar as principais operações de API e a linguagem de definição do Step Functions.

O Cenário da Cafeteria (Orquestração de Relatórios Gerenciais)

Agora que a atualização do estoque de grãos de café foi automatizada com mensageria no Módulo 10, Frank solicitou relatórios gerenciais periódicos com os dados mais recentes do inventário. No entanto, a geração de um relatório completo exige que várias ações ocorram em uma ordem estrita e sequencialmente dependente.

Para resolver essa demanda, Sofía não escreverá uma função Lambda gigantesca, complexa e monolítica. Em vez disso, ela utilizará o AWS Step Functions para orquestrar as seguintes tarefas de forma limpa, desacoplada e coordenada:

  1. Buscar dados brutos no banco de dados relacional Amazon RDS (Aurora Serverless).
  2. Acionar uma função AWS Lambda para processar, filtrar e formatar esses dados em um relatório consolidado.
  3. Salvar o arquivo final do relatório em um bucket protegido do Amazon S3.
  4. Disparar uma notificação via Amazon SNS avisando a Frank que o relatório foi gerado e está pronto para download seguro via URL pré-assinada.
Step Functions na arquitetura da aplicação: orquestrando a busca de dados no RDS, processamento no Lambda, upload no S3 e notificação via SNS

2. Coordinating tasks in distributed applications

Quebrar uma aplicação gigantesca em pequenos microsserviços independentes (como funções AWS Lambda desacopladas) traz enormes vantagens competitivas: você consegue implantar, escalar e atualizar cada pedaço do sistema rapidamente. No entanto, essa arquitetura distribuída cria um novo e complexo desafio de coordenação.

Os Desafios do Crescimento em Aplicações Distribuídas

Conforme a aplicação evolui e o número de pequenas funções aumenta, a interação entre elas torna-se uma teia complexa de dependências. Surgem cenários críticos como:

  • Sequenciamento Estrito: Acionar a Função B apenas se a Função A for concluída com êxito, garantindo que o resultado de A seja passado como entrada para B.
  • Paralelismo (Fork/Join): Invocar duas ou mais funções pesadas ao mesmo tempo e só acionar uma terceira função quando todas as anteriores terminarem e seus resultados forem consolidados.
  • Lógica Condicional (Branching): Escolher dinamicamente entre rodar a Função C ou a Função D com base em parâmetros de negócio presentes na saída gerada pela Função A.
  • Pausas e Esperas (Timeouts): Aguardar uma resposta externa, aprovação manual de um operador humano ou pausar a execução por um tempo determinado antes do próximo passo.

O Problema das Falhas e Retentativas

Na nuvem, falhas transitórias acontecem o tempo todo: um serviço pode enfrentar lentidão temporária, uma função pode sofrer timeout ou estourar a memória (Out of Memory). Quando isso ocorre, o serviço que invocou a função geralmente realiza retentativas automáticas.

  • Por causa dessas retentativas, o código precisa ser desenhado para processar o mesmo evento repetidas vezes sem causar efeitos colaterais indesejados (como faturar duas vezes o mesmo cartão de crédito).
  • Gerenciar essas exceções, cronômetros de retentativa com exponential backoff e desvios de fluxo diretamente dentro do código das funções torna a aplicação frágil, difícil de auditar e propensa a loops infinitos.

A Necessidade de uma Camada de Coordenação Externa

Para resolver esse quebra-cabeça arquitetural, a melhor prática na AWS é nunca escrever a lógica de orquestração dentro do código da própria função (isso reacoplaria os microsserviços e geraria código espaguete).

É indispensável adotar uma Camada de Coordenação Externa dedicada, cuja função é:

  • Escalar automaticamente: Acompanhar flutuações de carga de trabalho sem necessidade de provisionamento de servidores.
  • Tratar erros e timeouts nativamente: Gerenciar retentativas configuráveis e blocos de contingência sem sobrecarregar a lógica de negócio.
  • Gerenciar o estado da aplicação: Rastrear com precisão em qual etapa cada execução se encontra, guardando a memória dos dados que transitam de um passo para o seguinte.
  • Fornecer visibilidade visual e rastreabilidade: Permitir que desenvolvedores e equipes de operações monitorem o fluxo graficamente em tempo real, simplificando o diagnóstico de falhas (troubleshooting).

Tabela Comparativa: Orquestração no Código vs. Camada Dedicada (Step Functions)

Critério Coordenação Embutida no Código (Ponto a Ponto) Camada de Coordenação Externa (Step Functions)
Acoplamento Forte acoplamento entre as funções Lambda Baixo acoplamento (funções são 100% independentes)
Tratamento de Erros Manual em cada função (blocos try/except complexos) Nativo, declarativo com Retry e Catch configuráveis
Gestão de Estado Exige salvar estado intermediário manualmente em banco (DynamoDB/S3) Automática: o serviço mantém o histórico completo e passa o payload JSON entre estados

Manutenibilidade Alterar a ordem dos passos exige alterar código de produção e reimplantar Alteração visual ou declarativa no JSON/ASL da máquina de estados

3. Introducing AWS Step Functions

O AWS Step Functions é o serviço serverless da AWS projetado especificamente para orquestração de workflows. Ele remove a responsabilidade de coordenação de dentro do seu código e a transforma em uma Máquina de Estados visual, modular e altamente gerenciável.

O Vocabulário Essencial do Step Functions (Foco em Certificação)

Para trabalhar com o Step Functions, quatro conceitos fundamentais formam a base de toda a arquitetura:

  • Máquina de Estados (State Machine): É o nome formal do seu fluxo de trabalho (workflow) completo. A máquina é uma coleção de estados interligados que tomam decisões e executam ações com base nas condições do passo anterior.
  • Estado (State): É um passo individual dentro da máquina de estados. Um estado recebe um payload de entrada em formato JSON (Input), executa sua lógica ou aguarda uma condição, e produz uma saída em formato JSON (Output) que é encaminhada para o próximo estado.
  • Tarefa (Task): É o tipo de estado que efetivamente realiza o trabalho pesado. Uma Task pode invocar uma função Lambda, rodar uma tarefa em contêiner no Amazon ECS, publicar em um tópico SNS, enfileirar no SQS ou interagir com mais de 200 serviços da AWS via API nativa (Optimized Integrations).
  • Transição (Transition): É a regra que define a movimentação da execução de um estado para o seguinte após a conclusão bem-sucedida do trabalho.

Como o Fluxo é Definido: Amazon States Language (ASL)

Você não programa o fluxo de estados em linguagens tradicionais como Python ou Java. As Máquinas de Estado do Step Functions são estruturadas utilizando a ASL (Amazon States Language), uma especificação declarativa baseada puramente em JSON.

Estrutura Básica de um JSON em ASL:

  • StartAt: Define obrigatoriamente qual é o primeiro estado que deve ser executado no início da máquina de estados.
  • States: Objeto que agrupa todos os estados individuais do fluxo.
  • Next: Especifica o nome do próximo estado que deve ser executado na sequência.
  • End: true: Sinaliza que aquele estado é terminal e encerra o workflow quando concluído. (Estados específicos do tipo Succeed ou Fail também finalizam a execução).

Dica Prática — Workflow Studio: Embora você possa escrever o código JSON em ASL manualmente, o console da AWS oferece o Workflow Studio, um construtor visual interativo onde você monta fluxos complexos arrastando e soltando blocos (drag-and-drop). O Workflow Studio gera a especificação ASL JSON automaticamente em tempo real.

Opções de Fluxo de Trabalho (Workflow Options)

Opções de construção de fluxos no Step Functions: Execução em sequência, processamento em paralelo, decisão condicional baseada em dados, blocos try-catch-finally e políticas de retentativa

O Step Functions disponibiliza padrões nativos de fluxo que eliminam milhares de linhas de código de controle:

  • Run tasks in sequence (Sequenciamento): O estado A executa uma tarefa e passa seu resultado diretamente para o estado B.
  • Run tasks in parallel (Processamento Paralelo): O estado Parallel executa múltiplos ramos de tarefas simultaneamente e só avança para o estado C quando todos os ramos forem concluídos com sucesso.
  • Select a task based on data (Decisão Condicional): O estado Choice inspeciona variáveis no JSON de entrada (ex: se status == "APPROVED") e desvia o fluxo para caminhos diferentes.
  • Manage try-catch-finally behavior (Tratamento de Exceções): O bloco Catch captura tipos específicos de erros e redireciona o fluxo para caminhos de contingência ou compensação.
  • Retry failed tasks (Políticas de Retentativa): O bloco Retry define regras automáticas de nova tentativa, permitindo configurar intervalo inicial, fator de multiplicação exponencial (BackoffRate) e número máximo de tentativas antes de considerar o passo como falho.

Os Grandes Benefícios da Arquitetura:
1. Tratamento de Erros Nativo: Se o banco de dados RDS sofrer uma instabilidade transitória, o Step Functions aplica a política de Retry automaticamente sem cancelar o fluxo e sem intervenção humana.
2. Gestão Total de Estado: O serviço mantém a trilha de auditoria completa da execução. É possível inspecionar visualmente o payload exato que entrou e saiu de cada estado individual, facilitando a depuração imediata de qualquer falha.

4. State types

A linguagem de definição da Máquina de Estados (Amazon States Language - ASL) usa a estrutura declarativa em JSON para configurar o comportamento e a transição de cada bloco do fluxo. Abaixo está o detalhamento completo dos 7 Tipos de Estados (State Types) com seus respectivos exemplos práticos em código JSON:

1. Task (A Tarefa)

É o estado que realmente executa o trabalho na máquina de estados. Uma Task pode invocar uma função AWS Lambda, acionar um contêiner no Amazon ECS ou fazer uma chamada de API diretamente para outros serviços gerenciados da AWS.

"LambdaState": { 
  "Type": "Task", 
  "Resource": "arn:aws:lambda:us-east-1:123456789012:function:HelloWorld", 
  "Next": "NextState" 
}

2. Choice (A Decisão / Ramificação)

Adiciona lógica condicional de ramificação (equivalente a uma estrutura if / else if / else). Ele inspeciona variáveis no payload de entrada (Input) comparando valores (numéricos, strings, booleanos ou timestamps) para decidir qual será o próximo estado executado.

"ChoiceState": {
  "Type": "Choice",
  "Choices": [
    {
      "Variable": "$.numerical_value",
      "NumericEquals": 1,
      "Next": "FirstBranchState"
    }
  ],
  "Default": "DefaultFallbackState"
}

3. Pass (O Passa-Fita / Injeção de Dados)

Passa a entrada (Input) diretamente para a saída (Output) sem realizar trabalho computacional externo. É extremamente útil para depuração (debugging), transformação de dados ou injeção de dados estáticos/fictícios (mock data) no fluxo durante testes.

"No-op": { 
  "Type": "Pass", 
  "Result": { 
    "x-datum": 0.381018,
    "y-datum": 622.2269926397355 
  },
  "ResultPath": "$.coords",
  "Next": "End" 
}

4. Wait (A Espera)

Atrasa propositalmente a execução do fluxo por um período determinado. A espera pode ser configurada por um intervalo relativo em segundos (Seconds ou SecondsPath) ou até um carimbo de data/hora absoluto (Timestamp ou TimestampPath).

"wait_ten_seconds": { 
  "Type": "Wait", 
  "Seconds": 10, 
  "Next": "NextState" 
}

5. Parallel (O Paralelismo)

Cria múltiplas ramificações independentes (Branches) que são disparadas e executadas simultaneamente. O estado Parallel como um todo só avança para o próximo passo quando todas as suas ramificações terminarem com sucesso. Se qualquer ramificação falhar e o erro não for capturado, o bloco inteiro falha.

"LookupCustomerInfo": { 
  "Type": "Parallel", 
  "Branches": [ 
    { 
      "StartAt": "PState1", 
      "States": { 
        "PState1": {"Type": "Task", "Resource": "...", "End": true} 
      } 
    }, 
    { 
      "StartAt": "PState2",
      "States": { 
        "PState2": {"Type": "Task", "Resource": "...", "End": true} 
      } 
    } 
  ], 
  "Next": "NextState" 
}

6. Map (A Iteração Dinâmica)

Executa dinamicamente os mesmos passos para cada item contido em um array (lista) fornecido no JSON de entrada. Se o array contiver 10 itens, ele criará até 10 execuções paralelas baseadas na definição interna do Iterator (ou ItemProcessor), controladas pelo parâmetro MaxConcurrency.

"Validate-All": { 
  "Type": "Map", 
  "InputPath": "$.detail", 
  "ItemsPath": "$.shipped", 
  "MaxConcurrency": 0, 
  "Iterator": { 
    "StartAt": "Validate", 
    "States": { 
      "Validate": { 
        "Type": "Task", 
        "Resource": "arn:aws:lambda:us-east-1:123456789012:function:ship-val",
        "End": true
      }  
    } 
  }, 
  "ResultPath": "$.detail.shipped", 
  "End": true 
}

7. Succeed & Fail (Os Estados Terminais)

Encerram imediatamente a execução da máquina de estados. Por serem estados terminais absolutos, nunca possuem nem exigem os campos Next ou End: true:

  • Succeed: Finaliza a execução inteira com status de sucesso limpo.
  • Fail: Interrompe a execução inteira com status de falha, podendo opcionalmente incluir os campos descritivos Error (código do erro) e Cause (motivo detalhado da falha) para fins de telemetria e diagnóstico.
"FailState": { 
  "Type": "Fail", 
  "Cause": "Invalid response.", 
  "Error": "ErrorA" 
}

"SuccessState": { 
  "Type": "Succeed" 
}

Quadro Resumo: Tipos de Estados no AWS Step Functions

Tipo de Estado Finalidade Principal Campos Chave (ASL) É Terminal?
Task Executar trabalho real (Lambda, ECS, APIs) Type: "Task", Resource, Parameters Não (a menos que End: true)
Choice Decisão e desvios condicionais (if/else) Type: "Choice", Choices, Variable, Default Não
Pass Passar dados adiante / Injetar dados estáticos Type: "Pass", Result, ResultPath Não (a menos que End: true)
Wait Atrasar o fluxo por tempo relativo ou data exata Type: "Wait", Seconds, Timestamp Não (a menos que End: true)
Parallel Executar ramificações simultâneas fixas Type: "Parallel", Branches Não (a menos que End: true)
Map Iterar dinamicamente sobre itens de um array Type: "Map", ItemsPath, Iterator, MaxConcurrency Não (a menos que End: true)
Succeed Encerrar o workflow com sucesso Type: "Succeed" Sim (sempre terminal)
Fail Encerrar o workflow com falha Type: "Fail", Error, Cause Sim (sempre terminal)

5. Step Functions use cases

Antes de iniciar uma Máquina de Estados, você deve escolher entre dois "Motores" de execução (Workflow Types). Embora a linguagem de definição (ASL JSON) seja idêntica, o comportamento de execução, a durabilidade e o modelo de cobrança mudam radicalmente:

1. Standard Workflows (O Padrão para Processos Críticos)

  • Finalidade: Projetado para fluxos de trabalho longos, auditáveis e de missão crítica que exigem histórico de execução detalhado e rastreabilidade passo a passo.
  • Duração Máxima: A execução pode permanecer ativa por até 1 ano.
  • Garantia de Execução: Opera estritamente no modelo "Exactly-once" (Exatamente uma vez). O Step Functions garante que nenhuma tarefa seja executada em duplicidade, a menos que você configure explicitamente uma política de Retry no JSON.
  • Modelo de Cobrança: Você paga por Transição de Estado (cada vez que a execução avança de um estado para o seguinte).
  • Casos de Uso Ideais: Processos de aprovação manual (RH, compras corporativas), orquestração pesada de pipelines de Machine Learning (SageMaker), checkout de pedidos de alto valor e faturamento empresarial.

2. Express Workflows (O Rápido para Alto Volume)

  • Finalidade: Projetado para processamento de eventos de altíssima velocidade e volumes massivos de dados em tempo real.
  • Duração Máxima: O fluxo possui um timeout rígido de no máximo 5 minutos.
  • Garantia de Execução: Opera no modelo "At-least-once" (Pelo menos uma vez) em execuções assíncronas ou "At-most-once" (No máximo uma vez) em execuções síncronas. O código consumidor deve ser idempotente.
  • Modelo de Cobrança: Você não paga por transição. A cobrança é calculada pelo tempo de execução em milissegundos e pela quantidade de memória consumida (modelo idêntico ao AWS Lambda).
  • Casos de Uso Ideais: Ingestão massiva de telemetria IoT (milhares de mensagens por segundo), processamento de cliques em streaming (clickstream), transformação rápida de dados de APIs e microsserviços de alta escala.

Tabela Comparativa: Standard Workflows vs. Express Workflows

Característica Standard Workflows Express Workflows
Duração Máxima Até 1 ano Até 5 minutos
Semântica de Execução Exactly-once (Exatamente uma vez) At-least-once (Assíncrono) ou At-most-once (Síncrono)
Modelo de Cobrança Por Transição de Estado Por duração (ms) e memória consumida
Taxa de Execução (Throughput) Até ~2.000 execuções/segundo Mais de 100.000 execuções/segundo
Histórico de Auditoria Histórico completo gravado visualmente no Console por até 90 dias Enviado para o Amazon CloudWatch Logs
Aprovação Manual / Pausa Longa Sim (suporta Task Tokens por meses) Não (limitado a 5 minutos)

Aprovação Manual e Sistemas Externos (Task Tokens & Activities)

O Step Functions se destaca ao permitir pausar automações complexas e aguardar uma decisão humana ou a resposta de um sistema legado externo:

Como Funciona o Padrão "Aprovação do Gerente" com Task Token:

  1. O workflow alcança uma tarefa configurada com o padrão .waitForTaskToken (ex: "Aguardar Aprovação de Crédito").
  2. Em vez de executar e avançar imediatamente, o Step Functions pausa a máquina de estados e gera um taskToken exclusivo (um identificador longo e criptograficamente seguro).
  3. Uma função Lambda recebe esse token e envia um e-mail com botões interativos para o gestor responsável (o link de aprovação embute o taskToken).
  4. O Step Functions fica "congelado", em estado dormente, sem cobrar nada por tempo ocioso (podendo esperar por dias ou até 1 ano no fluxo Standard).
  5. Dias depois, o gerente abre o e-mail e clica em "Aprovar". Isso dispara uma requisição HTTP para o backend.
  6. O backend invoca a API do Step Functions emitindo o comando SendTaskSuccess (ou SendTaskFailure) passando o taskToken e o payload de aprovação.
  7. O Step Functions valida o token, "acorda" a máquina de estados na mesma hora e dá continuidade ao fluxo pelo ramo correspondente.

Nota Prática — Activity Workers: A mesma lógica de token é aplicada quando você registra uma Activity executada em instâncias EC2 ou servidores locais (on-premises). O servidor atua como um Activity Worker, sondando periodicamente a tarefa via chamada GetActivityTask, processando a atividade pesada no seu tempo e devolvendo o status final via SendTaskSuccess. Isso desacopla totalmente a infraestrutura de computação do orquestrador.

6. Step Functions API

A interação programática com o AWS Step Functions ocorre por meio dos AWS SDKs (como Boto3 em Python ou SDK para JavaScript/TypeScript) ou chamadas diretas de API REST. Conhecer as operações fundamentais é indispensável para acionar e monitorar fluxos diretamente do código da aplicação.

Principais Operações de API

  • CreateStateMachine: Cria ou atualiza a definição em ASL JSON da Máquina de Estados, associando sua IAM Role de execução.
  • StartExecution: Dispara uma nova instância do fluxo de trabalho. Aceita um payload JSON de entrada (Input) e retorna o Execution ARN exclusivo que identifica aquela execução específica.
  • StopExecution: Interrompe forçadamente uma execução em andamento, registrando o carimbo de data/hora exato e a causa da parada.
  • GetExecutionHistory: Retorna o histórico de eventos detalhado e ordenado da execução (fundamental para auditoria, observabilidade e depuração automatizada).
  • ListStateMachines / DescribeStateMachine: Listam as máquinas criadas na conta e inspecionam sua definição ASL atual.
  • SendTaskSuccess / SendTaskFailure: Envia o sinal de retorno com dados para destravar um estado pausado aguardando um taskToken.

Gatilhos de Execução (Padrões de Integração Clássicos)

Em arquiteturas modernas Serverless, as máquinas de estado raramente são iniciadas manualmente. Os dois gatilhos mais comuns e cobrados em certificações são:

  • Amazon API Gateway (Acionamento Síncrono/Assíncrono via REST): Você configura uma rota de API (ex: POST /pedidos) integrada diretamente ao Step Functions chamando a ação StartExecution. O cliente faz uma chamada HTTPS e a máquina de estados inicia instantaneamente.
  • Amazon EventBridge / CloudWatch Events (Acionamento Orientado a Eventos ou Agendado):
    • Agendamento Periódico (Cron): Dispara o fluxo em horários programados (ex: gerar o relatório de estoque da cafeteria toda segunda-feira às 08:00).
    • Eventos de Nuvem: Inicia o fluxo automaticamente em reação a alterações de recursos na AWS (ex: um arquivo chega ao S3 ou uma instância muda de estado).

Cotas de Serviço e Throttling (Quotas): Para proteger a conta contra loops infinitos ou gastos descontrolados por erros de lógica, a AWS aplica cotas rígidas de taxa de chamada de API e de concorrência. É crítico lembrar que os limites de taxa de inicialização e transições são moderados para Standard Workflows e extraordinariamente elevados para Express Workflows (capazes de sustentar picos maciços de eventos em tempo real).

Lab 11.1: Orchestrating Serverless Functions with Step Functions

Visão Geral e Objetivos do Laboratório

Neste laboratório prático, você usará o AWS Step Functions para coordenar as ações necessárias para gerar e entregar relatórios gerenciais sob demanda. O relatório consolidará registros reais de estoque armazenados em um banco de dados relacional e será entregue com segurança ao solicitante através de links pré-assinados do Amazon S3.

Depois de concluir este laboratório, você será capaz de:

  • Criar e configurar uma máquina de estados no AWS Step Functions utilizando o Workflow Studio e a Amazon States Language (ASL).
  • Configurar um tópico do Amazon Simple Notification Service (Amazon SNS) para enviar notificações de e-mail automatizadas com URLs temporárias.
  • Configurar funções do AWS Lambda em Python e Node.js para serem invocadas sequencialmente e em paralelo a partir da máquina de estados.
  • Implementar um estado do tipo Parallel no design do workflow para executar tarefas simultâneas (geração de HTML e geração de URL pré-assinada).
  • Integrar e invocar uma máquina de estados diretamente a partir de um endpoint REST do Amazon API Gateway utilizando modelos de mapeamento (Mapping Templates).
  • Configurar uma função Lambda conectada à Amazon VPC privada para consultar com segurança uma instância do Amazon Aurora Serverless (MySQL).
  • Gerar URLs pré-assinadas (Presigned URLs) temporárias para proteger arquivos restritos hospedados em buckets do Amazon S3.

Duração e Restrições de Serviço

  • Duração estimada: Aproximadamente 90 minutos.
  • Restrições de serviço: O acesso aos serviços da AWS neste ambiente é limitado aos recursos estritamente necessários para a conclusão das instruções do laboratório (Step Functions, Lambda, API Gateway, SNS, S3, RDS Aurora, VPC e IAM).

Cenário da Cafeteria

Graças ao sistema de mensageria implementado no laboratório anterior, o estoque de grãos de café agora é atualizado automaticamente. Contudo, Frank pediu a Sofía uma forma rápida de solicitar um relatório gerencial consolidado com os dados mais recentes do inventário.

Mateo, consultor da AWS e cliente regular da cafeteria, sugeriu a criação de um mecanismo baseado no AWS Step Functions para orquestrar as tarefas de forma desacoplada:

  1. O usuário solicita o relatório acionando um endpoint REST no Amazon API Gateway.
  2. O API Gateway inicia a execução da Máquina de Estados no Step Functions.
  3. A máquina de estados invoca a função Lambda generateReportData, que se conecta com segurança ao Amazon RDS Aurora Serverless dentro da VPC privada para consultar os fornecedores e tipos de grãos.
  4. A máquina de estados dispara um estado Parallel que executa simultaneamente:
    • A função Lambda generateHTML, que monta o relatório visual e faz o upload de report.html no Amazon S3.
    • A função Lambda GeneratePresignedURL, que gera uma URL pré-assinada de acesso temporário restrito para o arquivo no S3.
  5. A máquina de estados publica a URL pré-assinada gerada em um tópico do Amazon SNS.
  6. Frank recebe um e-mail com a URL pré-assinada segura e consegue visualizar o relatório no navegador antes que o link expire.

Evolução da Arquitetura do Laboratório

1. Arquitetura Inicial (Endpoint Simulado):

Arquitetura Inicial: API Gateway com endpoint mockado e recursos isolados ainda não integrados

2. Arquitetura Final (Orquestração Serverless Completa):

Arquitetura Final: API Gateway $\rightarrow$ Step Functions $\rightarrow$ Lambda (RDS) $\rightarrow$ Parallel [Lambda (S3) || Lambda (Presigned URL)] $\rightarrow$ SNS $\rightarrow$ E-mail para Frank
Etapa Componente Ação Executada
1 API Gateway (create_report) Frank solicita o relatório via POST; a API dispara a execução da Máquina de Estados no Step Functions.
2 Lambda (generateReportData) Consulta as tabelas suppliers e beans no banco de dados MySQL hospedado no Amazon RDS Aurora Serverless.
3 Estado Paralelo (Process Report) Inicia duas funções Lambda para execução simultânea, reduzindo a latência total do fluxo.
4 Lambda (generateHTML) Transforma os dados JSON em página HTML estilizada e faz upload do arquivo report.html para o bucket do Amazon S3.
5 Lambda (GeneratePresignedURL) Gera uma URL pré-assinada criptografada com validade de 1 hora para download seguro do relatório no S3.
6 Amazon SNS $\rightarrow$ E-mail Publica a URL pré-assinada no tópico do SNS; Frank recebe a notificação por e-mail e acessa o relatório protegido.

Tarefa 4: Criação de Função Lambda para Gerar Presigned URLs

Nesta tarefa, você cria um arquivo HTML de relatório no S3, analisa como a política de bucket restringe o acesso direto e desenvolve uma função Lambda em Python para gerar links assinados temporários.

1. Criar e subir o arquivo de exemplo no S3:

No VS Code IDE, crie o arquivo report.html com o conteúdo:

<output>Hello! This is some sample HTML.</output>

Faça o upload para o bucket S3 configurando cache-control max-age=0:

bucket=$(aws s3api list-buckets --query "Buckets[].Name" | grep s3bucket | tr -d ',' | sed -e 's/"//g' | xargs)
aws s3 cp report.html s3://$bucket/ --cache-control "max-age=0"

2. Análise da Política do Bucket (Acesso Restrito):

No console do S3, veja que a política do bucket possui uma regra explícita de negação (Deny) para acesso direto:

{
    "Sid": "DenyOneObjectIfRequestNotSigned",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::<BUCKET_NAME>/report.html",
    "Condition": {
        "StringNotEquals": {
            "s3:authtype": "REST-QUERY-STRING"
        }
    }
}

Por que dá AccessDenied no acesso comum? A condição StringNotEquals: {"s3:authtype": "REST-QUERY-STRING"} bloqueia qualquer requisição HTTP tradicional. O objeto report.html só pode ser lido se a requisição contiver parâmetros de autenticação pré-assinada na query string!

3. Teste via AWS CLI (Presign):

Gere uma URL pré-assinada temporária válida por apenas 30 segundos:

aws s3 presign s3://$bucket/report.html --expires-in 30

Abra a URL gerada no navegador: o HTML é exibido perfeitamente. Aguarde 30 segundos, atualize a página e comprove que o acesso passa a retornar AccessDenied por expiração do token.

4. Criação da Função Lambda GeneratePresignedURL:

  • No console do AWS Lambda, crie uma função com:
    • Nome: GeneratePresignedURL.
    • Runtime: Python 3.9.
    • Role: RoleForAllLambdas.
  • Substitua o código por: 
    import logging
import boto3
from botocore.exceptions import ClientError

s3_client = boto3.client('s3')

def lambda_handler(event, context):
    bucket_name = "SEU_BUCKET_NAME_AQUI"
    object_name = "report.html"
    expiration_in_seconds = 120

    try:
        presigned_url_str = s3_client.generate_presigned_url(
            'get_object',
            Params={'Bucket': bucket_name, 'Key': object_name},
            ExpiresIn=expiration_in_seconds
        )
        response = { "presigned_url_str": presigned_url_str }
    except ClientError as e:
        logging.error(e)
        return None

    return response
  • Substitua SEU_BUCKET_NAME_AQUI pelo nome real do seu bucket (que possui -s3bucket no nome), clique em Deploy e teste com o evento padrão test1 para confirmar que o JSON retorna a URL pré-assinada.

5. Incluir a Função Lambda no Step Functions:

  1. No Workflow Studio de MyStateMachine, arraste a ação AWS Lambda Invoke para ficar logo acima do estado SNS Publish.
  2. Configure o estado:
    • State name: GeneratePresignedURL.
    • Function name: GeneratePresignedURL:$LATEST.
    • Payload: Nenhuma carga útil.
    • Next state: SNS Publish.
  3. Salve as alterações e execute a máquina de estados passando {} como entrada. Verifique seu e-mail: você receberá um link temporário funcional para ler o relatório!

Tarefa 6: Função Lambda generateHTML para Formatação Visual

Crie uma função em Node.js responsável por transformar os dados brutos de fornecedores e cafés em uma página HTML formatada profissionalmente com CSS inline e salvá-la no S3.

  1. No console do AWS Lambda, crie a função:
    • Nome: generateHTML.
    • Runtime: Node.js 20.x.
    • Role: RoleForAllLambdas.
    • Timeout: Ajuste para 2 minutos em Configuração Geral.
  2. No editor de código, insira o script completo que lê o array my_json_arr, monta as seções com createHTML(), grava o arquivo no S3 via PutObjectCommand e gera uma URL pré-assinada com validade de 1 hora (3600 segundos): 
    import { S3Client, PutObjectCommand, GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const BUCKET_NAME_STR = "SEU_BUCKET_NAME_AQUI";
const s3Client = new S3Client({ apiVersion: "2006-03-01" });

export const handler = async (event) => {
    let parsedEvent;
    try {
        const firstLevelParse = typeof event === 'string' ? JSON.parse(event) : event;
        if (firstLevelParse.body) {
            parsedEvent = typeof firstLevelParse.body === 'string'
                ? JSON.parse(firstLevelParse.body)
                : firstLevelParse.body;
        } else {
            parsedEvent = firstLevelParse;
        }

        if (typeof parsedEvent.my_json_arr === 'string') {
            parsedEvent.my_json_arr = JSON.parse(parsedEvent.my_json_arr);
        }

        if (!Array.isArray(parsedEvent.my_json_arr)) {
            throw new TypeError('Expected my_json_arr to be an array, but got ' + typeof parsedEvent.my_json_arr);
        }

        // Geração e upload do relatório HTML para o S3
        const htmlContent = await createHTML(parsedEvent);
        await writeReport(htmlContent);

        // Geração da URL pré-assinada
        const presignedUrl = await generatePresignedUrl();

        return {
            "msg_str": "Report published to S3",
            "presigned_url_str": presignedUrl
        };
    } catch (error) {
        console.error('Error processing event:', error);
        throw new Error(`Failed to process event: ${error.message}`);
    }
};

async function writeReport(html_str) {
    const params = {
        Bucket: BUCKET_NAME_STR,
        Key: "report.html",
        Body: html_str,
        CacheControl: "max-age=0",
        ContentType: "text/html"
    };
    const command = new PutObjectCommand(params);
    await s3Client.send(command);
}

async function generatePresignedUrl() {
    const command = new GetObjectCommand({
        Bucket: BUCKET_NAME_STR,
        Key: "report.html"
    });
    return await getSignedUrl(s3Client, command, { expiresIn: 3600 });
}
  3. Substitua as ocorrências de SEU_BUCKET_NAME_AQUI pelo nome do seu bucket S3, clique em Deploy e teste com o evento test2 contendo registros fictícios de fornecedores. A função responderá com {"msg_str": "Report published to S3"}.

Tarefa 8: Lambda generateReportData Conectada à VPC (MySQL no RDS)

Crie a função Lambda responsável por consultar os dados reais de fornecedores e estoques no banco de dados relacional Amazon Aurora Serverless localizado em uma sub-rede privada da VPC.

  1. No console do Amazon RDS, selecione o banco de dados supplierdb e copie o endereço do Writer Endpoint (Endpoint de Gravação).
  2. No terminal do VS Code IDE, crie a pasta lambda com os arquivos de dependência: 
    mkdir -p ~/environment/lambda && cd ~/environment/lambda
  3. Crie o arquivo package.json: 
    {
    "dependencies": {
        "mysql2": "*",
        "@aws-sdk/client-s3": "*"
    },
    "type": "module"
}
  4. Crie o arquivo index.js substituindo DB-ENDPOINT pelo endpoint do seu Aurora RDS: 
    import { S3Client } from '@aws-sdk/client-s3';
import mysql from 'mysql2/promise';

const s3Client = new S3Client({ region: "us-east-1" });

export const handler = async (event, context) => {
    try {
        const connection = await mysql.createConnection({
            host: 'DB-ENDPOINT',
            user: 'nodeapp',
            password: 'coffee',
            database: 'COFFEE'
        });

        const [suppliers] = await connection.query('SELECT * FROM suppliers');
        const [beans] = await connection.query('SELECT * FROM beans');
        await connection.end();

        const mergedData = mergeData(suppliers, beans);

        return {
            statusCode: 200,
            body: JSON.stringify({
                my_json_arr: mergedData
            })
        };
    } catch (err) {
        console.error("Error executing query:", err);
        return {
            statusCode: 500,
            body: JSON.stringify({ error: err.message })
        };
    }
};

function mergeData(suppliers_arr, beans_arr) {
    const fine_tunes_data_arr = [];
    for (const supplier of suppliers_arr) {
        const o = {
            suppliers_id_int: supplier.id,
            supplier_name_str: supplier.name,
            supplier_address_str: supplier.address,
            supplier_phone_str: supplier.phone,
            bean_info_obj_arr: []
        };
        for (const bean of beans_arr) {
            if (supplier.id === bean.supplier_id) {
                o.bean_info_obj_arr.push({
                    type_str: bean.type,
                    product_name_str: bean.product_name,
                    quantity_int: bean.quantity,
                    price_int_str: bean.price ? bean.price.toString() : "15.00"
                });
            }
        }
        fine_tunes_data_arr.push(o);
    }
    return fine_tunes_data_arr;
}
  5. Instale as dependências com npm install e compacte o pacote:

zip -r ../lambda.zip *
  6. No console do AWS Lambda, crie a função:

      • Security Group: Selecione o grupo que contém ClusterSecurityGroup.
