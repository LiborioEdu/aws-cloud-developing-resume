9. Caching Information for Scalability

1. Introduction

Na nuvem, tempo é dinheiro e latência é perda de clientes. A solução definitiva para isso é o uso estratégico de Cache (armazenamento temporário de dados de acesso ultrarrápido).

Objetivos de Aprendizado

Ao final deste módulo, você estará preparado para dominar os seguintes temas vitais para arquitetura de sistemas escaláveis e de alta performance na AWS:

  • Cenários e Padrões de Uso de Cache: Entender os cenários exatos de quando e onde utilizar cache em uma arquitetura distribuída na nuvem.
  • Amazon ElastiCache: Trabalhar com o serviço gerenciado focado em cache de banco de dados e armazenamento em memória RAM (motores Memcached e Redis).
  • Amazon CloudFront: Trabalhar com a CDN global da AWS focada em cache de rede, aceleração de tráfego web e terminação criptográfica segura.
  • Computação na Borda (Edge Computing): Descrever, analisar e comparar tecnologias de processamento na borda da rede: Lambda@Edge e CloudFront Functions.
  • Estratégias de Invalidação e Atualização: Aplicar as melhores estratégias de invalidação, controle de TTL (Time To Live) e atualização de cache para mitigar dados obsoletos (stale data).

O Caso da Cafeteria (O Problema de Performance)

Com o estrondoso sucesso e popularização do site da cafeteria, um novo problema de escala surgiu: os clientes começaram a reclamar publicamente que a página de "Estoque de Grãos de Café" está demorando muito para carregar.

Além da lentidão no catálogo de grãos, a desenvolvedora Sofía precisa garantir um requisito essencial de governança e segurança na nuvem: fazer com que todo o site da cafeteria opere de forma criptografada e segura utilizando o protocolo HTTPS.

A Solução em Duas Frentes (A Arquitetura)

Para resolver a lentidão e atender aos requisitos de segurança simultaneamente, a arquiteta consultora Olivia e Sofía dividirão a arquitetura de cache em duas camadas estratégicas:

  1. No Back-end (Camada de Banco de Dados):

    O site demora porque toda vez que alguém abre a página, a função Lambda precisa realizar uma consulta pesada e repetitiva no banco de dados relacional para listar os grãos. A solução definitiva será posicionar o Amazon ElastiCache (usando o motor Memcached) na frente do banco de dados para guardar temporariamente em memória RAM o resultado dessa lista de grãos já consultada, aliviando o banco de dados e respondendo em microssegundos.

  2. No Front-end (Camada de Rede / Site):

    Para resolver o carregamento lento das imagens, arquivos HTML, CSS e JavaScript hospedados no Amazon S3, e para ativar a criptografia HTTPS global com certificados SSL/TLS sem onerar o bucket de origem, elas utilizarão o Amazon CloudFront, a CDN (Content Delivery Network - Rede de Entrega de Conteúdo) de alta velocidade da AWS com presença em centenas de pontos de borda (Edge Locations) ao redor do mundo.

Resumo Arquitetural da Solução da Cafeteria:
• Borda / Rede (CloudFront): Cache dos arquivos estáticos do S3 + Terminação segura HTTPS.
• Aplicação / Banco (ElastiCache Memcached): Cache em memória RAM da listagem de grãos entre o Lambda e o banco de dados.

2. Caching overview

Com o crescimento exponencial das aplicações modernas (escala global, dispositivos IoT, jogos em tempo real e microsserviços), a exigência sobre a infraestrutura de dados aumentou drasticamente. Não basta mais apenas entregar o dado; é fundamental entregá-lo em microssegundos.

O que é Caching?

Em termos simples, Caching é o ato de atender a uma requisição computacional usando uma cópia temporária e de altíssima velocidade de um dado, em vez de buscar o dado original diretamente na fonte persistente (como um banco de dados relacional em disco ou um servidor raiz).

Uma estratégia de cache se apoia em três conceitos fundamentais:

  • O Cache: É a cópia rápida e temporária mantida em um meio de armazenamento volátil de baixa latência (como memória RAM).
  • A Origem (Origin): É a fonte verdadeira, canônica e persistente dos dados (o banco de dados primário, cluster Aurora, servidor web ou bucket S3).
  • Tempo de Vida (TTL - Time To Live): Como os dados no cache são temporários, eles recebem uma "data de validade" (TTL) para garantir que não fiquem desatualizados (obsoletos) para sempre. Ao expirar o TTL, a próxima requisição força a busca do dado renovado na origem.

Onde o Cache Pode Ser Implementado?

O cache não é uma tecnologia isolada, mas uma estratégia que pode (e deve) ser implementada em todas as camadas de um sistema moderno:

  • No Cliente: No navegador web ou aplicativo mobile do usuário, controlado via cabeçalhos HTTP (ex: Cache-Control, Expires, ETag).
  • Na Rede / Entrega: Em Redes de Entrega de Conteúdo (CDN) distribuídas globalmente, como o Amazon CloudFront.
  • No Back-end / Banco de Dados: Em bancos de dados em memória posicionados na frente de bases relacionais e não relacionais, como o Amazon ElastiCache (Redis e Memcached) e o DynamoDB Accelerator (DAX).

Quando Usar Cache? (As Perguntas de Ouro)

Decidir se você deve ou não usar cache em sua arquitetura exige responder a quatro perguntas fundamentais:

  1. A consulta original é lenta e cara?

    Se o banco de dados precisa juntar (JOIN) várias tabelas complexas, calcular somas analíticas ou varrer milhões de registros para gerar um relatório, o processo será demorado e consumirá muito processamento de CPU e I/O. Guardar o resultado final no cache economiza tempo, ciclos de máquina e dinheiro.

  2. O dado é estático e muito acessado?

    Não faz sentido colocar em cache um dado que muda a cada segundo ou que é lido apenas uma vez por mês. O candidato ideal para o cache é um dado que muda pouco, mas que é acessado milhares de vezes por minuto (padrão Read-Heavy, como o perfil público de um usuário ou o catálogo de grãos da cafeteria).

  3. A aplicação tolera dados "velhos" (Stale Data)?

    Por definição, qualquer dado lido do cache é um dado "desatualizado" em relação à origem primária. Se você está mostrando a cotação de moedas para um usuário comum ou o saldo aproximado de pontos, um atraso de 1 minuto é perfeitamente aceitável. Se a tela for para um corretor executando uma compra milionária de ações na bolsa, o dado precisa ser estritamente em tempo real (direto da origem).

  4. Vale a pena o custo e a complexidade?

    Manter um cluster de cache adiciona custos de infraestrutura provisionada e aumenta sensivelmente a complexidade do código da aplicação (lógica de sincronização, expiração de chaves e tratamento de falhas). A regra geral de arquitetura é: não otimize cedo demais. Construa a aplicação, monitore os gargalos em produção e, então, aplique o cache onde ele realmente fará diferença.

Pontos-Chave (Key Takeaways):
• Proteção da Origem: O Cache serve requisições usando cópias rápidas em memória, protegendo a origem persistente de sobrecargas e picos de tráfego.
• Cenários Ideais: É ideal para aplicações com volume intenso de leitura (Read-Heavy) e cálculos computacionais pesados (Compute-Intensive).
• Defesa em Profundidade: Pode ser aplicado em múltiplas camadas do sistema simultaneamente (Cliente → CDN → API → Banco de Dados).

3. Caching with ElastiCache

O Amazon ElastiCache é a resposta totalmente gerenciada da AWS para bancos de dados que não dão conta do volume massivo de leitura ou para aplicações que precisam responder com latência estrita em sub-milissegundos. O segredo de sua velocidade vertiginosa reside no armazenamento dos dados diretamente na memória RAM, e não no disco rígido ou SSD.

O ElastiCache é um serviço gerenciado (a AWS é responsável pelo provisionamento de hardware, detecção de falhas, aplicação de patches e backups automáticos). Ao criar um cluster no ElastiCache, o arquiteto ou desenvolvedor precisa tomar a decisão técnica mais importante de todo o projeto: escolher o "Motor" (Engine) de cache.

A Grande Escolha: Memcached vs. Redis (Foco de Prova AWS)

O Amazon ElastiCache oferece suporte a dois motores de código aberto consagrados no mercado, cada um projetado para filosofias e casos de uso distintos:

1. ElastiCache for Memcached: A Palavra de Ordem é Simplicidade
• Características Arquiteturais: É uma engine multithreaded (capaz de utilizar múltiplos núcleos de processamento de CPU em uma única instância), exige baixíssima manutenção operacional e escala horizontalmente com extrema facilidade através da adição de nós ao cluster.
• O que Guarda: Armazena exclusivamente dados simples e planos (flat strings / formato chave-valor simples), como páginas HTML renderizadas inteiras ou fragmentos serializados de arquivos JSON.
• Quando Usar: Quando você precisa do modelo de cache mais simples, leve e rápido possível, e não se importa se perder os dados caso o nó desligue ou seja reiniciado (o Memcached é 100% volátil e não possui nenhum mecanismo de persistência em disco).
2. ElastiCache for Redis: A Palavra de Ordem é Poder Avançado
• Características Arquiteturais: Suporta persistência de dados (se o nó cair ou for reiniciado, os dados não somem, sendo recuperados via snapshots RDB ou logs de comandos AOF), suporte a replicação de alta disponibilidade (Multi-AZ) com failover automático e réplicas de leitura.
• O que Guarda: Manipula nativamente estruturas e tipos de dados complexos (Listas, Hashes, Sets, Sorted Sets para placares/leaderboards, Bitmaps, HyperLogLogs e Geospatial). Opera verdadeiramente como um banco de dados relacional/NoSQL completo em memória.
• Recurso Extra de Mensageria: Possui sistema nativo de mensageria Pub/Sub (Publish/Subscribe), amplamente adotado em salas de chat, mecanismos de streaming e notificações reativas em tempo real.
• Quando Usar: Quando sua aplicação exige durabilidade e persistência dos dados no cache, manipulação de estruturas de dados complexas sem serialização/desserialização no cliente, ou alta disponibilidade contínua sem risco de perda de sessão.

Tabela Comparativa: Memcached vs. Redis

Recurso / Critério Amazon ElastiCache for Memcached Amazon ElastiCache for Redis
Filosofia Principal Simplicidade e velocidade pura para chave-valor Recursos avançados e estruturas complexas em memória
Modelo de Concorrência Multithread (escala com múltiplos cores de CPU) Single-thread para comandos (Multithread para I/O auxiliar)
Tipos de Dados Apenas Strings planas e objetos serializados Strings, Hashes, Lists, Sets, Sorted Sets, Bitmaps, Geo

Pub/Sub e Mensageria Não suportado Suportado nativamente (Publish/Subscribe)
Backup e Restauração Não suportado Suportado (exportação/importação para Amazon S3)

Vocabulário Básico da Arquitetura do ElastiCache

Para projetar e dimensionar clusters no ElastiCache, é fundamental dominar três conceitos de infraestrutura:

  • Node (Nó): É a máquina virtual isolada subjacente; representa um "bloco alocado" de memória RAM rodando em uma rede VPC privada com sua própria CPU e endereçamento de rede. É a menor unidade fundamental de construção do ElastiCache.
  • Cluster: É o agrupamento lógico de gerenciamento de um ou mais Nós de cache. No caso do Memcached, o cluster particiona os dados horizontalmente entre até 20 nós distribuídos.
  • Especificidade do Redis (Shards e Réplicas): O Redis estrutura nós em unidades chamadas Shards (partições). Cada Shard contém 1 nó primário (responsável por receber comandos de gravação e leitura) e de zero a 5 nós de réplica somente leitura (read-replicas) posicionados em diferentes Zonas de Disponibilidade. Um cluster Redis avançado pode conter dezenas de Shards agrupando centenas de nós.

A Lógica do Código: O Fluxo de Acesso e a Penalidade do Cache Miss

Como desenvolvedor, quando você posiciona o ElastiCache na frente de uma base de dados persistente (como Amazon RDS, Aurora ou DynamoDB), sua aplicação deve implementar explicitamente a seguinte lógica de consulta:

  1. A aplicação recebe uma solicitação e pergunta primeiro ao ElastiCache: "Você tem o resultado da chave 'Lista_de_Graos'?"
  2. Cenário A — Cache Hit (Acerto no Cache):
    O ElastiCache responde instantaneamente: "Sim, o dado está em memória!" e devolve o valor em sub-milissegundos. A requisição é concluída com sucesso imediatamente, sem consumir nenhum recurso do banco de dados relacional.
  3. Cenário B — Cache Miss (Falha / Dado Ausente):
    O ElastiCache responde: "Não, o dado não existe nesta chave ou o tempo de validade (TTL) expirou".
A Penalidade do Cache Miss (The Cache Miss Penalty):
Quando ocorre um Cache Miss, a aplicação não economiza tempo; na verdade, ela sofre uma penalidade cumulativa de três viagens de rede obrigatórias:

1. Primeira Viagem: A aplicação perdeu preciosos milissegundos enviando uma requisição de consulta ao ElastiCache apenas para descobrir que o dado não estava lá.
2. Segunda Viagem: A aplicação é forçada a recorrer à fonte primária e lenta, executando a query pesada no disco do banco de dados (Amazon RDS/Aurora).
3. Terceira Viagem: A aplicação precisa enviar uma nova requisição de gravação ao ElastiCache para armazenar o dado recém-consultado na memória RAM, garantindo que a próxima requisição encontre um Cache Hit.

Alerta de Engenharia: Se a configuração de expiração (TTL - Time To Live) for configurada com um tempo curto demais, o sistema sofrerá Cache Misses em cascata. Isso degrada o throughput global, aumenta a latência média para os usuários e anula completamente os benefícios de performance que a camada de cache deveria proporcionar!

Decisão Arquitetural: Por que NÃO usar cache local na instância EC2?
Seria possível instalar um software de cache diretamente no sistema operacional da instância EC2 que hospeda os contêineres. No entanto, Olivia explicou por que essa abordagem é inadequada para produção na nuvem:
1. Sem Tolerância a Falhas: Se a instância EC2 for encerrada, sofrer falha ou for reciclada pelo Auto Scaling, todos os dados em cache são instantaneamente perdidos.
2. Inconsistência no Auto Scaling: Quando o Beanstalk adiciona novas instâncias EC2, cada instância começa com um cache "frio" e isolado, duplicando consultas ao banco de dados.
3. Sobrecarga Operacional: A equipe da cafeteria teria que gerenciar manualmente instalação, patches de segurança, particionamento de memória e monitoramento.
4. A Escolha Gerenciada: O Amazon ElastiCache desacopla a camada de cache em um cluster autônomo, elástico, monitorado pela AWS e compartilhável por todas as instâncias da aplicação.

O script update_item.py demonstra a estratégia de Cache Eviction: sempre que um UPDATE é executado na origem, a chave no Memcached é imediatamente expurgada.

  1. Abra o arquivo python_3/update_item.py no VS Code:

# Invalida explicitamente a chave no cache
memcached_call = memcached_client.delete('all_beans')
  2. Preencha os endpoints <FMI_1> e <FMI_2>, salve o arquivo e execute: 
    python3 update_item.py

    Saída esperada:

4. Caching with CloudFront

O Amazon CloudFront é a Content Delivery Network (CDN) global e gerenciada da AWS, projetada para distribuir conteúdos estáticos (HTML, CSS, imagens, arquivos JS), conteúdos dinâmicos, vídeos sob demanda e transmissões ao vivo com latência mínima, alta segurança e roteamento otimizado através de centenas de Pontos de Presença (Edge Locations) espalhados pelo mundo.

Acelerador de Transferência do Amazon S3 (S3 Transfer Acceleration)

O Amazon CloudFront não serve apenas para entregar conteúdo aos usuários que navegam no site (leitura e download); a infraestrutura global da CDN também é utilizada para acelerar drasticamente o envio (upload) de arquivos pesados para a nuvem da AWS através do recurso S3 Transfer Acceleration.

  • O Problema da Internet Pública: Se um cliente corporativo ou aplicativo no Japão tentar fazer o upload de um arquivo volumoso de 10 GB diretamente para um bucket Amazon S3 localizado em uma Região nos Estados Unidos (ex: us-east-1), os pacotes de dados terão que percorrer milhares de quilômetros pela internet pública. Ao atravessar múltiplos roteadores de provedores terceirizados não confiáveis, o upload sofrerá com altíssima latência, oscilações de banda e elevado risco de perda e retransmissão de pacotes.
  • A Solução com CloudFront: Com o S3 Transfer Acceleration habilitado, o cliente no Japão não envia o arquivo diretamente para os EUA; ele faz o upload para a Edge Location do CloudFront mais próxima, localizada em Tóquio. Assim que os dados alcançam a borda da AWS em Tóquio, o tráfego é roteado até o bucket S3 nos EUA exclusivamente através da rede de fibra óptica privada, dedicada e monitorada da própria AWS. Essa rota privada é otimizada em nível de protocolo e drasticamente mais rápida, confiável e segura que a internet pública.

Customizando na Borda (Edge Computing)

Em um modelo tradicional de CDN, o CloudFront atua de forma puramente intermediária: recebe uma requisição, verifica se o arquivo está no cache de borda e, se não estiver, busca na origem e repassa ao cliente. Contudo, em aplicações modernas, surge frequentemente a necessidade de executar lógica de programação diretamente na borda antes que a requisição toque a origem ou antes que a resposta chegue ao usuário final (por exemplo: validar se o cliente possui um token JWT de autenticação, redirecioná-lo para páginas com base em seu país de acesso, injetar cabeçalhos de segurança ou reescrever URLs).

Para viabilizar processamento na borda (Edge Computing) próximo ao usuário, a AWS oferece duas tecnologias complementares:

1. CloudFront Functions: O Leve, Econômico e Ultrarrápido
• O que é: Um recurso nativo integrado diretamente em todas as mais de 450+ Edge Locations do CloudFront, projetado para executar scripts compactos em JavaScript com latência sub-milissegundo.
• Casos de Uso Ideais: Tarefas leves de manipulação de requisições, como normalização de URLs (ex: converter toda a URL para minúsculas antes de consultar a chave de cache para maximizar Cache Hits), manipulação simples de cabeçalhos HTTP (adicionar Strict-Transport-Security, X-Content-Type-Options), redirecionamentos de rota simples e controle básico de cookies.
• Limitações Técnicas:
  • Tempo máximo de execução inferior a 1 milissegundo.
  • Sem acesso à internet (não pode invocar APIs externas, webhooks ou microsserviços).
  • Não tem acesso ao corpo da requisição HTTP (body).
  • Não suporta bibliotecas externas nem o AWS SDK.
  • Custo Reduzido: Custa aproximadamente 1/6 do valor do Lambda@Edge.
2. Lambda@Edge: O Robusto e Poderoso
• O que é: O serviço AWS Lambda tradicional implantado na camada de Caches Regionais do CloudFront (Regional Edge Caches) espalhados globalmente. Oferece suporte completo aos runtimes de Node.js e Python.
• Casos de Uso Ideais: Lógica de negócio completa e avançada na borda. Pode inspecionar e modificar o corpo inteiro da requisição HTTP (o body), processar fluxos de autenticação complexos (como validação profunda de OAuth/OpenID Connect) e consultar dinamicamente bancos de dados externos (como chamadas de API para o Amazon DynamoDB ou RDS).
• Limitações e Características:
  • Tempo de execução superior (pode durar vários milissegundos ou até segundos).
  • Possui acesso completo à rede/internet e a todas as bibliotecas do AWS SDK.
  • Custo por execução maior que o CloudFront Functions, sendo reservado para tarefas onde o poder computacional na borda é essencial.

• S3 Transfer Acceleration: Aproveita a malha de fibra óptica privada da AWS para acelerar uploads de longa distância.
• Edge Computing: CloudFront Functions para tarefas ultrarrápidas de cabeçalho/URL; Lambda@Edge para lógica avançada com acesso a dados e autenticação pesada.

5. Caching strategies

Em arquitetura de software para sistemas em nuvem, colocar dados na memória RAM é apenas o primeiro passo. O verdadeiro diferencial de engenharia reside em definir o padrão de atualização e consistência entre o cache em memória (como o Amazon ElastiCache) e a base persistente de dados (como Amazon Aurora).

Existem dois padrões fundamentais de design que todo arquiteto e desenvolvedor deve dominar e programar na aplicação:

1. Lazy Loading (Carregamento Preguiçoso / Cache-Aside)

A Lógica de Operação: É uma estratégia reativa. O cache inicia vazio e só é abastecido no momento exato em que algum usuário tenta ler o dado. O fluxo de código segue a ordem:

  1. A aplicação pesquisa primeiro no cache pelo identificador da chave.
  2. Se não encontrar (Cache Miss), a aplicação recorre ao banco de dados relacional lento.
  3. A aplicação obtém o dado do banco e grava uma cópia no cache antes de responder ao cliente, garantindo que as próximas requisições encontrem o dado já em memória (Cache Hit).
  • Vantagens:
    • Eficiência de Memória: O cache nunca fica sobrecarregado com dados desnecessários; apenas os registros efetivamente requisitados pelos usuários consomem espaço na memória RAM.
    • Resiliência a Falhas de Nó: Se um nó do ElastiCache falhar, travar ou reiniciar totalmente vazio, o sistema não entra em colapso. A aplicação simplesmente experimentará uma sequência inicial de Cache Misses temporários, e o cache se reabastecerá gradualmente de forma autônoma sob demanda.
  • Desvantagens:
    • Penalidade do Miss (Miss Penalty): O primeiro usuário que solicitar um determinado produto ou dado sofrerá lentidão perceptível, pois a aplicação terá que aguardar as três etapas de rede (consultar cache → consultar banco → gravar no cache).
    • Risco de Dados Obsoletos (Stale Data): Se um dado for modificado diretamente no banco de dados e a chave no cache ainda for válida (com um TTL longo), os usuários continuarão recebendo a versão antiga e desatualizada do dado até que a chave expire.
  • Caso de Uso Ideal: Perfil de Usuário. Um usuário altera sua própria foto de perfil ou biografia pouquíssimas vezes por ano, mas sua página de perfil pode ser acessada milhares de vezes por amigos ou seguidores ao longo do dia.

2. Write-Through (Gravação Direta)

A Lógica de Operação: É uma estratégia proativa. Toda vez que uma gravação ou alteração é realizada no banco de dados (operações de escrita como INSERT ou UPDATE), a aplicação é programada para forçar obrigatoriamente e simultaneamente a gravação dessa mesma alteração dentro do cache de memória.

  • Vantagens:
    • Dados Sempre Atualizados: O cache reflete em tempo real o estado exato da fonte canônica de dados, eliminando o risco de leituras com dados desatualizados (zero stale data).
  • Desvantagens:
    • Penalidade de Gravação (Write Penalty): Salvar dados torna-se ligeiramente mais demorado, pois a aplicação precisa completar o commit em dois armazenamentos físicos distintos (banco de dados e cache) antes de devolver a resposta de sucesso ao usuário.
    • Desperdício de Espaço de RAM (Cache Bloat): Se o sistema gravar no cache registros ou itens novos que ninguém irá ler no futuro, a memória RAM ficará ocupada com dados inúteis, gerando custo financeiro desnecessário.
    • Risco de Falha do Nó: Se um nó de cache reiniciar ou for substituído por um nó vazio, aquele dado novo não estará no cache até que ocorra uma nova operação de gravação no banco de dados (exigindo que você implemente o Lazy Loading em paralelo como mecanismo de contingência para leituras).
  • Caso de Uso Ideal: Dados Críticos em Tempo Real. Exemplo: Placar de líderes mundial (Top 100 Leaderboard) de um jogo online multijogador, contadores de curtidas ao vivo de notícias de última hora ou atualizações críticas de estoque em promoções relâmpago da cafeteria.

Tabela Comparativa: Lazy Loading vs. Write-Through

Critério Lazy Loading (Cache-Aside) Write-Through
Natureza do Fluxo Reativo (orientado à Leitura) Proativo (orientado à Escrita)
Momento da Carga Apenas quando o dado é solicitado pela 1ª vez Imediatamente na criação/atualização do registro
Uso de Memória RAM Otimizado (apenas dados requisitados ocupam espaço) Maior (pode inflar o cache com dados nunca lidos)
Latência na Leitura Lenta no 1º acesso (Miss); instantânea nos seguintes Sempre instantânea (dado já pré-carregado)
Latência na Gravação Nenhuma penalidade extra na escrita Penalidade de gravação dupla (Banco + Cache)
Risco de Dados Obsoletos Sim (mitigado definindo um bom TTL) Nulo (dados sempre sincronizados)
Comportamento se Nó Cair Recupera-se sozinho gradualmente com leituras Exige Lazy Loading como mecanismo de contingência
Resumo dos Pontos-Chave da Seção 5 (Key Takeaways):
• Lazy Loading: Foca na leitura. Excelente para economia de memória RAM, mas exige lidar com dados desatualizados através de uma calibração precisa do tempo de expiração (TTL - Time To Live).
• Write-Through: Foca na gravação. Garante consistência imediata sincronizando a escrita. Causa uma pequena penalidade na gravação, mas garante leitura instantânea com 100% de precisão.
• A Arquitetura Ideal (Padrão Híbrido): Sistemas corporativos de alta criticidade (como grandes e-commerces) geralmente mesclam os dois padrões: aplicam Lazy Loading com TTL para o catálogo geral de produtos e navegação histórica, e utilizam Write-Through para o estoque em tempo real das promoções do dia!

    • O site da cafeteria carregará perfeitamente, com cadeado de segurança verde atestando a criptografia HTTPS!
    • Teste abrir a URL em um celular via rede 4G/móvel ou execute wget <distribution-domain-name> no terminal do IDE: o site está acessível globalmente.

Tarefa 3: Proteção do Acesso de Rede à Distribuição usando AWS WAF (Global)

Agora que o site está no CloudFront, qualquer pessoa na internet com a URL poderia acessá-lo. Para restringir o acesso exclusivamente ao endereço IP do escritório da cafeteria durante o desenvolvimento, utilizaremos o AWS WAF com escopo Global (CloudFront).

  1. No console da AWS, acesse o serviço WAF & Shield.
  2. Crie o Conjunto de IPs Global:
    • No menu lateral, selecione Conjuntos de IPs (IP sets) > Create IP set.
    • Nome: office | Descrição: office IP
    • Região: Global (CloudFront).
    • Endereços IP: Insira seu endereço IPv4 público seguido de /32 (ex: 203.0.113.45/32).
    • Clique em Criar conjunto de IP.
  3. Crie a Web ACL Global para o CloudFront:
    • No menu lateral, selecione ACLs Web (Web ACLs) > Criar ACL da web.
    • Tipo de recurso: CloudFront distributions.
    • Nome: cafe-website-office-only-during-dev
    • Recursos associados da AWS: Clique em Add AWS resources e selecione a distribuição CloudFront criada na Tarefa 2.
    • Na etapa Add rules, selecione Add my own rules and rule groups:
      • Tipo de regra: IP set.
      • Nome da regra: only_office_please
      • IP set: Selecione o conjunto office.
      • Endereço IP de origem: Source IP address.
      • Ação: Allow (Permitir).
    • Default web ACL action (Ação padrão): Defina como Block (Bloquear). Isso garante que qualquer requisição originada de um IP fora do conjunto office seja sumariamente bloqueada!
    • Avance mantendo as métricas padrão e clique em Create web ACL.
  4. Validação Prática da Proteção Perimetral:
    • No seu computador (mesmo IP cadastrado), recarregue a URL do CloudFront: o site continua acessível normalmente (200 OK).
    • No seu smartphone conectado na rede móvel 4G (ou via terminal do VS Code IDE executando wget https://<distribution-domain>.cloudfront.net): a requisição é interceptada na borda pelo WAF e retorna HTTP 403 Forbidden!

Tarefa 4: Proteção de um Endpoint da API REST usando AWS WAF (Regional)

O site estático está protegido na borda, mas as chamadas AJAX do frontend consultam a API REST no Amazon API Gateway diretamente. Para impedir invocações diretas não autorizadas aos dados de estoque, criaremos uma Web ACL com escopo Regional associada ao estágio de produção da API.

  1. No console do WAF & Shield, acesse Conjuntos de IPs e clique em Create IP set:
    • Nome: office_regional
    • Região: US East (N. Virginia) (região onde o API Gateway está implantado).
    • Endereços IP: Seu IP público seguido de /32.
    • Clique em Criar conjunto de IP.
  2. Crie a Web ACL Regional:
    • Vá em Web ACLs > Criar ACL da web.
    • Tipo de recurso: Regional resources (US East - N. Virginia).
    • Nome: website-api-gw-office-only-during-dev
    • Recursos associados: Selecione Amazon API Gateway → ProductsApi - prod.
    • Adicionar Regras: Adicione uma regra do tipo IP set chamada ip_for_apigw vinculada ao IP set office_regional, com ação Allow.
    • Ação Padrão (Default action): Block (Bloquear).
    • Conclua a criação da Web ACL.
  3. Validação da Segurança da API:
    • No console do API Gateway, acesse ProductsApi > Estágios > prod > /bean_products (GET).
    • Copie o Invocar URL (formato https://<api-id>.execute-api.us-east-1.amazonaws.com/prod/bean_products) e abra no navegador do seu computador: o documento JSON com a lista de grãos é retornado normalmente.
    • Abra a mesma URL em um dispositivo fora da rede (leitura de QR Code no smartphone ou wget <invoke-url> no terminal do IDE): a resposta retornará imediatamente: 
      {"message": "Forbidden"}

Tarefa 5: Configuração de uma CloudFront Function na Borda

Frank solicitou que o site exiba aleatoriamente uma sobremesa artesanal em destaque na página inicial. Implementar isso gerando páginas dinâmicas no servidor destruiria a capacidade de cache da CDN; implementar via JavaScript no cliente aumentaria o peso do download. A solução ideal da AWS é executar uma CloudFront Function na borda: a função intercepta a resposta do CloudFront (Viewer Response), sorteia um item de um array de doces e injeta um cookie HTTP (the_image). O código estático do site lê esse cookie e altera dinamicamente a imagem de fundo!

  1. No console do CloudFront, selecione Functions (Funções) no menu lateral e clique em Criar função:
    • Nome: random_image_header
    • Clique em Criar função.
  2. Na aba Function code (Código de função), substitua o código padrão pelo seguinte script JavaScript: 
    function handler(event) {
    var pastry_name_arr = [
        "apple_pie",
        "apple_pie_slice",
        "chocolate_chip_cupcake",
        "strawberry_cupcake",
        "blueberry_jelly_doughnut",
        "plain_bagel"
    ],
    random_int = Math.floor(Math.random() * (pastry_name_arr.length)),
    response = event.response,
    date = new Date(),
    attr_str = "",
    distro_str = "<DISTRIBUTION_ID>"; // Substitua pelo ID da sua distribuição CloudFront
    
    date.setTime(+ date + (365 * 86400000)); // Validade de 1 ano em milissegundos
    attr_str = "Secure; Path=/; Domain=" + distro_str + ".cloudfront.net; Expires=" + date + ";";
    
    response.cookies = {
        "the_image": {
"value": pastry_name_arr[random_int],
"attributes": attr_str
        }
    };
    
    return response;
}

    Importante: Na variável distro_str, substitua o placeholder pela string do domínio da sua distribuição CloudFront (apenas o prefixo antes de .cloudfront.net). Salve as alterações.

  3. Teste e Publique a Função:
    • Acesse a aba Teste, selecione o tipo de evento Viewer Response e clique em Test function. Confirme que o status de saída seja 200 OK com o cookie the_image gerado no payload.
    • Acesse a aba Publicar e clique em Publicar função.
    • Na seção Distribuições associadas, clique em Adicionar associação:
      • Distribuição: Selecione a distribuição da cafeteria.
      • Tipo de evento: Viewer Response.
      • Comportamento de cache: Padrão (*).
  4. Teste no Navegador: Abra o site da cafeteria no CloudFront e pressione F5 várias vezes seguidas. A cada recarregamento, a imagem da sobremesa em destaque à direita da xícara de café alternará aleatoriamente (torta de maçã, cupcakes, donut de geleia ou bagel), enquanto todo o restante da página permanece servido em altíssima velocidade pelo cache!

Tarefa 6: Ajustar a Duração do Cache (TTL & Cache-Control no S3)

Durante a fase de desenvolvimento, todos os arquivos foram enviados ao S3 com o cabeçalho Cache-Control: max-age=0. Isso forçava o CloudFront a revalidar todas as requisições na origem (o bucket S3), gerando cabeçalhos de resposta x-cache: RefreshHit from cloudfront ou Miss from cloudfront.

Agora que a distribuição está estável, Sofía ajustará a política de expiração definindo um TTL de 180 segundos (3 minutos) em todos os objetos do bucket S3 via linha de comando na AWS CLI.

  1. Inspecione o Comportamento Atual no Navegador:
    • No site da cafeteria, abra as ferramentas do desenvolvedor (F12 > Network) e recarregue a página.
    • Selecione a requisição do domínio .cloudfront.net e veja os Response Headers: 
      cache-control: max-age=0
x-cache: RefreshHit from cloudfront (ou Miss from cloudfront)
  2. Atualize o Cabeçalho Cache-Control em Lote no S3 via AWS CLI:

    No terminal Bash do VS Code, execute o pipeline de comandos para sobrescrever os metadados de todos os arquivos para max-age=180:

    BUCKET_NAME=$(aws s3api list-buckets --query "Buckets[?contains(Name, 's3bucket')].Name" --output text)
echo "Bucket identificado: $BUCKET_NAME"

aws s3 ls s3://$BUCKET_NAME/ | awk '{print $4}' | xargs -I {} aws s3api copy-object   --bucket $BUCKET_NAME   --copy-source $BUCKET_NAME/{}   --key {}   --cache-control "max-age=180"   --metadata-directive REPLACE
  3. Valide no Console do S3: Abra o bucket -s3bucket, selecione qualquer arquivo e verifique que a propriedade Cache-Control agora exibe max-age=180.
  4. Teste os Efeitos do Cache na Borda:
    • Recarregue o site da cafeteria no navegador. Na aba Network, observe que o cabeçalho cache-control: max-age=180 agora está ativo.
    • Recarregue a página pela segunda vez (dentro da janela de 3 minutos): o cabeçalho de diagnóstico agora reportará orgulhosamente: 
      x-cache: Hit from cloudfront

      O arquivo HTML e os ativos estáticos foram entregues diretamente da memória da Edge Location do CloudFront em microssegundos, sem tocar no Amazon S3!

    • Aguarde 3 minutos até que o TTL expire e recarregue a página: o cabeçalho mudará para x-cache: RefreshHit from cloudfront (o CloudFront consultou o S3 para verificar se o arquivo mudou, renovando o cache por mais 180 segundos).
    • Mesmo com a página em estado de Cache Hit, a CloudFront Function continua disparando no evento Viewer Response, garantindo a alternância contínua da imagem promocional sem quebrar o cache de borda!
