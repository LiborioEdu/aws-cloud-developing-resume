1. Introduction

Este módulo é dedicado a entender como os sistemas se comunicam na internet usando APIs e foca no serviço Amazon API Gateway, a porta de entrada para suas aplicações na AWS.

Conceitos-Chave (Sopa de Letrinhas):

  • API: Application Programming Interface (Interface de Programação de Aplicações). É o contrato de comunicação entre dois softwares.
  • REST: Representational State Transfer. É o padrão arquitetural mais comum na web para construir APIs, usando os métodos HTTP clássicos (GET, POST, PUT, DELETE).

Objetivos de Aprendizado:

Ao final do módulo, você saberá como:

  • Explicar o que é o Amazon API Gateway.
  • Seguir os passos para criar APIs RESTful do zero.
  • Publicar (fazer o deploy), monitorar, dar manutenção e, o mais importante, proteger (adicionar segurança) às suas APIs.

O Caso da Cafeteria (Cenário Prático):

A Sofía precisa integrar o site da cafeteria (Front-end) com o banco de dados de produtos (Back-end) usando uma API. No entanto, ela quer testar como o site vai se comportar e aprovar o visual com os donos antes de ter o trabalho de escrever todo o código de integração com o DynamoDB.

O Mock finge ser o banco de dados e devolve dados fictícios instantaneamente para o site. Assim que o site for testado e aprovado com esses dados simulados, ela apenas atualiza a configuração do API Gateway para apontar para o DynamoDB real.

2. Introducing APIs

O que é uma API?

A sigla significa Application Programming Interface (Interface de Programação de Aplicações). Na prática, uma API é um mecanismo que simplifica a vida do desenvolvedor fazendo três coisas:

  • Abstrai a complexidade: O cliente (front-end) não precisa saber como o banco de dados funciona por baixo dos panos.
  • Expõe apenas o necessário: O front-end só tem acesso aos dados e ações que a API permite.
  • Estabelece um contrato: Define regras claras de como a informação deve ser enviada e recebida.
Exemplo clássico: Quando você usa o "Login com o Facebook" ou paga algo via "PayPal" em um site terceiro, o site está apenas chamando a API dessas empresas.

Requisições e Respostas (Requests and Responses)

A comunicação funciona em um ciclo de pergunta (Requisição) e resposta. Para isso, utiliza-se protocolos. Os mais comuns são o HTTP (padrão da web), SOAP (baseado em XML) e WebSockets (protocolo bidirecional para aplicações em tempo real, cujas URLs começam com ws://).

Dica de segurança: Sempre utilize as versões seguras desses protocolos: HTTPS e WSS.

Códigos de Status HTTP (Importante para o dia a dia e provas)

Toda resposta da API devolve um número que indica o que aconteceu. Eles são divididos em três famílias principais:

  • Série 200 (20x - Sucesso): Tudo correu perfeitamente. Ex: 200 OK ou 201 Created (dado criado com sucesso).
  • Série 400 (40x - Erro do Cliente): A culpa é de quem fez a requisição. O cliente mandou uma senha errada, faltou uma informação obrigatória ou ele não tem permissão. Ex: 403 Forbidden ou 404 Not Found.
  • Série 500 (50x - Erro do Servidor): A culpa é do servidor (Back-end/AWS). O código deu um bug interno ou o banco de dados caiu. Ex: 500 Internal Server Error.

O que é uma API RESTful?

REST (Representational State Transfer) não é uma linguagem de programação, é um estilo de arquitetura. É a forma padrão e mais adotada pelo mercado para estruturar como um cliente pede dados a um servidor web. Quando uma API segue rigorosamente as regras e os princípios do estilo REST, ela é chamada de RESTful API.

3. Introducing API Gateway

Para entender o serviço, primeiro você precisa entender o conceito. Um API Gateway funciona como um Proxy — um intermediário blindado entre o cliente (o front-end) e o seu servidor (o back-end).

Se você não tivesse um API Gateway, o seu servidor teria que processar as regras de acesso de todas as pessoas que chegassem, o que desperdiçaria muito processamento. O API Gateway assume o trabalho de "recepção e segurança", fazendo coisas como:

  • Limitação de Taxa (Rate Limiting / Throttling): Age como o "segurança da balada". Se muitos acessos chegarem ao mesmo tempo, ele segura a onda para que o seu servidor não caia por sobrecarga.
  • Validação de Chaves: Verifica se quem está chamando a API possui uma API Key válida (como as chaves do Google Maps ou Twitter) e bloqueia acessos inválidos antes mesmo que cheguem ao seu servidor.
  • Roteamento e Filtros: Pode redirecionar o tráfego com base na região do usuário (geo-routing) ou nos cabeçalhos da requisição.

O Amazon API Gateway

É o serviço totalmente gerenciado e serverless (sem servidor) da AWS que atua como a "porta de entrada" (front door) das suas aplicações.

A grande vantagem: Você não precisa de servidores (EC2) para hospedar sua API. O API Gateway pode receber a requisição, transformar os dados, invocar um código no AWS Lambda (ou até mesmo ir direto no DynamoDB), e devolver a resposta formatada para o cliente. Você só paga pelas chamadas que a API receber e pelos dados transferidos.

Protocolos Suportados (Importante para Provas)

O serviço suporta dois tipos principais de APIs, com comportamentos opostos:

APIs RESTful:

  • Comunicação padrão de Requisição e Resposta (Request/Response).
  • Usa os métodos HTTP tradicionais (GET, POST, PUT, DELETE).
  • É uma comunicação curta (short-lived) e Sem Estado (Stateless) — ou seja, cada requisição é independente e o servidor não "lembra" da requisição anterior.

APIs WebSockets:

  • Abre um canal de comunicação de mão dupla (bidirecional).
  • É uma comunicação contínua (long-lived) e Com Estado (Stateful) — a conexão fica aberta e mantida ativa entre cliente e servidor.
  • Uso ideal: Chats em tempo real, jogos multiplayer e painéis de monitoramento / dashboards com atualizações contínuas.

4. Introducing API Gateway - Part 2

Quando você clica em "Criar API" no Amazon API Gateway, a AWS te dá algumas opções arquiteturais. É crucial entender a diferença entre elas para não gastar dinheiro à toa ou perder performance.

1. REST API vs. HTTP API

Para comunicações tradicionais de requisição/resposta, você tem duas opções:

  • REST API (Modo Avançado): Oferece controle total e absoluto. É aqui que você consegue criar Mock Endpoints (como a Sofía vai fazer), configurar autenticações super complexas e manipular pesadamente os dados que entram e saem.
  • HTTP API (Modo Simples e Leve): É a versão simplificada. Serve perfeitamente se você só precisa de um proxy básico (exemplo: uma porta de entrada simples para acionar uma função do AWS Lambda).
    A grande vantagem: É muito mais rápido (menor latência) e custa até 70% menos que a versão REST tradicional. Se você não precisa de recursos avançados, escolha sempre a HTTP API.

2. WebSockets (Para aplicações "faladoras")

Se você for criar um chat, um jogo multiplayer ou um painel financeiro em tempo real, o HTTP normal é uma péssima escolha. O HTTP exige o envio de "envelopes" pesados (cabeçalhos, tokens de segurança) a cada nova mensagem enviada, o que desperdiça banda e causa lentidão.

A Solução WebSocket: Ele estabelece um "tubo" de conexão bidirecional. O envelope pesado de segurança só é enviado uma vez (na abertura da conexão). Depois disso, as mensagens (como "Oi" ou "LOL") trafegam de forma extremamente leve e instantânea nos dois sentidos.

Dica: Sempre use a versão segura, o WSS.

Gerenciamento e Implantação (Infraestrutura como Código)

Em vez de clicar botões no console da AWS para criar sua API, profissionais utilizam ferramentas de automação (Deploy):

Desenvolvimento (Develop):

  • AWS Management Console: Interface gráfica interativa no navegador para testes e visualização rápida.
  • AWS Command Line Interface (AWS CLI): Linha de comando para automação por scripts e chamadas de terminais.
  • OpenAPI Specification (Swagger): Padrões da indústria para desenhar e documentar a estrutura da sua API.

Implantação (Deploy):

  • AWS SAM (Serverless Application Model): Uma extensão do CloudFormation feita sob medida para aplicações serverless. É excelente para testar APIs e funções Lambda localmente no seu computador antes de enviar para a nuvem.
  • AWS CloudFormation: Serviço clássico para criar recursos na AWS usando arquivos de texto em formato JSON ou YAML.
  • AWS CDK (Cloud Development Kit): Permite que você escreva a sua infraestrutura usando linguagens de programação reais (como Python, TypeScript ou Java) em vez de escrever arquivos de configuração estáticos.

5. Creating a REST API

Quando você cria uma API no Amazon API Gateway, a AWS gera automaticamente uma URL base (Endpoint) estruturada de forma padronizada:

https://{restapi_id}.execute-api.{region}.amazonaws.com/{stage_name}/

Anatomia da URL base gerada:

  • {restapi_id}: O identificador alfanumérico exclusivo da API (API Identifier) gerado pela AWS.
  • {region}: A região AWS onde a API foi provisionada (ex: us-east-2).
  • {stage_name}: O nome do estágio de implantação da API (ex: dev, staging, prod).

Você pode realizar a criação tanto pelo Console da AWS quanto de forma automatizada por linha de comando através da AWS CLI (ou via IaC com CloudFormation, SAM e CDK).

Métodos e Rotas (Methods and Routes)

Uma API do mundo real faz muito mais do que apenas uma única tarefa. Você não cria uma API diferente para listar produtos e outra para editar produtos; você cria Rotas diferentes dentro da mesma API.

A combinação de um Método HTTP (a ação pretendida) e um Caminho (Path) define uma Rota. Cada Rota pode acionar um código (como uma função Lambda) diferente:

  • Listar tudo: [GET] /products → Aciona a função Lambda readFn.
  • Ver um item específico: [GET] /products/{product_id} → Aciona a mesma função readFn, mas a função percebe que o ID foi passado no caminho e faz uma busca específica em vez de listar todos.
  • Atualizar produto: [PUT] /products/{product_id} → Aciona a função Lambda updateFn para regravar os dados do produto.

Exemplo prático de criação de rotas via AWS CLI (aws apigatewayv2 create-route):

# Rota GET para produto específico por ID:
aws apigatewayv2 create-route     --api-id 03z501670a     --route-key 'GET /products/{product_id}'     --target arn:aws:lambda:us-east-2:123456789012:function:readFn

# Rota GET para listar o catálogo completo de produtos:
aws apigatewayv2 create-route     --api-id 03z501670a     --route-key 'GET /products'     --target arn:aws:lambda:us-east-2:123456789012:function:readFn

# Rota PUT para atualização de dados de um produto:
aws apigatewayv2 create-route     --api-id 03z501670a     --route-key 'PUT /product/{product_id}'     --target arn:aws:lambda:us-east-2:123456789012:function:updateFn

Variável de Caminho "Guloso" (Greedy Path Variable: {proxy+})

Se você não quiser configurar cada rota ou subcaminho separadamente no API Gateway, pode utilizar o atalho {proxy+} (ex: GET /products/{proxy+}).

  • O que faz: Ele atua como um recurso "pega-tudo" (catch-all). Qualquer coisa digitada após /products/ (ex: /products/34/detalhes/extra) será capturada e enviada diretamente para a sua Função Lambda.
Desvantagem & Melhor Prática: Ao usar o {proxy+}, o trabalho pesado de descobrir para onde o usuário queria ir e qual ação tomar será empurrado para o código da sua Função Lambda, aumentando latência e complexidade de código. Melhor prática: Prefira caminhos e rotas específicos e declarativos no API Gateway sempre que possível!

Criando APIs WebSockets

Para fluxos bidirecionais contínuos e comunicação em tempo real, podemos criar uma API WebSocket no API Gateway:

aws apigatewayv2 create-api     --name 'mywebsocketapi'     --protocol-type WEBSOCKET     --route-selection-expression '.body.action'

A criação de uma API WebSocket exige um parâmetro especial: o route-selection-expression (Expressão de Seleção de Rota).

  • Como funciona: Como o WebSocket é um canal contínuo onde os dados trafegam nos dois sentidos em formato JSON, o API Gateway precisa saber como inspecionar o seu JSON para decidir qual rota acionar.
  • Se você configurar a expressão para ler a chave .body.action, sempre que o cliente enviar um JSON como: 
    {
  "service": "chat",
  "action": "join",
  "data": {
    "room": "room1234"
  }
}
    O API Gateway avaliará o campo "action": "join" e saberá imediatamente que deve acionar o código que coloca o usuário na sala de chat especificada.
  • Rotas Padrão do Sistema: O WebSocket possui três rotas nativas gerenciadas:
    • : Acionada no momento exato em que o cliente estabelece a conexão inicial.
    • : Acionada quando o cliente ou servidor encerra a sessão.
    • : Acionada como rota de fallback se a mensagem enviada não bater com nenhuma outra regra customizada.

Importando APIs (Swagger / OpenAPI)

Se você (ou sua equipe) já desenhou toda a arquitetura da sua API em um arquivo padronizado Swagger ou OpenAPI (em formato JSON ou YAML), você não precisa refazer o trabalho clicando botão por botão no console da AWS.

Você pode usar o comando de importação da AWS CLI (aws apigateway import-rest-api ou aws apigatewayv2 reimport-api) ou a opção de importação no Console, e o API Gateway cria todas as rotas, métodos, parâmetros e modelos automaticamente a partir daquele arquivo.

6. Part 1: Integrating with API Gateway

Agora que a API foi criada, precisamos decidir como ela será exposta para o mundo (ou restrita à rede interna) e como o front-end (ou clientes externos) vai se comunicar com ela.

A forma como você publica a sua API afeta diretamente o desempenho (latência), os custos e a segurança. O Amazon API Gateway oferece três tipos de configuração de rede (endpoints):

Tipos de Endpoints de Rede (Endpoint Types)

  • 1. Edge-Optimized (Otimizado para Borda):
    • Exclusividade: Exclusivo para APIs REST clássicas (REST only). Não é suportado para HTTP APIs nem WebSockets.
    • Como funciona: A AWS provisiona e gerencia automaticamente uma distribuição global do Amazon CloudFront na frente da sua API. As requisições dos clientes são roteadas para o ponto de presença (Edge Location) do CloudFront mais próximo geograficamente e trafegam pela rede troncal ultra-rápida e privada da AWS até a região onde a API está implantada.
    • Quando usar: Quando os usuários e clientes da sua aplicação estiverem geograficamente dispersos pelo mundo. Reduz drasticamente a latência de handshake TLS e oferece proteção nativa contra ataques DDoS volumétricos através do AWS Shield Standard.
  • 2. Regional (Regional):
    • Suporte: Suportado por todos os tipos de API no API Gateway (REST, HTTP e WebSocket).
    • Como funciona: A API é implantada e atende requisições estritamente dentro da Região AWS selecionada (ex: us-east-1 ou sa-east-1). Não há distribuição do CloudFront gerenciada pela AWS na frente.
    • Quando usar: É o formato padrão e recomendado para a maioria dos casos de uso gerais, especialmente quando as requisições se originam dentro da mesma região (como instâncias Amazon EC2, containers no ECS/EKS ou outros microsserviços na mesma VPC).
    • Melhor Prática Arquitetural: Para aplicações voltadas à internet pública, a AWS recomenda criar um endpoint Regional e configurar a sua própria distribuição do CloudFront (Customer-Managed CloudFront Distribution) na frente dele. Isso proporciona controle granular total sobre políticas de cache (TTL), regras avançadas do AWS WAF, certificados SSL/TLS customizados e consolidação de múltiplos backends/estáticos sob o mesmo domínio.
  • 3. Private (Privado):
    • Exclusividade: Exclusivo para APIs REST clássicas (REST only).
    • Como funciona: Essa API não possui nenhum endereço IP público nem acesso à internet. Ela só pode ser acessada de dentro da sua nuvem privada virtual (Amazon VPC) através de um VPC Interface Endpoint (alimentado pela tecnologia AWS PrivateLink).
    • Quando usar: Ideal para arquiteturas corporativas de microsserviços internos, sistemas de backoffice, comunicação entre parceiros via VPC Peering / Direct Connect ou qualquer tráfego confidencial regulamentado que nunca deve passar pela internet pública.

Como o Front-end chama a API? (HTTPS vs. SDKs)

No caso de uso prático da cafeteria (Café Business Case), quando a Sofía for conectar o site ao API Gateway, ela tem dois caminhos possíveis para a comunicação:

  • 1. Requisições HTTPS Padrão (Abordagem Recomendada):

    O site consome a API através de ferramentas e bibliotecas web nativas e consagradas (como fetch() nativo ou axios no JavaScript) para realizar requisições HTTP clássicas (GET, POST, PUT) diretamente para a URL pública gerada pelo API Gateway.

    É o padrão universal da web: simples, leve, compatível com qualquer biblioteca ou framework moderno (React, Vue, Angular, Vanilla JS) e desacoplado.

  • 2. Gerar um SDK Customizado no API Gateway:

    Para REST APIs, o API Gateway oferece um recurso de compilação automática: você clica em "Generate SDK" e a AWS gera um pacote de software pronto para download em diversas plataformas e linguagens, incluindo JavaScript, Android (Java), iOS (Objective-C/Swift), Java e Ruby.

    Esse SDK cliente já encapsula chamadas para todos os métodos e modelos definidos na sua API.

Alerta Crítico de Segurança (Armadilha em Front-ends Públicos):
Embora pareça tentador e prático baixar o SDK JavaScript gerado e usá-lo diretamente no código do site da cafeteria, isso exige que credenciais da AWS (chaves de acesso IAM ou tokens assinados) sejam embutidas no código executado no navegador do usuário.

Qualquer usuário com o DevTools (F12) aberto poderia inspecionar e roubar essas credenciais! Portanto, para aplicações web voltadas ao público (SPAs e sites estáticos), nunca utilize SDKs que dependam de credenciais no cliente — mantenha sempre a comunicação via requisições HTTPS padrão (utilizando cabeçalhos como Authorization: Bearer <token-jwt> ou cookies HTTP-Only seguros para autenticação).

7. Part 2: Integrating with API Gateway

Para conectar o mundo externo (seu site, aplicativo mobile ou clientes de API) com os recursos internos da AWS, o Amazon API Gateway precisa saber exatamente com quem ele vai falar. É aqui que entram as Integrações de Back-end (Backend Integrations).

Muitos serviços da AWS (como o AWS Lambda e o Amazon DynamoDB) não possuem URLs públicas nativas abertas para a internet. Você não pode simplesmente fazer um GET ou POST direto neles a partir do navegador. O API Gateway atua como esse procurador inteligente (reverse proxy), recebendo a chamada HTTP do cliente, autenticando e acionando esses serviços internamente através da rede privada da AWS.

Opções de Integração de Back-end

O API Gateway oferece suporte nativo e flexível a diversas origens de dados e processamento:

  • Serviços AWS Diretos (Direct AWS Service Integration):

    O API Gateway pode acionar funções do AWS Lambda, ler ou gravar arquivos diretamente no Amazon S3, executar queries ou gravações no Amazon DynamoDB, publicar mensagens no Amazon SQS / SNS ou iniciar fluxos de trabalho no AWS Step Functions — tudo isso de forma direta, muitas vezes sem precisar escrever nenhuma linha de código intermediária.

  • Endpoints HTTP Públicos (HTTP Proxy & Integrations):

    Permite conectar a sua API a servidores HTTP tradicionais hospedados no Amazon EC2, aplicações no AWS Elastic Beanstalk, ou a qualquer outra API REST/HTTP pública de terceiros na internet (como gateways de pagamento, serviços de consulta de CEP, microsserviços legados externos).

  • VPC Link (Acesso Seguro à Rede Privada):

    Um recurso poderoso e corporativo para conectar sua API pública (ou regional) a recursos e microsserviços privados que estão trancados dentro da sua Amazon VPC. O API Gateway se conecta através de um VPC Link a um Network Load Balancer (NLB) ou Application Load Balancer (ALB) interno, podendo estender a comunicação até servidores on-premises conectados via AWS Direct Connect ou VPN privada.

  • Mock Endpoints (O truque da Sofía!):

    Exclusivo do modo REST API. Permite que o API Gateway retorne respostas falsas (mocked / fakes) estáticas com códigos de status HTTP e payloads JSON pré-configurados, sem acionar nenhum backend real.

    O caso da cafeteria da Sofía: É perfeito para acelerar o desenvolvimento e prototipagem ágil! A desenvolvedora front-end pode começar a construir e testar a interface do site consumindo dados estáticos realistas do Mock Endpoint, enquanto a equipe de back-end ainda está modelando as tabelas e codificando as funções Lambda.

O Fluxo de Integração (O Caminho da Requisição em 4 Etapas)

Quando uma requisição chega ao API Gateway (em uma REST API clássica), ela não passa reto para o backend. Ela atravessa um pipeline estruturado em 4 etapas que permite inspecionar, validar, transformar e enriquecer os dados nos dois sentidos:

  1. 1. Requisição do Método (Method Request):

    É a "porta da frente" da API. Representa exatamente o que o cliente (ex: o site da cafeteria) enviou na chamada HTTP. Aqui o API Gateway realiza:

    • Modelagem & Validação: Inspeciona parâmetros de URL (query strings, path parameters), cabeçalhos obrigatórios e valida o formato do corpo da requisição (body) contra um JSON Schema. Se os dados forem inválidos, a requisição é rejeitada de imediato (HTTP 400 Bad Request) sem gastar execução de Lambda ou banco.
    • Autorização: Validação de chaves de API (API Keys), tokens JWT via Amazon Cognito ou Lambda Authorizers.
  2. 2. Requisição de Integração (Integration Request):

    Aqui ocorre a mágica da transformação (mapping templates via Apache Velocity Template Language - VTL). O API Gateway pega os dados brutos enviados pelo cliente e os formata no padrão exato exigido pelo backend de destino (ex: envelopando em parâmetros de evento para a função Lambda ou gerando parâmetros DynamoDB).

  3. 3. Resposta da Integração (Integration Response):

    O backend (Lambda, banco DynamoDB ou serviço HTTP) conclui o processamento e devolve a resposta em formato "cru" para o API Gateway. Nesta etapa, o API Gateway pode interceptar erros customizados, códigos de erro internos do backend e aplicar regras de mapeamento de status codes HTTP (ex: transformar um erro interno do Lambda em um HTTP 404 ou 500 elegante).

  4. 4. Resposta do Método (Method Response):

    É a etapa de saída final voltada para o cliente. O API Gateway pega o dado já processado, aplica cabeçalhos de resposta HTTP necessários (como cabeçalhos de CORS Access-Control-Allow-Origin, content-type application/json), valida o modelo de resposta e despacha a resposta HTTP final para o cliente solicitante.

8. Part 3: Integrating with API Gateway

A grande decisão arquitetural ao conectar o Amazon API Gateway a uma função do AWS Lambda é definir quem fará o "trabalho sujo" de formatar e envelopar a resposta HTTP para o cliente: o próprio código do Lambda ou o API Gateway.

1. Integração Proxy (O Caminho Direto: "Passa-Fio")

É a opção padrão e mais comum no desenvolvimento moderno serverless. O API Gateway atua essencialmente como um intermediário transparente ("passa-fio"):

  • Como funciona: O API Gateway recebe a requisição HTTP completa do cliente (caminho, query parameters, headers, body, contexto) e a entrega intacta como um único evento JSON para a função Lambda. O API Gateway não transforma nada na entrada nem na saída — a resposta retornada pela função passa direto para o cliente.
  • Responsabilidade total do desenvolvedor: A obrigação de montar e devolver uma resposta HTTP estruturada e válida é 100% do código da função Lambda.
  • Estrutura de Retorno Obrigatória: O Lambda não pode devolver apenas os dados brutos (como um objeto simples). A função deve retornar explicitamente um objeto JSON contendo chaves de rede obrigatórias:
    • statusCode (numérico): Código de status HTTP (ex: 200, 201, 400, 403, 500).
    • headers (objeto): Cabeçalhos HTTP da resposta (ex: Content-Type: application/json, Access-Control-Allow-Origin: * para CORS).
    • body (string): O payload real de resposta serializado obrigatoriamente como string (ex: via JSON.stringify() em Node.js ou json.dumps() em Python).

Exemplo de retorno obrigatório em Python no modelo Proxy:

import json

def lambda_handler(event, context):
    # Lógica de negócio...
    dados_resposta = {
        "pedidoId": "caf-1092",
        "status": "Em preparo",
        "cafe": "Cappuccino Aveludado"
    }

    return {
        "statusCode": 200,
        "headers": {
"Content-Type": "application/json",
"Access-Control-Allow-Origin": "*" # Essencial para navegadores (CORS)
        },
        "body": json.dumps(dados_resposta)
    }
Atenção em caso de erros no modelo Proxy: Se a sua lógica de negócio falhar ou o usuário não tiver permissão, o seu código precisa definir manualmente o "statusCode": 403 ou 404. Se o Lambda lançar uma exceção não tratada (crash de execução), o API Gateway devolverá automaticamente um HTTP 502 Bad Gateway para o cliente.

2. Integração Non-Proxy ou Customizada (O Caminho Transformador)

No modelo Non-Proxy (ou Custom Integration), o API Gateway assume o controle dos protocolos e metadados HTTP, desacoplando o código da função Lambda dos detalhes de rede:

  • Como funciona: A função Lambda atua estritamente como um processador de regras de negócio. Ela recebe apenas os dados limpos e devolve um dado puro (ex: {"mensagem": "Café pronto!"}). O API Gateway se encarrega de capturar esse retorno cru, envelopá-lo automaticamente dentro de um pacote HTTP com statusCode: 200, injetar os cabeçalhos corretos e despachar para o cliente.
  • Tratamento e Mapeamento de Erros: Como o Lambda devolve apenas o resultado bruto da execução, se ocorrer um erro de validação ou lógica dentro da função mas o script terminar sem crashar a runtime, o API Gateway considerará a execução um sucesso e devolverá um falso HTTP 200 OK!

    Para evitar isso, é obrigatório configurar expressões regulares de mapeamento de erro na Integration Response do API Gateway, instruindo o serviço a inspecionar mensagens de erro e converter a resposta no código HTTP correto (400, 404 ou 500).

O Poder da Transformação de Payloads (VTL - Apache Velocity Template Language)

A maior vantagem do modelo Non-Proxy é a capacidade de interceptar e reescrever dados "em voo" usando Modelos de Mapeamento (Mapping Templates) escritos em VTL (Apache Velocity Template Language):

  • Na Ida (Integration Request): O API Gateway pode interceptar a requisição enviada pelo front-end, remodelar o payload e repassar para o Lambda apenas os campos no formato esperado. Como demonstrado no slide acima, se o front-end envia firstname e lastname separados, o VTL do API Gateway pode concatená-los dinamicamente em um único campo name, aninhar propriedades de endereço (address: { city, state }) e transformar valores antes de entregar para o backend.
  • Na Volta (Integration Response): O VTL pode filtrar campos confidenciais, reestruturar listas e padronizar o JSON final entregue ao cliente sem exigir que nenhuma linha de código seja alterada ou reimplantada no Lambda.

9. Part 4: Integrating with API Gateway

Esta etapa final de integrações explora padrões arquiteturais avançados no Amazon API Gateway, essenciais para engenheiros de nuvem e arquitetos que desenham soluções corporativas de alta escala, migrações legadas e segurança de rede.

1. Integrações de Primeira Classe (First-Class Integrations)

Em muitas arquiteturas de microsserviços, desenvolvedores criavam uma função Lambda simples apenas para receber um payload HTTP e enfileirá-lo no Amazon SQS ou acionar uma máquina de estados. Isso gerava custos de execução extras e aumentava a latência (o chamado "Lambda tax").

Com as integrações de primeira classe nas HTTP APIs, o próprio API Gateway realiza essa chamada de forma nativa e direta para outros serviços da AWS, sem necessidade de nenhum código intermediário:

  • Como funciona: Se você deseja que a API envie uma mensagem diretamente para uma fila do Amazon SQS (SQS-SendMessage) ou inicie a execução de um fluxo no AWS Step Functions (StepFunctions-StartExecution), você mapeia o corpo da requisição HTTP (.body) diretamente nos parâmetros que o serviço de destino exige.
  • Vantagens arquiteturais: Menor custo financeiro, latência mínima e menos código de infraestrutura e aplicação para manter.

2. Integrações de Proxy HTTP (O Padrão de Migração Strangler Fig)

Um dos cenários mais cobrados em arquitetura corporativa e exames de certificação de nível avançado é a migração controlada e sem indisponibilidade de sistemas legados monolíticos para microsserviços modernos na nuvem.

O processo de migração divide-se em 3 etapas progressivas (baseado no consagrado padrão arquitetural Strangler Fig):

  1. Etapa 1 (Cenário Inicial): O cliente/website consome diretamente uma aplicação monolítica legada hospedada em instâncias Amazon EC2 (ex: rotas [GET] /products e [GET] /services).
  2. Etapa 2 (Inserção do Proxy): O API Gateway é posicionado na frente de toda a arquitetura. Inicialmente, o Gateway apenas repassa todas as rotas (HTTP Proxy Integration) direto para o servidor EC2 existente. Para o usuário final e para o front-end, o endpoint se unifica sem quebrar nenhuma funcionalidade.
  3. Etapa 3 (Desmontagem Gradual do Monólito): Conforme a equipe refatora módulos específicos para o modelo serverless, você atualiza apenas a rota refatorada no API Gateway (ex: [GET] /services agora aponta para uma função AWS Lambda moderna), enquanto as rotas restantes ([GET] /products) continuam sendo encaminhadas para a EC2. O monólito é estrangulado e migrado de forma 100% invisível para os clientes.

3. Integrações Privadas (Private Integrations & VPC Link)

Por padrão de segurança, bancos de dados, containers e servidores implantados em sub-redes privadas dentro de uma Amazon VPC não possuem endereços IP públicos e não podem ser alcançados diretamente a partir da internet pública.

A solução corporativa da AWS é o VPC Link:

  • O que é o VPC Link: É um canal de comunicação de rede seguro e de alta largura de banda que conecta o API Gateway diretamente a recursos internos da sua VPC.
  • Como opera: O tráfego recebido pelo API Gateway é autenticado (via permissões IAM, Amazon Cognito Authorizer ou Lambda Authorizer) e encaminhado através do VPC Link para um balanceador de carga interno (Network Load Balancer - NLB ou Application Load Balancer - ALB) ou via AWS Cloud Map.
  • Destinos suportados: O balanceador interno pode distribuir requisições para instâncias Amazon EC2, tarefas de containers no AWS Fargate / Amazon ECS, pods em clusters Amazon EKS ou até servidores no data center corporativo (on-premises) conectados via AWS Direct Connect ou VPN Site-to-Site.

4. Transformando Requisições e Respostas (Parameter Mapping em HTTP APIs)

Enquanto as APIs REST utilizam a complexa linguagem de template VTL para transformar mensagens, as HTTP APIs (leves, modernas e mais econômicas) contam com uma funcionalidade nativa e declarativa chamada Mapeamento de Parâmetros (Parameter Mapping):

O Parameter Mapping permite interceptar e manipular dados nos dois sentidos do fluxo:

  • Ações Disponíveis:
    • append: Adiciona valores a cabeçalhos ou parâmetros existentes.
    • overwrite: Sobrescreve completamente o valor de um cabeçalho, query string ou caminho.
    • remove: Remove cabeçalhos ou query strings sensíveis antes de entregar a requisição ou resposta.
  • Alvos de Manipulação: Cabeçalhos HTTP (headers), parâmetros de URL (query strings) e reescrita de caminhos da URL (path rewriting).

Exemplo de configuração via AWS CLI (adicionando o identificador da requisição .requestId em um cabeçalho personalizado):

aws apigatewayv2 create-integration     --api-id abcdef123     --integration-type HTTP_PROXY     --payload-format-version 1.0     --integration-uri 'https://api.example.com'     --integration-method ANY     --request-parameters '{"append:header.header3": ".requestId"}'
Atenção à Restrição de Cabeçalhos Reservados (Reserved Headers):
O API Gateway concede ampla liberdade para modificar cabeçalhos customizados, mas bloqueia estritamente a alteração de Cabeçalhos Reservados (como Host, Connection, Content-Length, entre outros cabeçalhos fundamentais de rede) para garantir a integridade dos protocolos de transporte e a segurança da infraestrutura de nuvem da AWS.

10. Deploying an API

Depois de configurar todas as rotas, métodos e integrações de backend, a sua API ainda não está disponível na internet. Para que o mundo exterior (ou o front-end da aplicação) consiga chamá-la, você precisa realizar a Implantação (Deploy).

Para publicar qualquer API no Amazon API Gateway, você é obrigatoriamente exigido a associá-la a um Estágio (Stage).

1. O que são Estágios (Stages)?

Um Estágio é essencialmente um snapshot (retrato congelado) da configuração da sua API em um determinado momento no tempo:

  • A URL Gerada: O nome atribuído ao estágio passa a fazer parte integrante do endereço final do endpoint (ex: https://{api-id}.execute-api.{region}.amazonaws.com/dev/products versus https://{api-id}.execute-api.{region}.amazonaws.com/prod/products).
  • Separação de Ambientes: O uso mais clássico e recomendado dos estágios é isolar os ambientes de ciclo de vida de desenvolvimento:
    • Ambiente dev: Versão instável para testes rápidos e desenvolvimento ativo dos programadores.
    • Ambiente prod (Produção): Versão estável, auditada e com alta disponibilidade que atende os clientes e usuários finais reais.
Diferença de Deploy (HTTP API vs. REST API): As HTTP APIs criam automaticamente um estágio padrão denominado $default com o recurso de auto-deploy ativado (qualquer alteração de rota entra em vigor imediatamente). Já as REST APIs clássicas exigem a criação manual do estágio e o acionamento explícito da ação de Deploy a cada atualização.

2. Variáveis de Estágio (Stage Variables)

Se você possui um estágio de desenvolvimento (dev) e outro de produção (prod), eles obviamente não deveriam gravar no mesmo banco de dados DynamoDB nem acionar a mesma versão da função Lambda.

As Stage Variables resolvem isso de maneira elegante: são pares de chave-valor configurados no nível do estágio que atuam como variáveis de ambiente no roteamento do API Gateway:

  • Permitem apontar a mesma estrutura de rotas da API para backends distintos dependendo do estágio ativo (ex: definindo o ARN da função Lambda dinamicamente com ${stageVariables.lambdaAlias}).
  • Evitam duplicar código, recriar rotas ou gerenciar definições de API separadas para cada ambiente.

3. Implantação Canário (Canary Deployments)

O Canary Deployment é uma estratégia avançada de alta disponibilidade para testar atualizações e novas versões da API em produção com risco mínimo:

  • O Problema: Se você atualizar o código da API para 100% dos usuários simultaneamente e houver um bug crítico não detectado, todo o sistema entrará em indisponibilidade.
  • A Solução Canário: O API Gateway permite instanciar uma versão secundária (Canary) convivendo dentro do mesmo estágio de produção. Você configura uma pequena fatia do tráfego real (por exemplo, 10%) para ser direcionada para a versão nova, enquanto 90% do tráfego permanece seguro na versão antiga e comprovada.
  • O Ciclo de Promoção: A equipe monitora métricas do CloudWatch (erros 4xx/5xx e latência). Não havendo anomalias, aumenta-se a fatia progressivamente (30%, 50%) até a promoção a 100%, momento em que o canário se torna a nova versão estável definitiva e a versão anterior é aposentada.

11. Part 1: Controlling access to a REST API

Chegamos ao pilar crítico de qualquer arquitetura corporativa: Segurança e Controle de Acesso. Não basta colocar a API no ar; é mandatório garantir que apenas pessoas, sistemas e clientes autorizados consigam chamá-la, protegendo seus dados e prevenindo custos operacionais com acessos indevidos.

O Amazon API Gateway possui múltiplas camadas para blindar a API contra tráfego malicioso ou não autorizado. Esta primeira parte foca em bloqueios de rede, identidade de sistemas e firewalls de aplicação:

  • Políticas de Recurso do IAM (IAM Resource Policies):

    Permitem anexar regras de permissão/bloqueio diretamente no endpoint da API. Com elas, você pode, por exemplo, restringir a chamada da API exclusivamente a uma conta AWS parceira, a uma VPC específica ou liberar o acesso ao estágio de dev unicamente para o endereço de IP estático da sua empresa ou laboratório.

    Atenção para exames de certificação: Políticas de Recurso do IAM em nível de API são suportadas nativamente apenas em REST APIs (não disponíveis em HTTP APIs).
  • Domínios Personalizados (Custom Domain Names):

    Permitem substituir aquela URL padronizada e longa gerada automaticamente pela AWS por um endereço profissional e amigável da sua própria marca (ex: https://api.cafeteria-sofia.com).

    Para garantir comunicação segura via HTTPS, o API Gateway integra-se nativamente ao AWS Certificate Manager (ACM) para emissão, validação e renovação automática de certificados SSL/TLS.

  • Certificados de Cliente e Mutual TLS (Client Certificates / mTLS):

    Estabelecem uma camada bidirecional de autenticação criptográfica. Quando a API encaminha requisições para um backend dedicado (como uma instância Amazon EC2), como o EC2 sabe que a requisição partiu legitimamente do seu API Gateway e não de um invasor direto na internet?

    O API Gateway pode gerar um certificado digital X.509 (com validade de 365 dias) que o seu servidor de backend utiliza para validar a autenticidade da chamada antes de processá-la. Esse mecanismo é amplamente utilizado em instituições bancárias, sistemas financeiros e ecossistemas de Internet das Coisas (IoT).

  • AWS WAF (Web Application Firewall):

    O escudo de proteção contra ameaças de camada de aplicação (Camada 7). O WAF protege a API contra ataques comuns da web, como injeção de SQL (SQL Injection) e scripts entre sites (Cross-Site Scripting - XSS).

    Além disso, permite criar regras customizadas de inspeção e mitigação:

    • Bloqueio por intervalos de endereços IP específicos (IP Set Rules).
    • Bloqueio geográfico baseado em países ou continentes inteiros (Geo-blocking).
    • Bloqueio por assinaturas de User-Agents maliciosos, scrapers ou robôs de varredura.

12. Part 2: Controlling access to a REST API

O grande pesadelo de muitos desenvolvedores web ao conectar front-ends modernos a backends na nuvem! Esta seção aborda um bloqueio clássico que a Sofía certamente enfrentaria ao tentar conectar a página estática do site da cafeteria hospedada no Amazon S3 com a API no API Gateway.

O Problema: O que é CORS?

CORS (Cross-Origin Resource Sharing / Compartilhamento de Recursos de Origem Cruzada) NÃO é um bloqueio gerado pela AWS, mas sim um recurso mandatório de segurança implementado pelos próprios navegadores web (Google Chrome, Firefox, Safari, Edge).

Se o seu site está hospedado em www.abc.com e faz uma requisição assíncrona (via fetch() ou AJAX) para a mesma origem exata (www.abc.com/products), o navegador libera a comunicação normalmente (Same domain).

Porém, se o site tentar chamar uma origem distinta, o navegador bloqueia a leitura dos dados recebidos para proteger o usuário final contra roubo de credenciais ou injeção de dados maliciosos.

Uma requisição é considerada de Origem Cruzada (Cross-Origin) se houver qualquer discrepância em:

  • Domínio: De site.com para api.com.
  • Subdomínio: De www.abc.com para api.abc.com ou abc.abc.com.
  • Porta: De site.com:80 para site.com:8080.
  • Protocolo: De http://site.com para https://site.com.

A Solução: A Requisição "Preflight" (OPTIONS)

Para autorizar o tráfego legítimo de um front-end hospedado em outro domínio ou subdomínio, o navegador executa uma verificação prévia e transparente chamada Preflight Request:

  • Antes de disparar a requisição real de escrita ou leitura avançada (como um POST com payload JSON), o navegador envia uma chamada preliminar e leve utilizando o método HTTP OPTIONS.
  • Essa chamada pergunta à API: "O domínio site.com tem autorização para utilizar este método e estes cabeçalhos HTTP?"
  • Se a API responder com os cabeçalhos apropriados (Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers), o navegador libera o envio da requisição real.

O Papel do API Gateway com Mock Endpoints

Se você não utilizasse o Amazon API Gateway, teria que poluir o código das suas funções Lambda com rotas e handlers redundantes apenas para responder às perguntas OPTIONS do navegador, gerando custos desnecessários de computação a cada interação do usuário.

O API Gateway resolve isso de forma elegante:

  • Você clica na opção "Enable CORS" diretamente no console da AWS para a rota desejada.
  • Em REST APIs, o API Gateway cria automaticamente uma rota OPTIONS associada a uma integração do tipo Mock Endpoint. O Mock intercepta a pergunta do navegador e devolve imediatamente os cabeçalhos Access-Control-* com status 200 OK, sem sequer acionar ou cobrar tempo de execução da sua função Lambda.

13. Part 3: Controlling access to a REST API

Para consolidar a segurança e governança de APIs, precisamos de mecanismos robustos para evitar que a infraestrutura seja sobrecarregada por tempestades de requisições — sejam ataques maliciosos de negação de serviço (DoS) ou clientes legítimos com código defeituoso em loops infinitos.

O que é Throttling (Estrangulamento de Taxa)?

Throttling é o mecanismo que limita o volume e a velocidade das requisições aceitas pela API. Quando um chamador ultrapassa o teto definido, o API Gateway interrompe o fluxo imediatamente e devolve o código de status HTTP padronizado HTTP 429 Too Many Requests.

Camadas de Throttling no API Gateway

  • 1. Limites Gerais da Conta (Account-level):

    Por padrão de segurança operacional, a AWS impõe um limite de proteção para a conta inteira de 10.000 requisições por segundo (RPS) por região, com suporte a rajadas (burst) de até 5.000 requisições (baseado no algoritmo Token Bucket).

  • 2. Limites em Nível de Estágio e Rota/Método (Stage & Method-level):

    Permite proteger componentes sensíveis de backend. Por exemplo: o estágio prod inteiro pode suportar até 1.000 req/s, mas uma rota de relatórios analíticos pesados (GET /reports) pode ser estrangulada para no máximo 50 req/s para preservar o pool de conexões do banco de dados.

  • 3. Planos de Uso e Chaves de API (Usage Plans & API Keys):

    Ferramentas projetadas para comercialização de APIs, modelos SaaS e distribuição para parceiros de negócio:

    • Chaves de API (API Keys): Strings alfanuméricas exclusivas fornecidas aos clientes para identificar e autenticar a origem do chamador via cabeçalho x-api-key.
    • Planos de Uso (Usage Plans): Atrelam as chaves de API a regras de consumo:
      • Taxa (Rate): Limite de requisições por segundo (com valor de rajada/burst).
      • Cota (Quota): Teto máximo acumulado em um período (ex: Plano Básico limitado a 1.000 requisições por mês; Plano Pro com 100.000 requisições por mês).

A Hierarquia de Avaliação de Bloqueio (Pegadinha Clássica de Provas!)

Quando múltiplos limites concorrentes estão ativos (no cliente, no estágio e na conta), o API Gateway avalia as regras sempre da mais específica/restritiva para a mais geral, nesta ordem estrita:

  1. Limite de um Método específico para um Cliente específico (configurado no Plano de Uso).
  2. Limite geral do Plano de Uso vinculado à chave daquele cliente.
  3. Limite de um Método/Rota específica configurado diretamente no Estágio.
  4. Limite geral do Estágio (Stage-level).
  5. Limite máximo da Conta AWS na região (as 10.000 RPS).

14. Part 4: Controlling access to a REST API

Mesmo com firewalls perimetrais (AWS WAF), políticas de rede e limites de taxa (throttling) devidamente configurados, você ainda precisa controlar a identidade do usuário e o que ele tem permissão para executar (Autenticação vs. Autorização).

O Amazon API Gateway disponibiliza quatro modelos principais para validar e autorizar requisições de entrada:

  • 1. Nenhum (Open / None):

    A API permanece totalmente pública na internet, sem exigir nenhum tipo de login, cabeçalho de assinatura ou credencial de acesso. Indicada para catálogos públicos de produtos, termos de serviço ou endpoints de health check.

  • 2. Permissões do IAM (IAM Permissions & AWS SigV4):

    Utiliza o sistema nativo de identidade e credenciais da própria AWS.

    • Como funciona: A requisição HTTP precisa ser assinada criptograficamente utilizando credenciais válidas da AWS (Access Key ID e Secret Access Key) através do protocolo Signature Version 4 (SigV4).
    • Se a assinatura estiver ausente, expirada ou o usuário/role IAM não tiver permissão explícita com a ação execute-api:Invoke, o API Gateway barra a requisição de imediato com HTTP 403 Forbidden.
    • Caso de uso ideal: Comunicação interna entre servidores, instâncias Amazon EC2, containers no ECS/EKS, funções Lambda ou microsserviços backend que rodam dentro do ecossistema AWS (onde os AWS SDKs assinam as chamadas de forma automatizada e transparente).
  • 3. Autorizadores JWT (JSON Web Tokens & Amazon Cognito):

    É o padrão ouro do mercado para autenticar usuários finais em aplicativos móveis (iOS e Android) e aplicações web modernas (Single Page Applications - SPAs em React, Vue, Angular), baseando-se nos protocolos abertos OAuth 2.0 e OpenID Connect (OIDC).

    • O Casamento Perfeito com o Amazon Cognito: Em REST APIs, o API Gateway integra-se nativamente com os Amazon Cognito User Pools.
    • O Fluxo: O usuário faz login no aplicativo através do Cognito, recebe um token JWT assinado (ID Token ou Access Token) e o envia no cabeçalho padronizado Authorization: Bearer <token> a cada requisição.
    • O API Gateway intercepta a chamada na borda, decodifica o token, valida a assinatura criptográfica com o Cognito e verifica se os escopos OAuth (scopes) do usuário concedem permissão de acesso àquela rota específica antes de acionar o backend.
  • 4. Autorizadores Lambda (Lambda Authorizers / Custom Authorizers):

    E se a sua empresa tiver um sistema de login legado proprietário, servidores LDAP / Active Directory corporativos, tokens SAML corporativos ou exigir verificações avançadas de segurança em um banco de dados externo?

    • Como funciona: Você cria uma função AWS Lambda dedicada cujo único objetivo é executar a sua lógica personalizada de segurança. Antes de a requisição chegar ao backend real, o API Gateway desvia a chamada para o Lambda Authorizer.
    • O código da função avalia os cabeçalhos, checa os bancos de dados e devolve para o API Gateway uma Política IAM gerada dinamicamente (contendo Effect: "Allow" ou "Deny") associada a um PrincipalId (ou um payload simples {"isAuthorized": true/false} nas HTTP APIs).
    • Vantagem Adicional (Contexto Enriquecido): Permite que o autorizador injete dados contextuais customizados (como ID de usuário interno, perfil de permissões, tenant da empresa) no objeto da requisição, repassando esse contexto enriquecido diretamente para o backend.

15. Monitoring a REST API

Para garantir que a sua API esteja operando com alta disponibilidade e identificar gargalos e falhas de forma proativa, o Amazon API Gateway integra-se nativamente com todo o ecossistema de observabilidade da AWS.

O Coração do Monitoramento: Amazon CloudWatch

O Amazon CloudWatch coleta e processa métricas quase em tempo real, retendo o histórico operacional por até 15 meses. Por padrão, o API Gateway envia quatro métricas cruciais a cada minuto (sem custos adicionais de telemetria):

  • Count (Contagem): O volume total de chamadas recebidas pela API em um determinado período.
  • Latency (Latência Total de Ponta a Ponta): O tempo exato transcorrido desde o momento em que o API Gateway recebeu a requisição do cliente até o instante em que devolveu a resposta final.
  • IntegrationLatency (Latência de Integração): Mede especificamente o tempo que o seu backend (função Lambda, serviço HTTP ou DynamoDB) demorou para responder ao API Gateway.
    Dica de Ouro para Diagnóstico: Se a métrica Latency estiver alta e a IntegrationLatency também estiver alta, a lentidão está acontecendo dentro do código do seu backend ou em consultas lentas de banco de dados. Se a IntegrationLatency for baixa mas a Latency geral for alta, o gargalo está nas transformações de VTL do API Gateway, no handshake SSL/TLS ou em autorizadores pesados.
  • Erros HTTP 4XX e 5XX:
    • 4XXError: Quantidade de chamadas rejeitadas por falha do cliente (401 Não Autorizado, 403 Proibido, 404 Não Encontrado, 429 Too Many Requests por throttling).
    • 5XXError: Quantidade de requisições que falharam por indisponibilidade ou falha interna do backend/servidor (502 Bad Gateway por crash de Lambda, 504 Gateway Timeout).

Logs de Acesso Detalhados (CloudWatch Access Logs): Enquanto as métricas numéricas acima são automáticas, o registro detalhado de quem acessou cada recurso (Logs de Acesso no CloudWatch Logs) é opcional. Para ativá-lo, você cria um Log Group no CloudWatch e o associa a um Estágio da sua API, podendo customizar as variáveis registradas (IP de origem, request ID, método, tempo e user-agent).

O Trio Avançado de Auditoria, Rastreamento e Conformidade

Em ambientes corporativos e questões de exames de certificação AWS, é fundamental diferenciar com clareza o propósito de cada uma destas três ferramentas adicionais:

  • 1. AWS X-Ray (O Rastreador de Gargalos):

    Responde à pergunta: "Onde exatamente está o problema na minha arquitetura?"

    Executa o rastreamento distribuído de ponta a ponta (Distributed Tracing). Se a requisição passa pelo API Gateway, aciona uma função Lambda e efetua uma busca no DynamoDB, o X-Ray gera um mapa visual de serviços (Service Map) detalhando quantos milissegundos foram gastos em cada nó e microsserviço individual. Indispensável para diagnosticar problemas de latência e cold starts.

  • 2. AWS CloudTrail (O Histórico de Auditoria / Caixa-Preta):

    Responde às perguntas: "Quem fez isso? Quando fez? O que modificou?"

    Grava toda e qualquer chamada de API de gerenciamento (operações de Control Plane) executada dentro da sua conta AWS. Se um administrador alterar as configurações do API Gateway, deletar uma rota ou modificar permissões de segurança, o CloudTrail registra a identidade do usuário IAM, data/hora e IP de origem.

  • 3. AWS Config (O Avaliador de Conformidade e Governança):

    Responde à pergunta: "Essa modificação segue as regras de governança e conformidade da empresa?"

    Registra o histórico contínuo de configuração dos recursos da AWS e avalia se eles estão em conformidade com as políticas corporativas (compliance). Se alguém configurar um endpoint do API Gateway como público sem vincular o AWS WAF (quando as regras internas exigem proteção obrigatória), o AWS Config marca o recurso como não-conforme e pode disparar remediações automáticas.

16. Optimizing API Gateway

Chegamos à reta final do Módulo 6! Depois de criar, integrar, implantar e proteger a sua API, o passo que coroa uma arquitetura em nuvem resiliente e profissional é a Otimização de Desempenho e Custos.

Detalhes sobre custos fixos vs. variáveis e armadilhas de performance são temas favoritos em bancas de concursos públicos e exames de certificação de TI (como o AWS Certified Developer - Associate). Para melhorar o tempo de resposta (latência) e diminuir a carga sobre o seu backend, o Amazon API Gateway disponibiliza duas estratégias principais de otimização:

1. Cache (Armazenamento em Memória)

Disponível para REST APIs clássicas, o cache permite que o API Gateway "decore" a resposta de requisições de leitura frequentes (especialmente métodos GET):

  • Como Funciona o Ciclo de Vida:
    • Quando um cliente requisita um recurso (ex: a lista de produtos da cafeteria), o API Gateway primeiro consulta o cache em memória.
    • Se a resposta já estiver armazenada (Cache Hit), o Gateway devolve os dados imediatamente sem repassar a chamada para a função Lambda ou banco de dados.
    • Se a resposta ainda não estiver em memória (Cache Miss), ele aciona a função Lambda normalmente, entrega a resposta ao cliente e salva uma cópia no cache vinculada àquela chave de busca.
  • Chaves de Cache (Cache Keys): Você pode personalizar as chaves que diferenciam uma resposta de outra, incluindo parâmetros de caminho (path parameters), cabeçalhos específicos (headers) ou parâmetros de busca (query strings).
  • Tempo de Vida (TTL - Time to Live): Você define o tempo de validade dos dados no cache (padrão de 300 segundos / 5 minutos, configurável entre 0 e 3.600 segundos). Também é possível habilitar criptografia em repouso para os dados cacheados.
  • Métricas de Monitoramento no CloudWatch:
    • CacheHitCount: Quantidade de vezes em que o cache atendeu a requisição, poupando o backend.
    • CacheMissCount: Quantidade de vezes em que a requisição precisou ir até o backend por ausência no cache.
A Pegadinha de Custo (Atenção em Provas e Projetos Reais!):
Diferente do core do API Gateway (que é puramente serverless e cobra apenas por requisições recebidas), o Cache é cobrado por HORA de provisionamento contínuo do nó de memória (com tamanhos variando de 0,5 GB até 237 GB), independentemente de estar recebendo tráfego ou não!

É essencial avaliar se a redução nos custos de invocação do Lambda e a queda de latência compensam o custo fixo horário da infraestrutura de cache provisionada.

2. Compressão de Payload (Payload Compression)

Se a sua API precisa devolver arquivos JSON extensos para o front-end, trafegar pacotes gigantescos pela internet consome tempo de rede e eleva custos de transferência de dados (Data Transfer Out). A solução nativa é habilitar a compressão de payloads (com algoritmos padronizados como gzip ou deflate):

  • Como Funciona: O cliente envia o cabeçalho Accept-Encoding: gzip indicando que seu navegador aceita dados compactados. O API Gateway compacta o corpo da resposta em trânsito antes do despacho, diminuindo expressivamente o tamanho transferido.
  • Configuração de Limite (minimumCompressionSize): Você define o tamanho mínimo (em bytes, configurável de 0 até 10.485.760 bytes / 10 MB) a partir do qual o API Gateway deve disparar a compressão.
O Risco da Supercompressão (Overhead de Processamento):
Se você configurar o minimumCompressionSize para 0 (forçando a compressão de absolutamente todas as respostas), você pode degradar a performance global da API em vez de melhorá-la!

Comprimir payloads microscópicos (ex: respostas de 50 ou 100 bytes) consome processamento inútil de CPU do servidor para empacotar e do navegador do cliente para descompactar. Além disso, devido ao overhead dos cabeçalhos do formato gzip, o arquivo compactado pode acabar ficando maior do que o JSON original! A melhor prática é estipular um piso mínimo prudente (por exemplo, a partir de 1 KB / 1024 bytes) validado por testes de carga.
